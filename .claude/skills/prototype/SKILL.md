# 原型

原型是回答一个设计问题的可丢弃代码, 问题决定其形态. Main Agent 分配原型任务和写入范围. 写入前遵循 [Subagent 分配](../../../docs/agents/subagent-allocation.md) 和 [Agent 文件写入](../../../docs/agents/agent-writes.md).

原型作者把验证结果和未解决的重要决定交回 Main Agent, 不自行把原型合入正式代码或决定长期设计.

## Pick a branch

识别要回答的问题, 可以来自用户请求, 周围代码或 Main Agent 提供的上下文:

- `逻辑或状态模型是否合适?` -> [LOGIC.md](LOGIC.md). 构建一个可共享的 HTML 文件, 提供可自由操作的按钮, 并用标签页组织分步引导, 让非开发者也能操作状态机, 检验难以只靠文字推理的情况.
- `它应当如何呈现?` -> [UI.md](UI.md). 在单一路由上生成多个设计明显不同的 UI 变体, 使用 URL 查询参数和底部浮动栏切换.

两种分支产生不同产物. 问题确实不明确时, 把需要用户决定的选择交回 Main Agent.

## Shared rules

1. 从一开始就标明可丢弃. 将原型放在接近其探索对象的位置, 并以名称表明它不是正式代码. 可丢弃 UI 路由遵循已有路由约定, 不创建新的顶层结构.
2. 保持易于运行. UI 原型从项目任务运行器的一条命令启动, 例如 `pnpm <name>`, `python <path>` 或 `bun <path>`. 逻辑演示是可直接打开的单个 HTML 文件.
3. 默认不持久化. 状态保留在内存中. 持久化应是原型要检验的问题, 而不是原型运行的前提. 如果问题明确检查数据库, 使用带有 `PROTOTYPE - wipe me` 清楚标记的临时数据库或本地文件.
4. 不追求正式代码的完整度. 只保留原型可运行所需的错误处理, 不添加测试或抽象.
5. 每次逻辑操作或变体切换后显示完整相关状态, 使用户能看到变化.
6. 原型回答问题后, 把它解决的问题, 结论和理由返回 Main Agent. Main Agent 核对结论, 按重要决定规则处理需要用户确认的选择, 并安排将已验证的决定落实到正式代码.

   随后将原型本身作为一手资料保留在对应 effort 的 `.scratch/<NNNN>-<effort-slug>/prototype/<name>/` 下. Main Agent 在 issue 或提交说明中记录问题和结论, 并按仓库正常流程及已有提交授权, 将原型与适用的 effort 记录一起提交.
