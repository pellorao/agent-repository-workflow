# Drift check

发布时由 `release` Skill 的可选步骤调用 (维护者选 run 或 skip), 也可由维护者单独调用. 目的是发现提供方更新默认模型或 CLI 升级造成的 Reviewer 能力下降; 它不是发布门禁, 不授权审核, 提交或发布.

1. 四个场景在两个后端的默认设置 (Codex `gpt-6-luna` `xhigh`, Claude `haiku` `high`) 各跑 1 个实例, 共 8 个, 按 `./SKILL.md` 的 Run 节计分并定稿 (盲裁用至少 sonnet high 的裁判).
2. 每格的 `final` 与同目录 `last-results.md` 中同场景, 同后端, 同设置的记录比较, 不使用绝对分数门槛. 没有记录的格只登记, 不比较.
3. 某格 `final` 比记录低 0.15 以上时, 同格再跑 2 个实例; 3 个实例的平均仍比记录低 0.15 以上才判定漂移, 停下排查 (模型版本, CLI 版本, Reviewer 运行时) 并在发布准备 issue 的 `## Comments` 报告, 不自动修复. 0.15 只决定是否多跑 2 个实例, 不是失败判定, 因为单个实例有波动.
4. 检查可在全部 VM 通过之后运行, 但结果只在发布完成之后 (`release` Skill 第 5 节) 把各格本次结果 (有加跑时取 3 个实例的平均) 写入 `last-results.md`, 运行 `node scripts/project-claude-skills.mjs` 重新投影, 再把表与投影一起提交 (先提交会让投影留在未提交状态, `--check` 失败); 候选修复导致发布流程重来时丢弃本次结果. 同一格只保留最新一行. 只有本检查维护该表, A/B 与回归的结果不写入. 写入或提交失败, 或检查在写入前中断时表保持原样 (已发布版本的登记可以缺失, 旧行保留), 下一次检查以表中仍有的行为基准, 没有则只登记, 并在发布准备 issue 的 `## Comments` 报告维护者, 不阻止任何发布步骤, 也不重跑已完成的检查. 两次检查之间改动频繁时, 一次检查覆盖这期间的全部变化. 每格只与上一次记录比较并覆盖它, 所以多期缓慢累积的下降不会被识别; 本检查只发现明显下降, 不追踪长期趋势.
