# 测试性能优化流程

本流程适用于创建或语义变更测试案例后的耗时检查, 以及以降低现有测试套件耗时为目标的优化工作. 使用目标仓库已有的测试命令, 报告器或性能分析功能, 不预设语言, 运行时或测试框架.

## Threshold

目标仓库在根 `AGENTS.md` 的 Repository-owned 区域声明单个测试回调耗时阈值. 该阈值计入回调等待的设置, 实际执行的行为和断言, 不根据子用例的累计耗时再次约束只负责分组的父回调.

创建测试案例或对其进行语义变更后, 在暂存或报告完成前测量当前候选内容中相应回调的耗时. 测量结果不得超过仓库阈值, 或已取得用户对精确案例及其实测耗时的例外批准. 只有各案例原因相同时才把例外请求合并为一个批次.

仓库没有已记录阈值时, 先创建 issue 并采集基线, 然后在修改测试或实现前由用户决定阈值并把它记录到根 `AGENTS.md` 的 Repository-owned 区域. 不从其他仓库或工具默认值推断阈值.

该阈值约束测试设计和修改决定. 普通测试运行不因墙钟超过阈值自动失败, 除非用例本身验证时间行为. 不设置所有仓库日常运行的统一套件耗时上限. 用户触发清理任务的默认完整命令目标由[测试价值清理](../test-value-cleanup/SKILL.md#default-scope-and-goals)拥有, 可按当前任务调整, 不改变本回调阈值.

## Baseline

开展现有测试套件的性能优化前, 先创建覆盖该工作的 issue. 在第一次修改前运行一次完整测试套件, 记录套件总耗时和单个测试回调耗时前 10 名. 记录测量命令, 运行环境和统计单位, 使后续结果可以按相同口径比较.

优先使用仓库已有的测试命令, 报告器或性能分析功能. 如果它们无法提供单个回调耗时, 建立临时且可移除的测量入口; 完成测量后移除该入口, 除非 issue 明确要求把它作为长期能力交付.

如果存在已知较快的历史版本, 或者性能变化与一批新增测试的范围相符, 把相应版本或变更范围作为结构对照. 比较测试声明与实际回调数量, 共享准备和生命周期调用, 参数矩阵, 实例数量及真实外部边界, 定位从何处开始重复工作. 历史对照不替代当前候选的完整套件基线.

当前 10 名由彼此独立的慢案例构成时, 继续逐例处理. 如果单个文件或测试组主导套件耗时, 或大量新增案例共享同一准备和验证成本, 对该文件或测试组进行一次剖析, 按共享根因统一重构. 共享重构可以影响本批列表外的案例; 下一批仍只使用本批结束后的完整套件排名选择目标.

## Optimization methods

优化前先读取长期规格和适用验证规则, 提取必须证明的每个可观察结果. 既有兼容或行为合同即使没有在一份文档中逐字重述, 仍赋予相应结果保留责任; 先根据公开 Interface, 对外结果及失败与恢复承诺判断合同, 不得把文档没有逐字列出某项行为理解为可以删除该产品行为.

为每个必须证明的结果保留一个最小代表. 现有测试回调, fixture, 测试数据和参数矩阵只是验证实现, 不构成独立的保留依据; 只有既有兼容或行为合同及适用文档要求能够赋予测试点保留责任. 一个案例能够证明多个必要结果时可以保留这些断言, 不根据内部步骤为它增加额外测试边界.

- 区分真实边界接线与语义组合. 文件系统, 进程, 命令行入口, 安装和发布链路通常先保留 1 至 2 个能够证明成功结果或关键失败结果的真实边界案例. 这个数量是寻找最少充分集的常见起点, 不是跨仓库上限; 每项独立边界责任都必须有对应案例.
- 缩小每个真实边界案例自身. 使用能够证明接线结果的最小代表数据, 创建最少的文件, 启动最少的进程, 并执行最少的完整生命周期调用. 只有真实边界合同本身要求的参与者, 场景, 实例和数据才留在该案例; 参数, 格式, 失败, 多实例, 多角色和聚合组合使用内存数据调用正式生产解析, 绑定, 评分或聚合 Interface.
- 把同一生产入口的参数, 格式和错误等价类放入一个表格驱动的测试回调. 根据不同的可观察结果, 失败影响或恢复结果选择代表输入, 不以穷举参数为目标.
- 复用共享且不可变的准备结果. 当多个案例需要相同输入时, 一次完成源码检出, 安装, Git 操作, 复制, 发布构建或准备/验证, 再为会被修改的数据创建隔离副本. 不得让复用把案例顺序变成通过条件.
- 删除与断言责任无关的准备, 数据和生命周期阶段. 如果下层正式 Interface 已由一个真实边界案例证明接线, 语义组合案例直接调用该 Interface, 不重复更外层的完整链路.
- 对彼此独立的读取或准备工作使用批量 Interface, 或在资源上限内并发执行. 保留确定顺序, 首个错误, 并发上限, 失败影响和恢复结果; 这些结果要求顺序执行时继续顺序执行.
- 命令行, 安装和发布测试保留能够证明真实入口, 参数传递, 输出, 退出状态及最终文件结果的最少端到端案例. 其余错误和组合通过正式模块 Interface 定向验证.

统一重构后, 同时核对声明和实际回调数量. 普通保留覆盖的优化, 对每个删除或合并项指出原责任由哪个保留案例或表格行证明. 用户触发价值清理时, 经本次明确接受的低风险独立观察损失按[清理流程](../test-value-cleanup/SKILL.md#value-and-authorization)如实记录, 不要求不存在的完全替代. 核心保证始终保留, 不把未说明损失当成耗时优化.

## Iteration

每个批次以一次完整测试套件测量开始, 记录总耗时和当前单回调前 10 名, 并冻结这份最多包含 10 个案例的本批列表. 首个批次使用基线测量; 后续批次直接使用上一批结束时取得的完整套件结果, 不重复运行相同的边界测量.

依次处理本批列表中的每个案例:

1. 编辑前对目标案例进行定向测量. 如果本批前面的共享优化可能已经影响该案例, 以这次结果替代批次开始时的耗时; 已不超过阈值的案例记录结果后跳过.
2. 分析仍然超出阈值的案例的主要成本和独立覆盖责任, 然后实施一个保留必要语义覆盖的改进. 通过减少重复准备, 不必要的文件或进程操作, 或跨边界重复工作降低成本, 不为达到阈值拆分测试案例.
3. 对修改后的目标案例进行定向测量, 并运行该变更需要的相邻验证.

批次中途只有在定向验证失败, 测量口径失效或变更风险要求时才运行更广的验证; 完整测试套件不是每个案例的固定步骤. 处理或跳过本批全部案例后, 运行一次完整测试套件, 记录新的总耗时和单回调前 10 名, 并把结果作为下一批基线.

目标案例在修改前和修改后都要定向测量. 只有当结果接近阈值, 排名不稳定或波动明显时, 才至少测量 3 次并使用中位数作出判断; 其他情况默认各测量 1 次.

Agent 可以自主实施容易撤销, 没有外部影响, 不改变产品语义或独立覆盖合同的优化. 低风险独立损失按清理流程取得本次准确范围授权, 已获授权的批次不重复请求. 新的独立损失, 公开 Interface 或架构变化, 长期依赖及阈值例外仍按重要决定规则处理, 不扩大既有取舍.

## Completion

以单案例性能达标为目标时, 批次结束的新前 10 名均满足仓库阈值或准确实测例外后, 结束单案例循环. 总耗时尚需降低时, 使用当前 issue 已明确的总耗时目标继续分析共享准备, 进程启动, 并发和测试组成本; 没有该目标时先记录并取得适用决定. 价值清理按[清理流程](../test-value-cleanup/SKILL.md#delete-and-optimize)判断默认完整命令目标和优化结束时点, 不要求重复设定目标, 也不把未修改的慢回调自动纳入额外目标. 各新建或语义修改回调的测量及阈值例外责任保留. 不能把回调达标当作尚未达成的完整命令目标已经完成.
