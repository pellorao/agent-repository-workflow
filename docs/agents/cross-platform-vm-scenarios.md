# 跨平台 VM 场景

## Real Repository matrix

对于发布, 每个受支持的平台都根据同一份候选内容验证长期发布规范所要求的目标仓库行为. `release-validation.json` 负责当前来源远程仓库 URL, 精确提交和明确的初始化 issue 场景选择. Release Validation Registry Module 负责场景清单, 顺序, 选择, 预期问题和语义操作, 并在 Registry 负责的位置把已注册的初始化 issue 操作绑定到已配置且符合条件的场景. 主机必须获取已配置的提交并创建捆绑包. 提交不可用时以关闭方式失败, 且不得回退到远程默认分支. 来宾系统只克隆本地捆绑包. 外部 VM JSON 不负责目标仓库 URL, 提交或 Registry 策略. 不得把来源远程仓库, 分支, 提交, 捆绑包或其他 Git 身份保留为发布证据.

Registry 为每个目标记录:

- 现有 Agent 状态.
- 工作流初始化配置.
- 适用的 Code Map 输入.
- 转换选择, 更新输入和删除选择.
- re-init 配置.

这些值在修改 VM 前固定于 Scenario Plan 中, 不在每个步骤前重新检查. 已注册的发布验证选择覆盖一种受支持的产品行为, 不限制用户在普通仓库中选择其他合法值. 不适用的选项会被省略, 而不是使用猜测的值进行序列化.

Registry 负责精确的生命周期步骤和 ID. 绑定到 `release-validation.json` 所选场景的操作会在第一次初始化后创建并完成初始化 issue, 并在 Registry 负责的位置执行完整的 Agent Post-init Handoff. 该记录是普通实施 issue. 只对这项可丢弃的发布验证操作省略该 issue 的 Spec Readiness. 场景不请求或创建来宾系统提交, 因此不会触发 Code Review, Commit Audit 和提交操作, 也没有豁免, 但不得把该场景限制写入目标 issue. 这项只适用于发布的省略不会改变普通仓库中相同任务适用的工作流. 其他初始化和重新初始化步骤遵循 Registry 当前定义.

实施前, Main Agent 创建处于 `ready-for-agent` 状态的初始化 issue. 如果不存在 Repository-owned 缺口, 该 issue 失败, 而不是在没有实施的情况下完成. 把所有目标仓库 Agent 指令视为审计输入. 发生冲突时, 当前已安装的 Workflow Distribution 是权威来源. 检查责任与 Workflow Distribution 规则重叠的每条指令. 使用当前 Workflow Distribution 行为替换每条冲突的 Repository-owned 规则, 删除语义重复项, 并保留每条不冲突的 Repository-owned 规则. 完成冲突解决后, 保留的目标规则适用于剩余的初始化 issue 工作. 使用已配置且只适用于发布的答案应用 Registry 列出的每项用户选择, 无需询问用户, 同时保留精确的仓库事实, 并完成由此产生的每项验证. 这项委托选择不会改变普通用户选择规则. 如果现有权威无法判定两条规则是否冲突, 把该决定交还用户. 把 issue 设为 `completed` 前, 在精确的 `## Validation` 标题下记录每项已经解决的冲突, 完整差异审查和非空验证证据.

对于具有 Code Map 的目标, 除非 Registry 明确授权, 否则不得运行批量 Code Map README 更新. 把每次 Code Map 验证与 Registry 完整排序的预期问题, 退出状态, 标准输出和标准错误进行比较. 不得根据虚拟机或场景名称推导 issue 完成后的预期集合. 不要求再次证明问题与初始化前状态一一对应. 每个步骤后审查完整差异, 并拒绝对现有 README 或 Repository-owned Agent 内容的任何变更, 除非该步骤明确授权.

## ARW lifecycle matrix

长期发布规范负责必要的 Installation 和最低运行时覆盖. Release Validation Registry 把这些责任分配给当前虚拟机场景, 并记录精确步骤, 命令解释器, 重启行为, 运行时标签和预期结果. 不得根据虚拟机键推断分配关系. 每个已注册 ESM 项必须具有一个完整结果, 其退出代码为 `0` 且输出流为空. 缺失, 重复或多余的项结果会使操作失败. 已注册的启动器观察必须输出预期的候选版本, 输出空标准错误, 并使完整受审文件状态保持不变. 不得在任何来宾系统中安装 pnpm 或开发依赖, 也不得运行 `pnpm typecheck` 或完整的 `pnpm test`. 这些检查证明 Source Checkout, 并在主机端的 `pre-tag` 检查中运行一次. 它们不能证明 Installation 目录或目标仓库.

已注册的有限非命令步骤使用其已注册操作和机械合同. 如果此类步骤观察 Installation 最终状态, 其步骤身份和操作合同身份仍是不同字段. Runner 负责其封闭输入, 精确的测试自有路径, 允许的变更, 完整观察和机械判断. Main Agent 不填写其普通判断, 但仍分析任何失败, 并决定临时补偿是否安全或有用.

问题, 包括发布阻断项, 不会为了修复 Source Checkout 而中断发布运行. Runner 保留正式失败记录, 推进不依赖待处理响应的每条路径, 并且只在没有其他记录可以推进后返回一个待处理清单路径. 每个补偿项把当前失败或补偿检查结果路径与最小响应模板路径配对. 必要的虚拟机安全处理不会等待该暂停.

Main Agent 分析结果, 决定安全, 最小且明确标记的临时补偿是否有用, 并在 Runner 外修改 VM. 已应用的响应绝不重放原始修改操作. Runner 改为执行失败步骤现有的只读预期状态检查:

- 机械检查通过后, 继续诊断后代路径.
- 机械检查失败时, 保存其已定义结果, 创建新的单次授权, 并再次暂停.
- 语义失败时, 重新捕获完整事实, 并创建新的语义判断交接. 再次判断失败时同样创建新授权.

Runner 绝不选择或执行修复, 且补偿响应不描述修复. 补偿后代路径在当前会话 `.tmp` 工作区中保持为诊断内容, 不进入规范归档, 也不会使候选内容成为通过状态. 在批量处理实施 issue, 代码变更, 验证和提交前, 完成所有可执行路径. 修复后的候选内容从头重新开始正式发布.

不得为不可用的流创建空输出文件, 也不得根据 `incomplete`, `failed`, `diagnostic`, `unresolved`, `pending-handoff` 或 `cleanup-failed` 场景创建规范归档. 已接受归档中的每个命令步骤记录实际的整数子进程退出代码. 只有流可用时才存储 `stdout.txt` 或 `stderr.txt`. 可用的零字节流仍是精确的空文件. 非命令有限操作和语义步骤没有退出代码或输出文件. 记录实际结果是否满足步骤预期的是 `matchesExpected`, 不能只看退出代码.

任何生命周期或仓库场景都不下载, 探测, 检查或启动 Codex, Claude Code 或其他 Agent CLI. 明确的工作流初始化选择决定投射哪个平台的内容. Agent CLI 可用性不属于 VM 基线或发布结果.

如果子进程有意调用裸 `node`, 测试驱动程序必须把所选 Node.js 24 或更高版本的运行时放在 PATH 首位. 仅使用绝对 `node` 路径启动父测试运行程序, 不能证明子 CLI 也使用同一运行时.
