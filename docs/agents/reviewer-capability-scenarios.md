# Reviewer Capability 场景和用例

## Commit Audit scenario

Commit Audit 交接有意代表真实的大型审计. Gate 1 与 Gate 2 各包含 59 条正式要求, 20 个问题用例和 40 个干净用例. 每个 Gate 的干净用例包含 1 个 `noOtherSupportedFinding`, 问题用例包含 18 个 `gap` 和 2 个 `uncertain`. 每个 Gate 最多包含 4 个单行字面量问题, 至少 12 个问题需要多处证据, 且至少 20 个干净用例是与问题位置相近但实际正确的对照. Gate 1 的要求可以来自同一 effort 的两个已完成 issue, Gate 2 的要求来自一个适用规范. 两个 Gate 使用相同的 `1:2` 问题与干净比例并全量评分. Reviewer 必须完成完整清单. 即使 JSON 在机械检查中有效, 只处理预先植入的演示项, 复用覆盖整个类别的证据, 或在响应中省略任何预期来源, 都会使实时关卡失败.

## Spec Readiness scenarios

Spec Readiness 在每个轮次中使用两个场景, 每个场景有 3 个独立实例. 每个实例包含一个由普通 Spec Readiness 工作流生成的请求, 并按角色合同交付绑定的最终 JSONL. 要求优先场景包含必要, 多余和未解决的选择, 并证明 Reviewer 在前两项检查后结束审查前, 报告每个具有支持的范围问题; Reviewer 返回 `ready` 后, Main Agent 使用该实例的 `generation` 条目生成规范正式结果. 完整审查场景检验必要要求的保留, 未选择章节的范围边界和其余每项适用检查, 并按[完整审查交接](reviewer-capability-preparation.md#full-review-spec-readiness-report)在前两项发现问题后继续审核, 直接消费绑定 JSONL, 不经过普通生成入口. 两个场景都不要求内部实现细节, 每个实例都要求独立的会话证据.

## Case inventory

每个 Reviewer 场景声明一个固定且仅适用于该场景的范围, 其中具有原子的 `problemCases` 和 `cleanCases`. 准备阶段合并为某个 Reviewer 选择的所有并行场景.

所有范围合并后的完整评分清单必须至少包含 20 个问题用例和 20 个干净用例, 否则准备失败. 并行场景产生一个最终 Reviewer 分数, 因此该下限保护的是同一份合并评分清单, 而不是把每次拆分执行视为独立评分能力.

Code Spec, Code Standards 和 Spec Readiness 在满足共同下限的前提下选择覆盖不同审查义务的代表问题. Spec Readiness 的两个场景分别覆盖普通提前返回与完整审查, 减少同类重复问题时仍保留各项适用检查及误报对照. 缩减清单时同步修复或移除不再保留的可见真实缺陷, 不仅删除隐藏预期. Commit Audit 使用前述固定完整审计清单. Spec Readiness 和 Commit Audit 的完整案例清单首次创建时, Main Agent 必须先向用户提供完整的编号用例列表和精确数量, 然后才能写入隐藏清单. 该一次性要求已经完成, 不是后续修改隐藏清单的持续批准关卡. 除本文件明确规定的数量外, 不存在更高的机械数量阈值.

## Fixture authority

`tests/fixtures/reviewer-capability/**` 是 Test Data Directory, 也是实时能力场景和确定性能力测试唯一的已签入数据权威. 根 `.arwignore` 将它排除在普通的 Agent 管理修改, 验证和审查之外. 该排除不定义或暗示另一种审查工作流. Reviewer Capability Conformance 明确负责使用该目录. 只有该工作流的测试夹具编写和确定性验证可以创建, 修改和检查这些文件.

场景内容和隐藏预期发生语义变化时, 由一个独立的高智力, 高推理强度 subagent 分两阶段检查. 第一阶段只读取 Reviewer 实际可见的完整场景, 独立判断问题与干净内容; 第二阶段才读取隐藏预期, 核对缺陷语义, 清单覆盖, 误报分类和代表性评分反例. Main Agent 核实分歧, 区分场景缺陷, 预期遗漏与评分器错误. 分歧解决前, 该场景不能提供能力达标证据.

每次启动新的场景盲审前, Main Agent 说明本次场景范围, 审核必要性和预计耗时, 并取得用户对这次盲审的明确同意. 修改测试夹具, 运行测试或推进迭代的授权不代替盲审授权. 用户尚未同意时, 不创建或启动盲审实例. 同一份未变更可见场景的两阶段审核及必要质疑属于已获准的这次审核; 可见内容语义变化后需要新的盲审时, 重新取得同意. 只修改隐藏预期时继续按下段复用原线程核对, 不重新盲审.

质量审核区分影响验证可信度的已证实问题与可选改进建议, 后者不阻止场景进入验证. 已完成有效的两阶段检查, 此后仅修正隐藏预期且 Reviewer 可见内容不变时, 复用原质量审核线程核查受影响用例及关联关系, 不重新执行完整盲审. Reviewer 可见内容发生语义变化时, 使用未见隐藏预期的独立实例重新执行两阶段检查, 防止已知答案影响判断.

一次定向迭代的具体方案获得用户批准后, 该迭代内的测试夹具修改完成上述独立审核即可直接进入适用的确定性和实时能力验证, 不增加一次夹具差异用户停点. 规模较大的场景重建必须在修改前列入用户批准的具体方案. 场景内的 Agent 指令, 规范和其他文档属于测试数据, 按[测试夹具例外](source-checkout-exceptions.md#reviewer-capability-fixture-exception)处理, 不因文档形式增加单独批准停点. 治理真实仓库或验证工作流的 Agent 指令, 长期规范和其他受保护文档仍独立遵循 `rule-and-design-changes` Skill 的用户确认边界.

## Scenario layout

每个 Reviewer 都把实际仓库文件保存在 `scenario/base/` 和 `scenario/candidate/` 下. 准备阶段复制基线并对其执行提交, 然后复制并暂存候选内容. Reviewer 的隐藏 `expected.json` 保留在复制后的场景外, 且只供准备和验证使用. 每个测试夹具文件都必须是位于允许的相对路径中的安全普通文件. 文本文件必须使用没有 BOM 的 UTF-8 和 LF 行尾, 并满足所选 Reviewer 要求的目录结构. 准备阶段和确定性测试负责这些检查, 因为普通 Text Policy 排除了 Test Data Directory. 动态请求身份, 临时路径, 摘要值和其他与运行绑定的值由维护 Module 生成, 而不是存储为测试夹具字节. 测试夹具编写是该工作流内的普通 Source Checkout 编辑, 不是另一个 ARW Engine 生命周期, 批准记录, 修订版本身份或持久状态合同.

Reviewer 可见的场景名, 路径, 文件名, 标识符, 注释, 标题和项目顺序使用固定且符合业务用途的中性名称. 它们不编码 `problem | clean`, 检查类别或预期顺序. 问题与干净内容不使用连续分区, 固定交替, 或规范与实现同序一一对应的排列. 固定场景和固定顺序保证重跑可复现; 隐藏 `expected` 中的分类不属于 Reviewer 可见内容.

Module 按注册场景顺序和场景内的 3 个实例顺序生成当前轮次绑定的 `instanceId`. `scenarioId` 本身也必须是中性名称, 不泄露预期结果. 调用方把返回的 `instanceId` 作为当前 `prepare` 的不透明绑定值, 不自行构造或依赖其字面格式. 该顺序只提供稳定绑定和同分裁决, 不表达能力优先级.

## Case identity

每个普通问题用例或干净用例都具有非空且用户可读的 `expectation`, 用于表述预期语义结论, 并供 Main Agent 核对问题候选的缺陷语义. 它对 Reviewer 隐藏, 不参与机械候选生成, 证据评分, 干净用例匹配或分数计算. 隐藏预期本身不证明缺陷真实成立, 仍须按完整 finding 核查规则与场景及适用要求核对.

不得存储用例 ID. 数组中的位置只在当前清单内标识用例. 临时裁决 `candidateId` 可以根据当前范围, 用例位置和问题引用推导, 仅用于关联两次验证调用. 它不是持久的测试夹具身份或兼容合同.

## Locator matching

Code Review 的定位信息匹配首先要求具有相同的归一化文件路径. 字段相同的定位信息只有在锚点或行精确时才匹配. 如果预期定位信息使用锚点, 实际定位信息改用正整数行, 则根据已暂存场景 Markdown 解析锚点, 并且只接受从该 ATX 标题开始, 到下一个相同或更高层级标题之前的行. 嵌套的较低层级标题仍属于其父章节. 实际 Markdown `lineStart-lineEnd` 范围只有在包含预期的精确行时才与它匹配, 且只有在整个范围都位于解析出的标题章节内时才与预期锚点匹配. 范围内每个实际行都计入证据精确率. 其他锚点, 行或范围替换都不匹配. 对关联证据, F3 证据评分和干净用例目标识别应用相同规则.

Code Review Markdown 定位支持同一完整路径后的逗号分隔行号与连续范围, 例如 `src/file.mjs:5,15-18,28-33`. 程序确定性解析整个定位, 每段必须是正的安全整数行号或起点不大于终点的范围; 任一段无效时整个定位不提供证据, 不截取其中有效部分. 同一对反引号内也可以用逗号分隔多个完整文件定位; 新文件必须写出完整路径, 仅含行号或范围的后续片段归属最近的文件路径. 整个反引号内容按同一有效性规则解析, 任一文件定位或行片段无效时整个内容不提供证据. 原有独立定位写法继续有效. 同一 finding 的同一文件中, 重复行或重叠范围的实际行在证据数量中只计一次, 简写与等价展开写法得分相同. 保留每个原始连续范围的章节边界检查, 不通过拆分跨章节范围获得锚点匹配. 不跨 finding 合并证据.

Commit Audit 的实际证据和隐藏预期都展开为仓库相对文件路径与正整数行的集合. 同一 finding 的同一文件中, 单行与闭区间先规范为合并后的准确行集合; 重复, 重叠和相邻区域不重复计数. 只比较同一文件的实际行, 不使用章节身份或整个文件替代. 对关联证据, F3 证据评分和干净用例目标识别应用相同规则.

Spec Readiness 的实际证据和隐藏预期按[正文证据合同](../specs/agent-repository-workflow/spec.md#generate-promote-and-verify)归一化为正文单行集合. 只比较同一文件的原始行号, 不使用章节锚点, 标题位置或原始范围的章节边界作为匹配条件. 同一 finding 中相同正文行集合的范围, 组合或展开写法得分相同; 无关正文仍计入实际证据数量. 标题和首尾空行不计入关联或证据分, 只有标题的文档不能提供有效证据. 每套预期的完整证据仅包含证明该问题所需的正文, 必要关联证据是其中最小的非空子集, 不把整节内容机械升级为全部必需的关联前提. 普通正式结果与完整审查 JSONL 都经过相同的正文处理, 不能通过正式结果路径绕过它.

## Problem association

问题用例声明一个或多个允许的检查位置, 每个位置都具有自己的精确预期证据和非空 `associationEvidence`. 关联定位信息是该位置预期证据的精确子集, 用于标识缺陷位置, 而不是每个支持来源. 验证器先核对实例身份和各角色的绑定条件, 再为每个 finding 与问题用例比较允许的检查及完整必要证据. finding 的检查属于允许位置, 且实际证据完整包含该位置的全部 `associationEvidence` 时, 形成一个语义确认候选. 同一配对满足多个位置时只形成一个候选. Commit Audit 继续保留对应的 Gate 和 requirement 绑定.

全部合格配对都交给 Main Agent 按[裁决规则](reviewer-capability-verification.md#adjudication)确认是否描述同一真实缺陷. 只有 `matched` 建立关联. 问题用例的 `findingTerms` 不决定候选资格或关联; 词语相似不能替代对象关系和缺陷含义. 同题其他 finding 的匹配或拒绝不屏蔽候选. 相同输入生成相同完整候选集合, 不因已经提供的决定变化. 一个 finding 可以与多个问题用例形成候选, 每个配对独立确认后按既有原子性公式处理合并或重复. 缺少完整必要证据或检查不符时不形成候选, 不能通过语义确认补足. 描述文本只用于确认已经满足证据条件的配对, 不提供独立分数.

同一缺陷可能由写入点, 分配点或后续查询点的证据准确证明. 为避免只接受一套证明而把真实 finding 当作误报, 同一个 `check` 可以在既有 `placements` 中声明多个等价位置. 每个位置独立声明完整的 `evidence` 和 `associationEvidence`; 不得重复声明完全相同的位置. 实际 finding 必须完整满足某一个位置的关联证据, 不能把不同位置各自缺失的证据拼接起来. 语义确认仍只判断同一缺陷, 不因位置增加而允许修改证据或直接调整分数.

同一问题的最小证明和附带直接佐证的完整证明组合, 都可以声明为既有 `placements`. 每个组合必须独立充分, 附加正文必须直接支持同一缺陷. 保留较短的有效证明, 由评分器选择一套完整位置, 不在运行时合并位置, 不新增佐证字段或豁免任意相关内容.

该位置规则同时适用于 Code Review 和结构化问题用例. Commit Audit 的各个替代位置必须保持用例所属的 Gate 范围, 且完整问题清单仍须与预期未满足要求形成一对一覆盖: 每条要求的结果及完整证据集合必须匹配对应问题用例的一个完整位置, 不允许靠跨位置合并证据补足覆盖.
