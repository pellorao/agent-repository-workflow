# 面向用户的说明

## Scope

与用户沟通的 Main Agent 在工作阶段结束, 或向用户发送任何沟通前读取本文. 已完整读取且内容未变时应用已有内容, 不重复加载. 本文唯一拥有面向用户的解释方法和共同场景说明, 其他入口引用并在各自步骤调用. 通用文本约束和各工作流必须提供的信息仍由原文档负责, 按下方的适用条件读取并遵循. 独立 Reviewer 和只向 Main Agent 交付的子 Agent 保留各自报告责任, 不承担本文的面向用户说明.

本规则适用于全部用户回复, 包括普通独立问答及澄清, 不以进入某个工作流为前提. 进度, 阶段完成, 最终交付, 方案讨论或 grilling, 审核反馈和处理决定, 具体差异审批, 失败, 阻塞, 等待及重述都是包括的场景, 不是适用范围的限定清单. 用户明确要求固定格式, 原文或简短输出时遵循原要求, 原有业务格式和授权边界保持有效.

## Other applicable rules

每次沟通仍遵循仓库根 Agent 指令的 `Output Text`, 包括标点, 中文与英文字母或数字之间的空格, 术语创建及等待用户操作的停点. 编写仓库文本时还读取[仓库写作规则](writing.md), 遵循语言, 编码和格式要求. 这些规则也适用于其他 Agent 或仓库内容, 不迁入本文.

发送说明前, 按当前场景读取以下来源中适用的规则. 已读取且内容未变时不重复加载, 不因一次普通进度汇报读取所有流程. 表内只指明来源及其责任, 具体要求在来源中维护; 本文的解释方法不能替代这些要求, 其他工作流仍按根 Agent 指令及所属 Skill 的读取触发执行.

| 沟通场景 | 仍需遵循的来源及责任 |
| --- | --- |
| 重要决定及 grilling | 根 Agent 指令的 `Important Decisions` 和当前平台的 `grilling` Skill, 负责何时请求决定, 本轮问题和选项, 编号, 已确认约束及等待用户回答的时点. |
| 实施进度及完成结果 | 当前平台的 `implement` Skill, [验证规则](validation.md)及 [issue 生命周期](issue-tracker.md#issue-lifecycle), 负责阶段完成条件, 当前有效证据和实际状态; 证据记录按 [issue 记录章节](issue-tracker.md#issue-record-sections)处理. |
| Reviewer 或识别问题的子 Agent 的反馈处理 | [问题核对和用户决定](subagent-findings.md#verify-findings), 负责独立核对, 请求决定的条件及必须提供的证据, 推理, 保留影响, 拟议变更, 重复关卡成本和额外等待资料. |
| Code Review 范围及结果展示 | 当前平台的 `code-review` Skill 及其后续审核资料, 负责准确比较身份和纳入路径, 分轴原始报告, 精确结果格式及完整或不完整状态. |
| Agent 规则或持久设计的具体差异批准 | [规则和设计更改](rule-and-design-changes.md#human-review), 负责准确路径批次, 变更摘要, 完整未暂存比较命令及实际字节批准, 暂存和提交的边界. |
| 检查失败或例外请求 | [验证规则](validation.md), 负责失败和语言检查结果的处理; 测试耗时例外按[测试性能流程](test-performance-optimization.md#threshold)提供准确案例及实测耗时. |
| Reviewer 等待或主动早退暂停 | [Reviewer 机器操作](reviewer.md#machine-operations), 负责提醒时点, 当前状态和不确定事实, 用户决定及保持运行或暂停的边界. |
| 子 Agent 容量阻塞 | [会话容量管理](subagent-allocation.md#session-capacity-management), 负责已尝试操作, 实际结果, 受影响工作及耗时影响, 以及请求决定后等待. |
| Git 提交相关结果 | [提交规则](commits.md), 负责提交授权, 固定候选和必要审核的实际状态, 不以说明或暂存代替提交事实. |

## Reader assumptions

假定读者不熟悉项目. 理解当前说明需要的名称即使已在术语表中登记, 也用日常语言解释其含义和必要边界; 复用本次对话已经解释的背景, 不每次从头介绍. 按费曼方法的实质, 先理解并回查自己讲不明的内容及证据缺口, 再连起目的, 具体问题, 前提, 原因, 行动和结果.

必要时用符合真实行为的例子或类比, 说明其不能覆盖的边界. 区分有证据的事实, 根据事实作出的推断和未确认事项, 讲清证据能够支持的结论及限制. 保留必要精确名称, 原始来源定位和数据, 不只堆术语, 路径, 测试数字或选项编号让用户自行拼出意义.

## Progress and results

Main Agent 每完成一个工作阶段都向用户汇报阶段结果, 不把每条工具动作另算一个阶段. 进度和阶段结果应让用户知道正在解决什么, 已经发生什么, 当前证据支持什么, 还剩什么及下一步. 简单事项可以很短, 不固定成四步模板, 不为每条工具输出进行长篇教学.

## Decisions and feedback

对每个重要决定, 陈述已确立的事实, 至少一个具体场景和有意义的可行选项及其直接后果. 说明真正要选什么, 已确认前提和仍待判断的事项, 各选项的收益, 成本和风险, 给出推荐理由. 编号和表达方式服从所属流程, 不用编号替代解释.

解释 Reviewer 反馈时在同一消息中包含问题本身, 区分实际程序错误, 检查不足和文档问题, 独立核对后说明修复与保留的影响及必要验证和审核成本. 不把 Reviewer 建议自动当成必须实施, 不把问题条目数当作新增测试案例数, 不把缺少检查说成程序已证实有错; 实际风险及审核结果仍按所属工作流处理.

Main Agent 在原始报告及准确证据定位之外另写面向用户的说明, 各审核轴的结果格式与呈现约束按上方引用的 code-review 流程执行. 通俗说明不替代独立结果或机器返回结构.

## Approval and blocked work

请求具体差异批准时解释解决的问题, 已准备的实际变化, 准确批准对象及权限边界, 保留所属流程的精确路径批次, 比较依据, 命令和审批时点. 一般性赞同不能代替实际差异批准, 暂存批准不能说成提交或发布授权.

失败, 阻塞或等待时说明未满足的条件, 已发生和尚未发生的影响及当前不确定性, 明确下一步或需要的用户操作, 保留原等待和授权停点.

## Restatement and visual aids

用户没理解时沿用当前沟通语言, 重组缺失背景, 前提和因果, 保留事实, 未确认内容和决定边界, 不仅换一组术语或强制使用简化技术英语.

图表只作可选辅助, 按信息类型参考[已有表示原则](writing.md#specification-design-presentation), 只在比文字更清楚时使用. 文字已足够时保持平实文字, 不要求每阶段画图, 不建立新的图表协议或渲染要求.
