# 仓库写作规则

遵循以下由仓库拥有的语言, 格式, 编码和文档约定. 保留逐字来源和字面语法. 保持术语与 `CONTEXT.md` 和适用 ADR 一致.

仓库自己编写的文档默认使用中文普通自然语言, Agent 规则文档也必须使用中文. 每份文档的普通自然语言必须完整使用中文或英文之一, 不得混用.

新建或大幅改写文档后, 运行 `arw language inspect <文件或目录>` 查看各文档的 Chinese, English 和 Other 字符比例. 该命令只报告比例, 不判定是否合格; 由 Agent 对照上述规则判断, 精确文字会降低主要语言的比例, 属正常现象, 比例明显偏离该文档应使用的语言时修正. 外部原样拷贝文档的来源合同继续决定内容是否允许改写; 允许改写时, 修改后的普通自然语言仍须统一使用同一种语言.

长期文档必须独立表达当前有效的规则, 设计和必要理由. 不得把 `.scratch` 下的短期工作记录作为引用目标, 依据或理解其含义所必需的上下文 (长期文档可以描述 `.scratch` 的通用结构, 路径语法和操作合同, 也可以使用不对应真实工作记录的示例路径). 如果短期工作记录中的决定需要长期保留, 把该决定及其必要理由写入拥有相应责任的长期文档, 不保留指向短期记录的引用.

已跟踪的仓库文本, 包括 `.scratch` 下的 ARW Artifact 和工作记录, 不记录只在某台机器上成立的内容, 如含用户名或主机名的绝对路径和本机服务地址; 改用仓库相对路径, 平台通用写法 (如 `~/.codex`, `CODEX_HOME`) 或占位符. 逐字引用的命令输出或日志含有这类内容时, 先替换为占位符.

在中文或英文文档中, 保留必须精确且不属于普通自然语言的文字. 这包括已在治理文档中建立的身份名称, 命令, 字段, 状态值, 路径, 代码标识符, 外部平台名称, 代码, 测试夹具, 逐字来源, 以及已建立的模块或 Interface 名称.

在中文文档中, 只有属于这类精确文字的英文内容才保留原文. 一个词来自常见技术领域或工作流, 不足以使它成为精确文字. 如果中文能够在不损失合同含义的情况下表达普通叙述, 则使用中文.

这些精确文字不决定文档语言, 也不构成中英文混写. 文档语言选择与标题合同相互独立. 模板或公共标题合同要求的精确英文标题不会使中文文档变成混合语言文档.

对于由 ARW 安装的规则, 以目标仓库内安装的版本为准. 安装后的 Agent 指引必须能够独立使用, 不得依赖仓库外的全局文档, 也不得为每份文档重复记录来源信息. Repository-owned 区域只记录本仓库新增的规则或对 Baseline 的明确例外, 不得重复 Baseline 内容.

除非有明确的仓库例外, 所有由 Agent 管理的文本必须是没有 BOM 的有效 UTF-8, 并使用 LF 换行符.

编写或修改会创建临时文件或目录的仓库代码前, 读取 `./environment.md`.

在 Agent 责任内的文件中创建或重命名文件或目录时, 不得在任何新路径组件中使用 `#` 或 `:`. 选择新路径时应用这项规则.

由 Agent 管理的文档和规划产物使用英文文件名. 该规则不适用于引入的第三方资源. `.scratch` 下的 ARW Artifact 还必须遵循跟踪器路径语法, 当后者更具体时以它为准.

不得手动强制换行 Markdown 散文. 在源码中让每个段落保持自然的一行, 由渲染器负责换行.

## Minimal sufficient contracts

遵循根 Agent 指令的效率与精简最高原则 (`Efficiency First`). 此外:

- 多个方法都满足验收标准时, 选择规则, 状态, 数据源和机制更少的方法.
- 模块, 工作流, 验证和实施过程只承担已确认的责任. 不得仅因内部步骤还能继续拆分, 就为这些步骤新增独立协议, 关卡, 记录或证据链.
- 删除没有当前使用者或兼容责任的机制.
- 每个事实只保留一个权威来源. 在拥有某项责任的文档中陈述规则, 其他文档引用该规则, 不得复制它.
- 规则文档, 长期规范和 ADR 等面向 Agent 的文档的引用使用反引号路径, 不用 Markdown 链接 (指向目录或无扩展名文件时保留 Markdown 链接; 同文件章节写成普通文字 "X 节"); 专为人类读者编写的文档 (如 README, 用户手册) 保留 Markdown 链接. 引用章节时写 "`路径` 的 <标题> 节", 不使用锚点. 以 `./` 或 `../` 开头时相对所在文件解析, 否则相对仓库根 (`docs/agents/`, `.agents/skills/`); 两种形式都可用时选字节数更少的一种, 相同时选仓库根形式.

## Common capabilities

- 编写代码前, 检查现有公共模块和公共方法, 能复用的尽量复用.
- 不依赖当前业务语义的通用功能必须放入公共模块, 不以已有多个调用方为前提.
- 不得创建只转发调用且没有隐藏任何复杂性的公共包装器.
- 公共能力仍须遵循最小充分合同. 不得仅因能力通用, 就在没有已确认需求时为方法和模块增加选项或扩展点.

## Baseline exceptions

Repository-owned 规则可以增加, 收紧或专门化 Baseline. 任何放宽 Baseline 要求的规则, 都必须在拥有该规则的文档的 Repository-owned 区域中明确声明为 Baseline 例外.

## Batch operations

多个数据项需要执行相同的文件系统, 进程, 数据库或远程服务操作时, 优先判断能否批量处理. 如果批处理能够减少重复访问, 且保留授权, 顺序, 可观察结果, 失败处理, 事务和资源边界, 就合并为一次操作, 或按资源上限分批处理. 只读操作也可以一次取得完整数据后在内存中处理.

只有当多个写入共享同一次授权和同一个事务时, 才批量写入. 批量写入必须保留原有的失败报告, 重试和恢复结果. 如果操作需要独立授权, 逐项隔离失败, 保持语义顺序, 或缺少安全的批处理 Interface, 则分别执行.

## Code comments

只为复杂或不明显的行为添加注释. 只有当行为, 设置, 返回结果或重要边界情况无法从代码和 Interface 中清楚看出时, 才为公开方法使用详细的 `/** ... */` 注释块.

## Markdown structure

模板规定的标题结构和固定文字必须保持不变, 其中的占位符则替换为当前文档的实际值. 当没有固定模板时, H1 跟随文档语言, H2 和更深的标题全部使用英文.

`CONTEXT.md` 在 H1 中替换其上下文名称, 并精确保留 `## Language`.

## Specification and terminology

- 编写或修改 effort spec 或长期规范前, 读取 `./specification-presentation.md`.
- 使用含义不明显的保留术语, 或根 `Output Text` 允许的新名称前, 读取 `./repository-terminology.md`.

# Source Checkout 读者文档

编写根 `README.md`, 根 `README.zh-CN.md` 或 `docs/manuals/` 下的任何文档前, 读取 `../specs/arw-reader-documentation/spec.md`. 作为 Baseline 例外, 本节用户文档的全部普通标题跟随文档语言; 模板固定标题和已建立的精确名称保持原文.

# Source Checkout 分发副本

`distribution/` 下的文件会安装到目标仓库, 必须自包含: 不含 `distribution/`, `node scripts/`, `README.zh-CN.md`, `readIssueSubject` 以及 Source Checkout 和 Workflow Distribution 这两个名称; Markdown 链接, `docs/agents/`, `.agents/skills/` 路径和 `./`, `../` 文件相对路径须在分发载荷内解析, 目标仓库自有约定 (清单见开发规范的 `Workflow Distribution` 一节) 除外. `node scripts/check-workflow-distribution.mjs` 的生产检查强制这条规则. 作为 Baseline 例外, 分发副本的语言只由发布流程中 `release` Skill 调用 `arw language inspect` 检查, 改写这些副本时不运行该命令.

# Source Checkout JavaScript 样式

使用描述性名称和输入输出清晰的小函数. 除非外部 Interface 要求, 否则避免使用 `class`.
