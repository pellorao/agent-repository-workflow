# Subagent 分配

## Scope

本文件负责任务委派, 实例创建和复用, 会话内的容量调度, 以及非预定义 subagent 的模型和推理强度. 与用户沟通的 Main Agent 和其他非 Reviewer 运行环境的 Main Agent 管理各自的子 Agent. 独立 Reviewer 按 [Reviewer 单 Agent 执行规则](reviewer.md#single-agent-execution) 自行完成全部审核, 不创建或恢复子 Agent; 本文件以下的委派, 容量和模型映射规则不用于 Reviewer. 其他预定义角色使用其已有完整配置.

## Delegation and reuse

各运行环境的 Main Agent 在不影响工作质量的前提下尽量把工作委派给合适的 subagent, 自己集中负责协调, 决策和必须亲自执行的操作. 适合独立交付的研究, 原型, 实现和文档编写默认交给 subagent 直接完成. 与用户沟通的 Main Agent 需要停下来向用户提问时, 已委派的独立工作仍可推进, 减少等待对整体进度的影响. 出现以下情况时可以自行执行:

- 需要频繁与用户互动.
- 无法合理拆分.
- 工作很小, 交接成本明显更高.

与用户沟通的 Main Agent 可以转发少量用户沟通, 不阻止普通任务委派. Reviewer 输入缺失或工作阻塞时, 按 [Reviewer 的通信与输入不足处理规则](reviewer.md#communication-and-observation) 交付不完整状态, 不向用户或与用户沟通的 Main Agent 提问.

各运行环境的 Main Agent 可以把会污染自身上下文, 无谓地大量占用上下文, 或不值得使用自身智力和努力程度处理的工作委派出去. 委派后, 该 Main Agent 负责协调, 由受派 Agent 完成执行过程; 同领域复用则保留已经获得的理解.

各运行环境的 Main Agent 统一创建和分配自身运行环境中的所有实例, 优先复用已经掌握同领域上下文的合适实例. 以下情况可以构成另建实例的理由:

- 工作要求独立审查.
- 现有实例的上下文已经混杂或过长.
- 工作确实需要并行执行.

独立 Reviewer 的身份, 初始上下文隔离和原线程复用遵循 [Reviewer 会话操作规则](reviewer.md#machine-operations), 结论有效性遵循 [Reviewer 报告交接规则](reviewer.md#review-handoff).

subagent 可以向所属运行环境的 Main Agent 申请协作者, 不自行创建下级实例. 该 Main Agent 提供获分配实例的标识和任务关系, 使双方可以直接沟通.

直接沟通不授予改变任务范围, 分配写入责任或决定重要问题的权限. 文件交付使用 [共同写入规则](agent-writes.md), 不要求 subagent 只返回建议再由 Main Agent 重写.

## Subagent management triggers

各运行环境的 Main Agent 在以下实际工作节点执行对应的管理检查, 具体处理遵循下方的会话容量管理规则. 这些是 Agent 工作流责任, 不表示平台已经安装自动钩子.

- 收到用户新消息时: 如果消息改变了现有 subagent 的工作依据, 执行授权, 阻塞条件或任务顺序, 及时协调受影响的 subagent, 按需查阅和更新对应名单条目. 其他消息不触发名单读取或完整调度检查; 协调只针对受影响的线程, 不要求全局检查.
- 上下文压缩后恢复执行前: 重新读取名单, 核对平台可用状态和未完成的调度安排.
- 调用创建或唤醒 subagent 的工具前: 检查可复用的原线程, 当前容量和必要的资源处理, 按双方当前优先级判断是否需要插队. 操作返回后把实际结果更新到名单.
- 收到 subagent 完成结果, 或暂停操作返回后: 更新状态, 检查待执行和已暂停任务, 利用可用容量安排执行或恢复.
- 创建或唤醒工具返回容量错误后: 主动处理闲置线程和遗留消息, 复查状态, 并验证实际需要的创建或唤醒结果.
- 准备等待 subagent, 或结束本轮回复前: 检查是否遗漏待执行或暂停任务的调度, 结合剩余工作重新判断优先级, 提前安排即将阻塞后续工作的任务.

## Session capacity management

各运行环境的 Main Agent 维护整个当前会话中的 subagent 名单, 使跨阶段参与工作的原线程能够及时恢复, 避免因遗漏身份, 重复创建或未处理容量限制而延误工作. 按 [临时工作区规则](environment.md#temporary-workspaces), 在当前会话工作区内保存一份简短文本列表. 列表中每个 subagent 一行, 记录原任务名, 可取得的线程 ID, 职责与写入范围, 当前优先级, 最近观察状态和恢复安排. 名单尚未建立时先创建, 已有名单保留原线程身份和恢复安排. 列表保留暂时不工作的线程, 不复制会话历史, 不记录抢占日志. 平台负责保存原会话和上下文.

各运行环境的 Main Agent 结合该列表, 平台可用的状态查询和实际调用结果检查当前容量, 优先复用适合当前任务的原线程. 当前工具列表未包含某个线程, 不代表它不存在或无法恢复; 已完成或已中断也不自动证明名额已释放. 普通任务的容量上限使用当前平台事实, 不固定为某个数量, 不把保留的线程总数当作正在工作的数量.

容量不足时, 所属运行环境的 Main Agent 必须主动检查并处理已完成或暂时闲置的线程, 不能停在报告其存在. 查明当前可用的关闭或卸载操作, 以及是否存在未消费消息或未结束的任务. 对不自动启动回合的消息, 及时安排处理; 旧请求已不再需要时明确取消其工作要求, 使线程完成必要的消息处理并结束回合. 仅使用能够保留原线程身份和持久会话的平台操作卸载实例, 并在需要时按原身份恢复上下文. 平台没有主动卸载接口时, 使用已验证的自动管理和恢复路径安排批次. 新建同名线程不能替代恢复原线程, 不通过删除会话腾出名额.

处理后重新查询可用的线程状态, 并执行当前实际需要的创建或唤醒, 确认操作是否成功. 在名单中更新实际观察状态和恢复安排, 分别判断线程是否移出列表与容量是否可用; 不把中断, 已完成或列表消失单独视为释放保证, 也不要求闲置线程必须在下一次创建前立即消失. 判断某次处理是否释放容量时, 区分同时发生的其他任务完成或状态变化; 无法归因时只报告已观察到的结果. 无需为每次正常调度另建探测线程.

各运行环境的 Main Agent 根据任务在当前阶段的目标, 依赖和剩余可推进工作自主确定优先级并决定是否插队, 不为日常调度请求用户决定. 优先级不固定绑定 subagent; 管理检查根据当前情况更新名单中的优先级, 不记录调整历史. 例如, grilling 前期仍有其他独立问题可讨论时, 附带调查可以较低优先级运行; 当剩余问题即将依赖调查结果时, 应及时提高其优先级并安排执行, 避免等到讨论停滞才处理. 只有更高优先级任务可以暂停较低优先级的普通任务, 同级和低优先级任务均不得抢占. 暂停时确认该任务已停止写入, 在其原文本行标记已暂停并保留暂停先后顺序和恢复安排. 独立 Reviewer 的中断, 等待, 身份和上下文隔离遵循 [Reviewer 机器操作](reviewer.md#machine-operations).

调度待执行任务和已暂停任务时, 优先执行高优先级任务; 同级优先恢复已暂停任务, 多个已暂停任务按暂停先后恢复. 恢复前确认原身份和上下文可继续使用, 并按 [写入分派规则](agent-writes.md#assign-and-hand-off) 重新确认写入范围, 再更新其状态并继续任务.

容量处理不直接放弃所需任务或反复执行条件未变化的创建请求. 所有可用名额都承担必要且不能被抢占的工作时, 等待适用任务完成, 同时推进不依赖这些结果的工作. 处理闲置线程后仍无法创建或恢复所需线程时, 与用户沟通的 Main Agent 向用户说明已尝试的操作, 实际结果, 受影响工作及等待或串行执行的耗时影响, 询问处理方式并立即结束回复等待决定. 独立 Reviewer 按 [Reviewer 的通信与输入不足处理规则](reviewer.md#communication-and-observation) 返回说明阻塞原因的不完整状态, 不向与用户沟通的 Main Agent 或用户提问. 保留待执行与暂停状态, 不自行改为串行或要求重启, 不声称容量已经释放或上下文已经恢复.

## Codex idle-thread recovery

以下示例适用于实际提供这些 `collaboration` 工具的 Codex 运行环境. 这些示例只用于允许创建子 Agent 的运行环境, 不用于独立 Reviewer. 将 `<原任务名>` 替换为待处理闲置线程的完整任务名, 如 `/root/helper`.

1. 查询线程状态:

   ```javascript
   collaboration.list_agents({"path_prefix":"<原任务名>"})
   ```

2. 唤醒线程, 取消遗留请求并结束回合:

   ```javascript
   collaboration.followup_task({"target":"<原任务名>","message":"此前任务已完成, 取消所有遗留请求和等待. 本次只处理消息, 请回复已处理并结束本回合."})
   ```

3. 等待该线程完成后, 重新查询状态, 再用原定参数重试需要的创建或唤醒操作:

   ```javascript
   collaboration.wait_agent({"timeout_ms":60000})
   collaboration.list_agents({})
   ```

## Task assessment

分别评估任务的智力需求和努力程度. 智力需求衡量需要的判断能力, 努力程度衡量需要的推理投入.

| 档位 | 智力需求 | 努力程度 |
| --- | --- | --- |
| 低 | 按明确步骤查找, 提取或核对事实 | 少量直接推导即可完成 |
| 中 | 结合上下文判断, 分析局部问题 | 需要多步推导, 比较或交叉核对 |
| 高 | 处理歧义, 跨领域约束或开放式设计 | 需要深入探索多条路径, 检验假设和反例 |

文件数量和机械重复量不直接提高档位. 从大量文件提取明确字段可以只需低档判断和推理, 而简短的开放式架构问题可能需要高档判断和深入推理.

## Allocation

每次创建非预定义 subagent 前读取本文件, 按以下顺序选择参数:

1. 读取 repository owned 区域的当前仓库配置. 尚未配置时, 先完成下述首次配置流程.
2. 根据任务的智力档位选择模型, 再根据努力档位选择该模型对应的推理强度. 所属运行环境的 Main Agent 的配置不作为参考.
3. 使用选定参数创建 subagent.

## Initial repository configuration

缺少仓库配置时, 所属运行环境的 Main Agent 调查当前可用的主流模型及其支持的推理强度, 拟定智力到模型, 努力到所选模型推理强度的映射. 提交方案前可以询问用户偏好. 该调查由创建非预定义 subagent 前的配置检查触发, 由所属运行环境的 Main Agent 完成.

向用户提交具体模型及其低, 中, 高努力档位的推理强度. 用户批准后, 将这些配置写入本文件的 repository owned 区域, 然后继续创建原定的 subagent. 审批前不使用候选映射. 当前创建 Interface 不能逐次设置 Fast, 因此本规则不把 Fast 状态作为可配置映射或创建承诺.

## Repository model mapping

本仓库使用以下 Codex 模型映射. 先按智力需求选择模型, 再按努力需求选择该行的推理强度.

| 智力需求 | 模型 | 低努力 | 中努力 | 高努力 |
| --- | --- | --- | --- | --- |
| 低 | `gpt-6-luna` | `low` | `medium` | `xhigh` |
| 中 | `gpt-6.1-sol` | `low` | `medium` | `high` |
| 高 | `gpt-6.1-sol` | `medium` | `high` | `xhigh` |

当前创建非预定义 subagent 的 Interface 不能逐次设置 Fast 参数. 表中的模型和推理强度是当前可传递的配置; Standard 主会话下的实际 Fast 状态由平台决定, 不属于本映射的承诺.
