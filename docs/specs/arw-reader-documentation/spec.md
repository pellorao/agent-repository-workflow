# ARW 读者文档

## Purpose

本规范定义 ARW Source Checkout 中面向读者的项目入口和手册怎样分工, 组织内容并相互路由. 它让读者从自己的情境和目标出发, 先判断适用路线, 再取得完成目标所需的说明, 同时让每份文档直接拥有自己的具体内容.

本规范只保存长期责任, 内容关系, 相互路由和权威来源边界. 它不规定被治理文档必须使用的标题, 篇幅, 固定句子, 关键词或内容清单.

## Scope and Authorities

本规范治理根 `README.md`, 根 `README.zh-CN.md` 和所有当前及未来的 `docs/manuals/**/*.md`. 这些用户文档同步维护中文和英文两个版本, 以英文为默认版本. 它只适用于 ARW Source Checkout, 不进入 `distribution/` 或采用 ARW 工作流的目标 Git 仓库.

读者文档帮助读者理解项目, 作出选择并完成目标. 长期规范和 ADR 拥有长期产品行为与设计边界, Agent 规则约束 Agent 的工作方式. ARW Artifact 是 `.scratch` 下登记的 `issue`, `map` 和 `spec`, 用于保存当前工作的要求, 状态和证据. 本规范通过说明这些责任限制读者文档的边界, 但不治理 ADR, ARW Artifact, Code Map, `docs/agents/**`, Reviewer Role, Skill, 其他规范或 Workflow Distribution 文档.

每份被治理文档拥有自己的具体内容. 本规范, 通用写作规则和测试不得复制这些内容形成第二份不完整来源. 教程, 参考, 路线选择器和速查卡可以作为表达形态, 但表达形态由目标读者要完成的目标决定, 不构成固定文档类型或合格条件.

## Document Responsibilities

读者先从项目入口判断 ARW 是否适用并开始主要路线, 再在目标转向专门使用或源码维护时进入相应手册. 当前各被治理文档的最低责任如下:

| 文档 | 目标读者 | 阅读起点 | 核心目标 | 责任边界 |
| --- | --- | --- | --- | --- |
| 根 `README.md` | 具备终端, Git 和 Node.js 基础, 但不了解 ARW 的读者 | 读者正在判断 ARW 是否适合自己的 Git 仓库, 或准备第一次安装和启用 ARW | 帮助读者判断适用性, 沿连贯路线完成首次安装和启用, 理解日常主路线, 并进入适用的专门路线 | 它拥有项目判断和首次成功路线, 可以包含首次使用所需的常见细节, 但把专门, 高级和 Source Checkout 维护路线交给手册 |
| `docs/manuals/application-jira.md` | 会使用终端和 Git, 但不了解 ARW 多仓库方式的新手 | 读者正在判断一项工作是否需要由多个 Git 仓库共同完成并与 JIRA 同步, 或已经选择这条路线但不了解其责任关系 | 帮助读者判断这条路线是否适用, 理解仓库与记录的责任关系, 按正确顺序操作, 并在失败后从准确边界恢复 | 它只承担多仓库工作与 JIRA 同步路线, 不把一般 ARW 使用重新写成另一条入口路线 |
| `docs/manuals/agent-cli.md` | 已经决定使用 ARW 保存并启动 Agent CLI 配置的用户 | 读者准备保存一个 Agent CLI 配置, 或使用已有配置启动该 CLI | 说明配置, 启动, 参数透传以及进程和会话边界 | 它不重新讲解一般 ARW 工作流, 也不拥有外部 Agent CLI 的选项语义 |
| `docs/manuals/daily-agent-conversation-commands.md` | 已经在与 Agent 协作, 并希望快速选择可发送内容的用户 | 读者已经处于 Agent 对话中, 需要为当前情境选择下一段可发送内容 | 提供可以采用的内容及必要的判断提示 | 它不承担完整工作流说明 |
| `docs/manuals/skills.md` | 已经安装 ARW, 想知道有哪些 Skill 以及何时点名的用户 | 读者想了解 ARW 附带的 Skill, 或不确定某个 Skill 是否会自动使用 | 按来源和用途列出 `distribution/skills/` 中的全部 Skill, 标明自动使用或需显式点名; 上游 Skill 简述并链接上游说明, ARW 自定义 Skill 说明触发时机, 主要步骤, 产出和相关命令 | 它不复制 Skill 的完整合同, 实际步骤以 `SKILL.md` 为准 |
| `docs/manuals/development.md` | 已经克隆 Source Checkout 的维护者 | 读者准备修改或维护 ARW Source Checkout | 帮助读者选择维护路线, 找到验证入口并理解源码责任导航 | 它不复制产品合同或 Agent 操作规则 |

表中路径是默认英文版本, 这些责任项按逻辑文档成对适用于其中英文版本. 它们是审核文档是否服务目标读者的最低判断, 不要求被治理文档使用相同标题, 表格或排列顺序. 未来手册也必须说明目标读者, 阅读起点, 核心目标和责任边界. 新手册只有在拥有可以独立说明的读者目标时才成立. 仅为了缩短文件而拆分手册, 或让多份手册共同拥有同一组具体步骤, 都会削弱单一来源.

## Bilingual Maintenance

默认英文项目入口使用 `README.md`, 中文入口使用 `README.zh-CN.md`. 手册不带语言后缀的 `.md` 文件使用英文, 对应中文版在同一目录使用 `.zh-CN.md` 后缀. 每本现有或新增手册都必须具有两个完整版本, 不以摘要, 自动翻译入口或跳回另一语言代替完整正文. 两个版本表达同一份用户文档的责任, 不形成两套独立产品合同.

每份 README 和每本手册的两个版本都在顶部提供语言切换链接, 放在主标题之后, 其他正文之前. 链接提供 `English` 和 `简体中文` 两个入口, 直接指向同一文档的对应版本. 这类语言名称是导航标签, 不属于正文混写. README 到手册, 手册到手册和返回项目入口的路由优先连接相同语言的版本, 两种语言都保留本规范要求的完整可达路线. 引用未翻译的规范或 Agent 规则时可以保留目标, 并在阅读需要时说明其语言, 不因此扩大用户文档的翻译范围.

新增, 修改, 移动或删除一份用户文档时, 在同一变更中处理对应版本及两侧链接. 两个版本的目标读者, 适用条件, 命令与参数, 操作顺序, 可观察结果, 限制和失败恢复含义必须一致. 表达可以符合各自语言习惯, 不要求逐句对应或相同章节标题. 事实变化时同步修订两个版本, 不把其中一种语言长期留在旧行为上.

双语维护适用于根 README 和用户手册, 不要求为 `docs/agents/`, `docs/specs/`, `docs/adr/`, Skill 或工作记录增加英文副本. 每份文档的普通自然语言仍完整使用一种语言, 语言比例可用 `arw language inspect` 查看. 人工审核完整性和语义一致性, 机械检查编码及链接, 不建立翻译生成系统或用固定句子测试代替语义审核.

## Content Organization

读者文档不创建持久项目术语. 新术语由 `CONTEXT.md`, 适用规范或 ADR 建立. 读者文档使用既有术语时, 在目标读者第一次需要其含义的具体情境中用普通语言解释, 再继续使用准确名称. 文档不得依赖集中术语章节要求读者预先学习概念.

面向不了解相应 ARW 路线的新手文档, 全文从读者的初始情境和目标开始, 并沿明显的因果关系推进. 每项主要内容由前面的原因, 选择, 操作结果或新问题引出. 命令, 表格, 清单和参考信息只在解决相应问题时引入, 并说明它们解决什么问题. 审核这一要求时判断信息之间的关系, 不检查连接词. 面向已经具备相应背景的专业读者文档可以按查询效率或技术关系组织.

读者文档保存完成目标所需的准确命令, 顺序, 示例和可观察结果. 稳定产品行为, 安全边界和长期设计的完整合同仍由适用规范, ADR 或实现拥有. 读者文档在理解或继续操作需要时链接相应来源, 但不要求每项事实逐句链接.

读者可以选择是否执行一条流程或路线时, 文档说明它解决的问题, 执行成本和质量收益, 使读者可以判断是否采用. 必须执行的流程直接说明要求, 目的和操作, 不把强制步骤描述成成本收益选择.

## Routing

根 `README.md` 拥有项目适用性判断和一条连贯的首次成功路线, 不受长度或固定章节限制. 当读者的目标转向专门, 高级或 Source Checkout 维护工作时, README 把责任交给相应手册, 而不是复制全部详细操作.

每份手册都必须从 README 经一条或多条有意义的路线可达. 链接上下文说明读者应在什么情境使用目标文档, 使读者能够在责任交接时判断下一步. README 只直接链接主要路线. 更专门的手册可以通过主要路线中的适用手册继续到达, 但无解释的链接目录或偶然提及不构成有意义的路线.

手册需要共同前提时可以链接回 README, 需要更具体的操作时可以链接到相应手册. 这些链接划分内容责任, 不要求多份文档重复相同说明.

## Sources and Review

当前 Git 仓库中可验证的实现, 命令, 目录布局, 清单和适用治理文档是事实来源. 历史原型可以帮助理解结构或覆盖范围, 但不能覆盖当前事实, 也不成为长期内容权威.

人工审核文档是否帮助目标读者完成目标. Agent 审核目标读者和阅读起点是否明确, 内容组织是否服务核心目标, 最低责任是否完整, 文档边界和路由是否一致, 以及事实是否准确. 审核每份文档的两个语言版本全文并核对语义一致性后, 还要分别检查所有手册从同语言 README 的可达性, 以及文档之间是否存在核心责任重叠或缺失.

机械检查负责 UTF-8, BOM, LF, 确定性术语, 链接, 受管理区域和 Source Checkout 与 Workflow Distribution 分离等可以准确计算的合同, 以及 Skills 手册的两个版本都逐一提到 `distribution/skills/` 中的每个 Skill 名. 它们不得通过固定标题, 句子, 关键词或命令清单判断文档语义质量.

对于人类作者编写或用户明确批准的产品评价, Agent 只审核文档结构, 必需信息是否存在和表达是否清楚, 不重新评价该产品判断是否过强, 是否应当弱化或是否值得保留. 当评价与当前可验证事实或适用治理文档冲突时, Agent 仍报告准确冲突.

## Change Boundaries

修改读者文档时只改当前目标所需的文档和直接拥有其长期责任的来源. 不为了让一个测试通过而在无关文档中增加固定文字, 也不让 README 或手册成为清单, Reviewer 身份, 发布证据或运行时行为的机器权威.

如果读者文档暴露实现或长期治理缺口, 维护者在真正拥有该行为的 issue 和治理来源中解决. 文档可以准确说明当前限制, 但不能用措辞代替未实现的行为.
