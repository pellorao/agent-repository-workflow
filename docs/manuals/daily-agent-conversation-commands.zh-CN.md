# 与 Agent 对话时可直接采用的内容

[English](daily-agent-conversation-commands.md) | [简体中文](daily-agent-conversation-commands.zh-CN.md)

这份速查手册面向已经在与 Agent 协作, 并希望为当前情境快速选择下一段内容的用户. 复制示例前, 把 `XXX`, `NNNN:NN` 和路径替换为实际值. 这些内容用来清楚表达目标和检查点, 不代替项目中的完整 Agent 规则或 Skill.

## 讨论并确认需求

当目标还不够清楚, 或一个选择会影响产品行为, 数据, 安全, 公开 Interface 或长期维护责任时, 可以直接发送:

> 我要做 XXX. 请使用 $grill-with-docs 和我讨论以达成共识. 每轮说明当前事实, 可行选择, 推荐方案和影响, 然后等待我回答.

`$grill-with-docs` 用逐轮提问检验计划, 并在你明确确认后记录需要长期保留的术语或决定. 如果描述太专业, 可以补充:

> 这些术语我还不理解. 请先用普通语言解释它们在这个具体场景中的含义, 再继续提问.

当 Agent 给出的方案可能超出当前目标, 或把初期实现设计得过深时, 可以先限制方案范围和实施深度, 把将来的扩展留到确有需要时再决定:

> 请把方案限制在当前目标内, 不要自行扩大范围. 选择满足当前需求的最浅实施深度, 说明暂不处理的扩展方向以及以后什么情况才需要处理.

当一项推荐看起来合理, 但你还不能确定它是否经得起反例时, 可以要求 Agent 从反面检查自己的判断:

> 请从反面检查你刚才的推荐. 找出最可能使它失败的前提, 反例和副作用, 再说明原推荐是否仍然成立, 或者应该怎样调整.

如果结论依赖尚未核实的项目事实, 可以发送:

> 先只读调查 XXX 的当前事实和权威来源. 把证据, 不确定性及其对当前选择的影响带回这轮讨论, 不要提前实施.

准备结束讨论前, 可以根据当前对话中已经可见的内容检查遗漏:

> 请列出当前已经确认的决定, 重要理由和仍未解决的问题. 只报告当前可见记录能够支持的内容, 不确定的项目明确标记为未知.

当讨论已经形成需要长期保留的决定时, 还可以检查这些决定是否写入了真正拥有相应责任的持久文档. 这项检查先给你审核补写方案, 不会立即改文档:

> 请检查当前会话内已经确认的决定和重要理由, 以及它们是否都记录在相应的持久文档中. 先输出检查清单和补写方案, 等我审核批准后再补写. 补写完成后重新检查并输出最终清单.

当某段流程说明难以理解时, 仅把事实拆成列表仍可能留下突然跳变. 可以要求 Agent 从触发原因开始, 沿因果关系说明正常推进和失败恢复:

> 你的流程说明我看不懂. 请从触发这个流程的原因开始, 按步骤说明每一步为什么发生, 需要什么输入, 执行什么操作, 产生什么结果, 结果怎样引出下一步. 如果某一步失败, 还要说明已经产生的影响, 没有产生的影响, 以及从哪里修正或重试.

## 整理设计和原型

已经达成整体共识, 需要把讨论整理成可实施规范时, 可以发送:

> 我们已经就 XXX 达成整体共识. 请使用 $to-spec 把当前对话整理为 effort spec. 在发布前先核对测试边界是否符合预期.

`$to-spec` 综合已经讨论的内容, 不重新进行需求访谈. 如果仍有会改变重要结果的选择, 先回到讨论, 不要让规范替你默默作出决定.

需要把已经确认的规范拆成实施 issues 时, 另用 `$to-tickets`. 先让 Agent 展示纵向切片, 阻断关系和各 issue 的治理依据, 审核并批准拆分后再发布到跟踪器.

当文字推理不足以判断状态模型或 UI 呈现时, 可以要求一个明确可丢弃的原型:

> 请使用 $prototype 构建一个可丢弃原型, 只回答这个问题: XXX. 先说明原型能验证什么和不能验证什么, 完成后报告观察结果, 未解决决定和建议, 不把原型直接当作正式实现.

原型用于降低设计不确定性. 当前平台是否另外提供图像生成, 浏览器或其他展示能力不属于 ARW 保证. 需要这些能力时, 先确认当前会话实际可用, 再把它作为辅助输入, 不把生成结果当作已经确认的产品行为.

需要探索 UI 设计, 并希望先从视觉方向收敛到可操作页面时, 可以把图像构想, 页面原型和人工评价串成一条路线:

> 请先用 imagegen 构想 XXX 模块的 UI 设计, 再用 $prototype 制作可操作的页面原型. 每轮向我展示结果并等待人工评价, 根据评价继续修改, 直到我明确确认设计决定. 最终原型仍是可丢弃的参考原型, 请另行记录经过确认和验证的设计决定, 不要把原型当作正式实现或实施授权.

当设计已经能实现目标, 但结构或流程显得过于复杂时, 可以要求 Agent 比较更简单的办法, 并把简化带来的副作用一起交给你判断:

> 请检查是否存在仍能满足当前目标的更简单方案. 比较它与当前方案的责任, 机制和维护成本, 并列出简化会带来的具体副作用. 不影响已确认结果且没有具体风险的副作用可以明确标为可接受候选, 等我决定采用哪种方案.

当方案开始为每个内部步骤增加流程, 关卡或证据时, 可以要求它只保留现有合同或具体风险真正需要的独立边界:

> 请检查当前方案是否为内部步骤建立了不必要的独立流程, 验证或证据链. 只保留现有合同要求, 或具体可预见风险确实需要的边界, 并说明每个保留项保护的结果. 不要仅因为一个步骤还能拆分就继续增加机制.

当一个设计经过多层实现才产生最终结果时, 可以优先验证用户真正观察到的结果, 避免重复检查整条内部链路:

> 请优先通过最终可观察结果验证完整设计, 不要默认把每个中间表示, 内部调用或实施阶段都设为独立检查点. 只有中间值本身属于公开合同, 持久证据, 授权边界或安全边界, 或最终结果不足以证明受治理属性时, 才增加相应的中间检查, 并说明理由.

## 实施已有 issue

已经存在获授权的实施 issue 时, 可以直接发送:

> 请使用 $implement 实现 issue:NNNN:NN.

实施相关的几个门禁分别解决不同问题. Spec Readiness 在实施前检查治理准备是否充分. Code Review 在提交前分别检查仓库标准和治理要求. Commit Audit 对已经冻结的提交候选进行最终要求核对. Agent 不得自行省略或改写它们或其他适用门禁. 只有用户明确决定并主动发送适用的授权内容时, 才能形成相应例外.

当你对准备提交的文档或代码非常有把握, 并愿意接受缺少独立审核留下的风险时, 可以主动授予仅适用于这一次工作的例外:

> 我授权这次实施及 commit 流程不运行任何 Reviewer. 这是仅此一次的例外授权.

当任务目标和实施方式已经非常明确, 不需要审核实施前的治理设计, 但你对最终生成的代码或文档仍没有把握时, 可以只保留直接审核最终候选的两个 Reviewer:

> 我授权这次实施及 commit 流程省略 Spec Readiness 和要求符合审核, 只保留 Code Standards Reviewer. 这是仅此一次的例外授权.

这两项例外都必须由用户根据当前工作的风险主动发送. Agent 不能自行推断例外, 也不能把一次授权用于后续工作.

## 检查和总结本次工作

需要了解一次 commit 流程实际投入了多少 Reviewer 工作, 以及审核解决了什么问题时, 可以要求 Agent 只根据当前可取得的流程记录整理明细:

> 请汇总这次 commit 流程中各类 Reviewer 的执行次数, 可取得的总耗时以及发现并修复的问题. Reviewer 信息用表格呈现, 包括 Reviewer 名称, 执行次数和总耗时, 表格后给出可以取得的 commit 流程总耗时. 已修复问题用列表呈现, 每项分别写问题描述和修复描述, 最后给出问题总数.

当同一种协作问题似乎反复出现, 并希望改进长期使用的工具或规则时, 可以先让 Agent 对当前实际可见的会话记录做只读分析. 一次性的失误不一定值得形成持久机制, 因此分析应先区分反复问题和一次性问题:

> 请只读分析当前实际可见的会话记录, 找出反复出现的协作问题, 并把它们与一次性问题分开. 对每个值得长期改进的问题, 指出应修改的具体 Skill, Agent 规则或其他工具, 提出修改方案, 说明预期效果和副作用. 先向我展示分析和计划并等待批准, 不要直接修改任何持久工具.
