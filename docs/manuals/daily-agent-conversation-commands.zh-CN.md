# 与 Agent 对话时可直接采用的内容

[English](daily-agent-conversation-commands.md) | [简体中文](daily-agent-conversation-commands.zh-CN.md)

如果你已经在与 Agent 协作, 这份速查手册可以帮你在当前情境下直接选用下一段消息, 清楚交代目标, 边界和检查点, 始终掌控工作方向. 全文按一次完整会话的推进顺序排列: 先澄清并确认需求, 接着整理设计和原型, 然后实施已获授权的 issue, 最后复盘和总结本次工作. 复制示例前, 把 `XXX`, `NNNN:NN` 和路径替换为实际值. 这些提示用来引导对话, 不代替项目中的完整 Agent 规则或 Skill.

## 讨论并确认需求

当目标还不够清楚, 或者一个选择会影响产品行为, 数据, 安全, 公开 Interface 或长期维护责任时, 从这里开始. 在动手构建任何内容之前, 先让 Agent 和你把问题聊透:

> 我要做 XXX. 请使用 $grill-with-docs 和我讨论以达成共识. 每轮说明当前事实, 可行选择, 推荐方案和影响, 然后等待我回答.

`$grill-with-docs` 会通过多轮提问检验计划, 并在你明确确认后记录需要长期保留的术语或决定. 因为 Agent 的提问或说明可能过于专业, 如果遇到陌生的行话, 可以先让它用日常语言解释清楚:

> 这些术语我还不理解. 请先用普通语言解释它们在这个具体场景中的含义, 再继续提问.

就算术语讲明白了, 如果流程说明只是把事实平铺成列表, 中间有突然跳变, 读起来依然会摸不着头脑. 想看清流程到底怎么运转, 可以要求 Agent 从触发原因开始, 顺着因果关系把正常推进和失败恢复串起来讲:

> 你的流程说明我看不懂. 请从触发这个流程的原因开始, 按步骤说明每一步为什么发生, 需要什么输入, 执行什么操作, 产生什么结果, 结果怎样引出下一步. 如果某一步失败, 还要说明已经产生的影响, 没有产生的影响, 以及从哪里修正或重试.

听懂方案之后, 接着收紧它的范围. 如果 Agent 给出的方案超出了当前目标, 或者把初期实现设计得过深, 可以先把它拉回满足当前需求的最浅实现, 把将来的扩展留到确有需要时再处理:

> 请把方案限制在当前目标内, 不要自行扩大范围. 选择满足当前需求的最浅实施深度, 说明暂不处理的扩展方向以及以后什么情况才需要处理.

即使一项推荐表面上看起来合理, 你可能也拿不准它能不能经得起极端情况的推敲. 此时可以让 Agent 自己反驳自己:

> 请从反面检查你刚才的推荐. 找出最可能使它失败的前提, 反例和副作用, 再说明原推荐是否仍然成立, 或者应该怎样调整.

有时候讨论卡住, 是因为结论依赖还没核实的项目事实. 与其凭空猜测, 不如先派 Agent 只读调查代码库或权威来源, 把证据带回来再议:

> 先只读调查 XXX 的当前事实和权威来源. 把证据, 不确定性及其对当前选择的影响带回这轮讨论, 不要提前实施.

准备结束讨论前, 先盘点一下进展, 免得遗漏待定事项. 让 Agent 严格根据当前对话中已经可见的记录做一次梳理:

> 请列出当前已经确认的决定, 重要理由和仍未解决的问题. 只报告当前可见记录能够支持的内容, 不确定的项目明确标记为未知.

最后, 如果讨论已经形成了需要长期保留的决定, 还要确保它们落入真正拥有相应责任的持久文档. 下面这段消息会先要求提供检查清单和补写草稿, 等你审核批准后才会真正改动文档:

> 请检查当前会话内已经确认的决定和重要理由, 以及它们是否都记录在相应的持久文档中. 先输出检查清单和补写方案, 等我审核批准后再补写. 补写完成后重新检查并输出最终清单.

## 整理设计和原型

当你和 Agent 就需求达成整体共识后, 下一步就是把讨论内容整理成可实施规范; 如果还有拿不准的想法, 可以用原型探路, 或者削减多余的复杂度.

要把达成共识的讨论整理成 effort spec, 发送:

> 我们已经就 XXX 达成整体共识. 请使用 $to-spec 把当前对话整理为 effort spec. 在发布前先核对测试边界是否符合预期.

`$to-spec` 只负责综合已经讨论过的内容, 不会重新开展需求访谈. 因此, 如果还有未决选择会改变重要结果, 应先回到讨论, 不要让规范替你默默拍板.

有时候单靠文字推理不足以判断状态模型或 UI 呈现. 在敲定设计之前, 可以要求制作一个明确可丢弃的原型来回答具体问题:

> 请使用 $prototype 构建一个可丢弃原型, 只回答这个问题: XXX. 先说明原型能验证什么和不能验证什么, 完成后报告观察结果, 未解决决定和建议, 不把原型直接当作正式实现.

原型的作用是降低设计不确定性, 而不是交付正式代码. 当前平台是否另外提供图像生成, 浏览器或其他展示能力不属于 ARW 保证. 需要这些能力时, 先确认当前会话实际可用, 并且只把生成结果当作辅助输入, 不要当作已经确认的产品行为.

如果你要探索 UI 设计, 希望先从视觉方向一步步收敛到可操作的页面, 可以把图像构想, 页面原型和人工评价串成一条反馈回路:

> 请先用 imagegen 构想 XXX 模块的 UI 设计, 再用 $prototype 制作可操作的页面原型. 每轮向我展示结果并等待人工评价, 根据评价继续修改, 直到我明确确认设计决定. 最终原型仍是可丢弃的参考原型, 请另行记录经过确认和验证的设计决定, 不要把原型当作正式实现或实施授权.

在设计成型的过程中, 要警惕过度设计. 如果方案已经能达成目标, 但结构或流程显得太重, 可以让 Agent 对比更简单的办法, 并把简化的具体副作用摆出来供你权衡:

> 请检查是否存在仍能满足当前目标的更简单方案. 比较它与当前方案的责任, 机制和维护成本, 并列出简化会带来的具体副作用. 不影响已确认结果且没有具体风险的副作用可以明确标为可接受候选, 等我决定采用哪种方案.

同样, 如果方案开始为每个内部步骤都加上独立流程, 关卡或证据链, 让它砍掉多余部分, 只保留现有合同或具体风险真正需要的独立边界:

> 请检查当前方案是否为内部步骤建立了不必要的独立流程, 验证或证据链. 只保留现有合同要求, 或具体可预见风险确实需要的边界, 并说明每个保留项保护的结果. 不要仅因为一个步骤还能拆分就继续增加机制.

而当一个设计要经过多层内部实现才产生最终结果时, 让验证聚焦在用户真正观察得到的结果上, 避免顺着内部链路层层重复设卡:

> 请优先通过最终可观察结果验证完整设计, 不要默认把每个中间表示, 内部调用或实施阶段都设为独立检查点. 只有中间值本身属于公开合同, 持久证据, 授权边界或安全边界, 或最终结果不足以证明受治理属性时, 才增加相应的中间检查, 并说明理由.

等规范确定并精简妥当后, 另用 `$to-tickets` 把它拆成实施 issues. 先让 Agent 展示纵向切片, 阻断关系和各 issue 的治理依据, 等你审核并批准拆分方案后, 再发布到跟踪器.

## 实施已有 issue

当跟踪器中已经有了获授权的实施 issue, 就可以开始动手实现. 直接发送:

> 请使用 $implement 实现 issue:NNNN:NN.

在实施和提交流程中, ARW 通过几道独立门禁分别把关不同问题. 实施开始前, Spec Readiness 检查治理准备是否充分. 到了需要运行 Commit Audit 的实施提交阶段, 流程会先固定候选内容, 再统一准备并并行运行 Code Review 的两个审核轴: Code Standards 检查仓库标准, 要求符合审核检查治理要求. Agent 不得擅自省略或改写这些或其他适用门禁; 只有你明确决定并主动发送适用的授权内容时, 才能破例.

如果你对准备提交的文档或代码非常有把握, 愿意承担跳过独立审核的风险, 可以主动为这一次工作授予完全免审的例外:

> 我授权这次实施及 commit 流程不运行任何 Reviewer. 这是仅此一次的例外授权.

只有对设计和最终产出都十拿九稳时才适合全部跳过. 如果任务目标和实施方式已经非常明确, 不需要审核实施前的治理设计, 但你对最终生成的代码或文档仍没有把握, 可以选择只保留直接审核最终候选的两个 Reviewer:

> 我授权这次实施及 commit 流程省略 Spec Readiness 和要求符合审核, 只保留 Code Standards Reviewer. 这是仅此一次的例外授权.

由于每项例外都伴随风险, 这两项授权都必须由你根据当前工作的风险主动发送. Agent 不能自行推断例外, 也不能把一次性的授权沿用到后续工作.

## 检查和总结本次工作

当一次 commit 流程走完后, 如果你想了解这次实际投入了多少 Reviewer 工作, 以及审核到底抓出了哪些问题, 可以让 Agent 严格根据当前可取得的流程记录汇总明细:

> 请汇总这次 commit 流程中各类 Reviewer 的执行次数, 可取得的总耗时以及发现并修复的问题. Reviewer 信息用表格呈现, 包括 Reviewer 名称, 执行次数和总耗时, 表格后给出可以取得的 commit 流程总耗时. 已修复问题用列表呈现, 每项分别写问题描述和修复描述, 最后给出问题总数.

跳出单次提交来看, 如果同一种协作摩擦在会话中反复出现, 你可以借助会话记录来改进长期使用的工具或规则. 因为一次性的失误不值得专门加一套持久机制, 所以先让 Agent 对当前实际可见的会话记录做只读分析, 把反复出现的问题和偶然失误区分开, 等你批准方案后再动手改工具:

> 请只读分析当前实际可见的会话记录, 找出反复出现的协作问题, 并把它们与一次性问题分开. 对每个值得长期改进的问题, 指出应修改的具体 Skill, Agent 规则或其他工具, 提出修改方案, 说明预期效果和副作用. 先向我展示分析和计划并等待批准, 不要直接修改任何持久工具.
