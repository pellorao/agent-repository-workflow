# 恢复记录缺失的空闲后台 Agent 可被回收

## Problem

遗漏卸载就删除了恢复目录 (如清理 `.tmp`) 的空闲后台 Agent, 因恢复记录读取失败而被判定为 "不安全空闲", 容量回收, `unload_agent` 和安装维护都无法处理它们, 名额永久泄漏 (anthropic 提供方 4 个名额被 4 个已完成的 Reviewer 运行占满, 新任务报 "capacity is exhausted").

## Solution

`safeIdle` 在恢复记录文件不存在 (`ENOENT`) 时不再判为不安全; 记录存在但与运行不符或无法读取仍不回收. 容量回收按最近最少使用顺序逐个卸载空闲运行, 此前已如此, 无需改动. 被回收的运行因无记录可核对而不再能恢复. 规范 `Capacity and recovery` 与设计取舍就地改写.

## Module Design

### Modules

后台 Agent 管理 Module 拥有空闲运行的回收判定, 容量回收, `unload_agent` 和安装维护共用它; 责任不变, 只改变它对一类读取失败的判定.

### Interfaces

- 调用方可见结果: 满额时的容量回收, `unload_agent` 和安装维护对一个空闲运行的判定. 恢复记录读取成功且与运行相符, 或记录文件不存在 (`ENOENT`) 时可卸载; 记录与运行不符, 或因其他原因无法读取时不卸载.
- 不可卸载时的结果与此前一致: 容量回收返回容量不足, `unload_agent` 明确失败, 维护报告忙碌或未知. 记录缺失的运行被卸载后, 不再能由 `followup_task` 恢复 (恢复核对记录失败).

### Seams and Adapters

None: 不新增 Seam.

### Dependencies and Data Flow

权威来源表中恢复记录一行的回收条件改为记录存在时才核对一致; 记录文件不存在时, 回收依据管理进程状态中同样保存的身份与设置. 数据流方向和依赖不变.

### Module Design Rationale

记录是调用方工作区中的文件, 可被调用方删除; 回收若依赖它, 删除方的遗漏会使名额永久泄漏, 且容量回收, `unload_agent` 和维护都无法补救. 放宽只限于文件不存在, 因此不卸载记录与运行不符或无法判断的运行. 代价是缺失记录的运行丧失恢复能力. 替代方案 "要求删除方先卸载" 已是既有规则, 但无法约束遗漏; 迁移记录到管理进程私有状态改变调用方绑定的路径合同, 已在规范中拒绝.

### ADR Evaluation

不需要新 ADR: 不改变记录位置, 持久数据格式或恢复协议, 可随时撤销; 理由见主规范 Module Design Rationale.
