# Linux 进程身份不随墙钟变化与管理进程启动失败即时报错

## Problem Statement

后台管理进程靠 "PID 加操作系统报告的进程创建时间" 判断一个旧进程是否还是原来那次启动 (共享 App Server 和每个 Claude 回合进程都有这样的身份文件). Linux 上这个创建时间由系统启动时刻 (`/proc/stat` 的 `btime`, 即当前墙钟减去系统已运行时长) 加进程启动时刻换算而来, 因此依赖墙钟. WSL2 在宿主休眠恢复时会把墙钟向前步进, 步进量等于暂停时长, 可达数小时: 同一个仍然存活的进程重新读取时得到另一个创建时间, 被判为 "同一 PID 但不是原来那次启动", 即 "已结束". 后果是仍在运行的 App Server 或 Claude 回合进程被当作已结束, 它的身份文件被删除, 对应的 Agent 被按已退出恢复, 实际进程却继续存在而不再被管理. 同一处还有一个多余依赖: 每次读取身份都要运行一次 `getconf CLK_TCK` 子进程.

另一个问题在启动路径. 客户端第一次需要后台服务时启动管理进程并轮询控制端口, 子进程的标准输出和标准错误都被丢弃. 管理进程启动即失败时 (例如已安装的运行时损坏, 状态目录不可用), 客户端看不到任何原因, 只能一直轮询到 `backgroundAgent.messageTimeoutMs` 的总预算用尽, 报 `Background Agent control timed out before delivery.`. 用户既等了整个预算, 又得不到失败原因.

## Solution

Linux 上的进程身份值改为 "内核启动标识 (`boot_id`) 加进程 starttime 的时钟滴答数": 同一次系统运行期间 `boot_id` 不变, starttime 是进程创建时记录的相对系统启动的滴答数, 两者都不随墙钟步进变化, 所以休眠恢复后存活的进程仍得到相同的值; 系统重启后 `boot_id` 改变, 旧记录被正确判为已结束. 滴答数只做相等比较, 不再换算成纳秒, 因此不再需要 `CLK_TCK`.

客户端每次启动管理进程时把子进程的标准错误写到私有运行状态目录中本次专用的文件, 并监听子进程退出. 子进程在控制端口可连接之前就退出时, 客户端立即以该文件内容报错, 不再等到预算用尽. 例外是另一个管理进程正在启动: 多个调用方同时冷启动时, 只有一个管理进程能取得启动租约, 其余的会立即退出; 这种退出不是失败, 客户端继续等待赢得租约的那个管理进程.

## User Stories

1. 作为 WSL2 用户, 我希望宿主休眠恢复后仍在运行的 App Server 和 Claude 回合进程不被判为已结束, 以便后台 Agent 不因墙钟步进而被错误恢复或失去管理.
2. 作为用户, 我希望系统重启后重启前留下的旧进程身份仍被判为已结束, 以便新管理进程能清理旧记录.
3. 作为升级到新版本的用户, 我希望旧版本管理进程异常退出时留下的身份文件仍能被正确核对, 以便升级后不需要手工删除状态文件.
4. 作为用户, 我希望管理进程启动失败时立即得到失败原因, 以便不必等到总预算用尽后再自己排查.
5. 作为同时发起多个后台请求的用户, 我希望并发冷启动不因为某个多余的管理进程退出而误报失败, 以便现有行为不退化.

## Implementation Decisions

### Process identity value

身份文件仍是 `<PID>,<值>` 的纯文本, 两个值以一个 ASCII 逗号连接, 这一固定格式不变. 变化的只是 Linux 上 "值" 的内容, 其他平台 (Windows 与 macOS) 不变:

| 来源 | 值的形式 | 例 |
| --- | --- | --- |
| Linux, 新记录 | `boot_id`, 一个英文冒号, starttime 滴答数 (十进制) | `d427385f-63f2-4b52-b058-91a63b252ad9:2114598` |
| Linux, 旧记录 | 纯十进制数: 旧版本按 "`btime` 秒数乘十亿加滴答数换算的纳秒" 写入 | `1793735971980000000` |
| Windows, macOS | 纯十进制数, 与现在相同 | |

读取一条记录时先按下列规则校验其值 (这是磁盘文件进入程序的信任边界, 之后以确定类型传递): 值要么是十进制数, 要么是 `boot_id` 的标准 UUID 小写十六进制形式加冒号加十进制数, 其他内容视为无效身份, 观察结果为 `unknown`, 与现有对畸形文件的处理一致. 写入时对值使用同一校验, 所以记录入口也接受新形式.

观察一个正在运行的进程时, Linux 读取该进程当前的 `boot_id` 和 starttime, 组合成新形式的值; PID 不存在返回 "无此进程". 比较规则仍是 "进程不存在, 或当前值与记录值不同, 即为已结束; 相同即存活; 读取失败为 `unknown`".

### Legacy record compatibility

旧版本管理进程留下的身份文件是纯数字值. 它只会出现在旧版本管理进程异常退出 (没有机会删除文件) 之后由新管理进程接手的场景, 因为正常的安装更新会先让管理进程关闭并删除这些文件. 所以兼容只需覆盖 "读取并核对, 然后按现有流程删除", 不需要把旧记录改写成新形式: 记录是短命的, 进程退出后文件即被删除.

在 Linux 上读到纯数字值的记录时, 观察端按旧公式重算当前值再比较: 系统 `btime` 秒数乘十亿, 加 starttime 滴答数乘一千万 (旧公式以每秒 100 滴答计算, Linux 用户空间的滴答频率 (`CLK_TCK`) 在 x86-64 与 arm64 上固定为每秒 100, 与旧实现读到的值一致, 所以结果与旧版本写入的值逐位相同). 旧记录因此仍受墙钟步进影响: 这与升级前的行为相同, 不是退化, 也不在本规范范围内修复.

这条兼容路径只保留一个发布版本: 引入本改动的发布版本之后的下一个发布版本中删除它 (读取 `btime` 与旧公式的分支), 届时 Linux 上读到纯数字值与读到其他无效内容一样视为无效身份. 旧版本管理进程的残留记录在一个发布周期内已被各次更新或重启清理, 仍残留的记录交给 `unknown` 的既有处理 (保留文件, 由维护者核实后删除). 降级到旧版本不受支持: 旧版本读不懂新形式的值, 会把记录视为 `unknown`.

观察端怎样知道记录是旧形式: 读取函数把记录里的值作为第二个参数传给身份读取器, Linux 读取器据此在新旧两种形式之间选择; 其他平台读取器忽略它. 这样旧形式的判断留在 Linux 读取器内部, 调用方 (共享 App Server 与 Claude 回合进程的身份文件读写) 不变.

### Startup failure reporting

客户端启动流程在启动子进程前, 在私有运行状态目录中创建本次启动专用的文件, 名称为 `daemon-stderr-` 加一个随机后缀, 访问权限限定为当前用户, 并把子进程的标准错误直接指向该文件的文件描述符, 不使用管道, 因此客户端不读取管道也不会因管道关闭而使子进程收到 `EPIPE`. 标准输出仍丢弃. 这个文件取代现有的 "状态目录可写" 探测文件: 现有流程在同一个位置创建并立即删除一个空的探测文件, 现在创建本次的标准错误文件即证明目录可写, 因此不再另有探测文件, 创建失败 (沙盒拒绝, 空间不足等) 就是原来的探测失败, 结果相同: 尚未启动任何子进程, 操作系统权限拒绝 (`EPERM`, `EACCES`, `EROFS`) 按原有 `sandbox` 失败响应报告, 其他错误原样抛出. 不为该文件失败增加降级路径 (例如不带文件继续启动), 因为状态目录此时已不可写, 管理进程自己也无法启动.

子进程启动后, 客户端监听其 `exit` 事件, 随后沿用现有的轮询: 每个周期先探测控制端口, 可连接即启动成功. 子进程已退出而控制端口仍拒绝连接时, 按下列顺序判断:

1. 先探测维护端口 (启动租约所在的固定本机端口). 可连接说明另一个管理进程正在启动或有维护在进行, 这次退出不构成失败, 继续轮询, 受总预算约束.
2. 否则再探测一次控制端口. 仍被拒绝时读取本次的文件然后报错: 文字为 `Background Agent manager exited during startup` 加上退出码 (被信号结束时为信号名), 然后是文件内容 (去掉首尾空白; 为空时写明没有输出). 这个错误不重试, 因为没有任何管理进程在启动, 再次启动会得到同样的结果, 调用方应根据原因修复.

两次探测的顺序是为了关闭一个竞争窗口: 赢得租约的管理进程在控制端口开始监听之后才释放租约. 先看租约再看控制端口, 租约已释放就意味着控制端口此前已在监听, 第二次探测会连上; 反过来的顺序可能在两次探测之间错过这个交接而误报失败. 请求在预算用尽前仍未等到可连接的控制端口时, 沿用现有的超时失败, 此时没有退出事件可报告 (子进程仍在运行, 例如启动缓慢), 客户端不读取文件.

无论启动以成功, 失败还是超时结束, 客户端在结束时都删除本次的文件 (删除失败忽略). 管理进程仍持有该文件时删除也能成功 (Node.js 在 Windows 上打开文件时允许共享删除, POSIX 系统本来允许), 并且不影响它; 它此后写到标准错误的内容随之不再保留, 这不属于合同: 文件只为启动失败的即时报告服务.

每次启动使用独立文件, 是因为私有运行状态目录由当前用户的所有客户端共享: 多个仓库的命令, 多个 Main Agent, 或同一进程内的多个并发请求都可能同时冷启动, 固定文件会被后来者截断或与对方的输出交错, 使失败一方读到空内容或别人的输出. 代价是每次启动都要在结束时删除文件; 客户端进程在创建文件之后, 结束之前被强行终止, 或删除调用本身失败 (例如目录权限被改动) 时会留下一个孤儿文件 (内容只是管理进程的错误信息, 体积很小), 接受这一点而不增加扫描清理逻辑. 孤儿文件按卸载规范对未知文件的既有规则处理: 卸载保留它, 它所在的私有状态目录因此不会被当作空目录删除, 只产生已有的手工清理提示, 不影响卸载结果; 安装更新不读取它.

文件存在于私有状态目录中, 内容只有管理进程自己写的错误信息, 不含凭据.

管理进程一侧不改变. 它本来就把启动失败的原因写到标准错误并以退出码 `1` 结束, 客户端只是从此读取它.

私有运行状态目录因此在启动期间短暂出现 `daemon-stderr-<后缀>` 文件; 它不是凭据, 不进入安装清单, 卸载时与目录内其他运行状态一样处理.

### Long-term documents

长期规范只在定义该值的位置更新一次, 其余提到 "进程创建时间" 的地方通过这个定义引用, 不逐处改写, 以免同一事实多处各写一遍而互相不一致. 安装规范 Background Agent management 节描述身份文件 "值" 的句子改为: 值是操作系统对目标进程报告的创建标识, 在 Linux 上由内核启动标识和进程 starttime 滴答数组成, 不依赖墙钟, 其他系统仍是创建时间, 本规范与其他长期文档各处的 "进程创建时间" 都指这个值; 同一节同时写明启动管理进程时客户端使用的 `daemon-stderr-<后缀>` 文件. 受这一定义覆盖而不改写的现有提法是: 主规范 Background Agent State 节, Capacity and recovery 节的进程退出判断, 以及测试决定里的相关句子; 安装规范 Installation transaction and recovery 节的离线维护句子与测试决定; 发布规范中关于进程观察和创建时间的三处; ADR 0030 与 ADR 0033 中的 "操作系统进程创建时间" (这两份 ADR 的决定是 "用操作系统对目标进程的观察而不是文件时间辨认启动", 新值仍然满足它, 所以 ADR 不修改). 主规范中描述冷启动与预算的位置补一两句启动失败的即时报告规则 (退出码与标准错误文件内容, 另一个管理进程正在启动时不视为失败). 旧记录兼容是过渡性的, 只记录在本 effort 中, 不写入长期规范; 删除兼容路径时无需再改长期规范.

## Module Design

### Modules

进程身份读取模块 (`process-identity`) 仍然是进程创建值的唯一来源与比较者: 它新增一项 Linux 读取形式, 保留旧形式的读取作为过渡. 后台客户端模块 (`client`) 仍然拥有 "启动管理进程并等待它可连接" 的责任, 新增 "启动失败时报告原因" 这一部分; 管理进程 (`daemon` 与 host 入口) 不变. 不新增模块.

### Interfaces

- 身份读取器 `readOperatingSystemProcessCreationTime(pid, recorded?)`: 新增可选第二参数 `recorded` (记录里的值). 输出仍是字符串或 `null`; 在 Linux 上默认输出新形式, `recorded` 是纯数字时输出旧公式的值; 其他平台忽略该参数. 注入式读取器 (各调用方传入的 `readCreationTime`) 的类型随之为 `(pid, recorded?) => Promise<string|null>`, 现有不接收第二参数的注入器照常工作.
- "创建值" 这个已有字段的含义在 Linux 上改变 (从纳秒时间戳变为 `boot_id` 与滴答数的组合): 它在所有调用方处仍是不透明字符串, 只做相等比较, 文件格式的外形 (`<PID>,<值>`) 不变. 校验规则见 "进程身份值".
- 客户端 `createBackgroundAgentClient` 新增可选输入 `maintenancePort`, 默认等于已有的固定维护端口, 与已有的 `port` 输入对称, 使测试能指向未被占用的端口. 调用方 (命令入口) 不传.
- 客户端的失败文字新增一种: `Background Agent manager exited during startup` 开头, 其余部分如上. 其他失败文字不变. 该失败走与现有失败相同的路径 (抛出, 由命令入口按机器接口的既有错误响应交给调用方).

### Seams and Adapters

不新增 Seam. 平台差异仍封装在身份读取器内部 (Linux, Windows, macOS 各一支); 旧形式判断是 Linux 一支的内部细节. 启动流程直接使用 Node.js 子进程与文件系统接口, 与现有一致.

### Dependencies and Data Flow

- 身份: 调用方在进程启动边界读取当前值并写入身份文件 (新形式); 之后核对流程读取文件, 把记录值交给读取器取得当前值, 比较得出 "存活, 已结束, 未知". 依赖方向不变.
- 启动: 客户端创建标准错误文件, 启动子进程, 监听退出, 轮询控制端口; 失败时读取文件并抛出错误. 子进程是已安装的管理进程入口, 它的失败原因经标准错误文件单向流向客户端.

### Module Design Rationale

身份值不选容差比较: WSL2 恢复时步进量等于暂停时长, 可达数小时, 任何有限容差要么放过 PID 复用要么挡不住步进. 选 `boot_id` 加 starttime 是因为二者组合在一次系统运行中既稳定又能区分 PID 复用, 并省掉一个子进程和换算. 不把旧记录迁移为新形式: 记录短命, 迁移要多一段写入路径和失败处理, 而兼容读取只多一个分支且随一个版本删除. 旧公式里的滴答频率写为常数 100: 它只为复现旧版本写入的值, 在 Linux 用户空间固定为 100, 保留 `getconf` 只为这条将被删除的路径是更差的成本.

失败原因选标准错误文件而不是管道: 管道需要客户端持续读取, 客户端早于子进程退出时子进程写入会收到 `EPIPE`, 而管理进程设计上要长期存活并比客户端活得久. 选 "退出事件即时失败" 而不是 "只缩短等待": 没有原因的快速失败仍需用户排查. 把 "另一个管理进程正在启动" 排除在失败之外是必须的, 否则并发冷启动 (一个客户端内的多个并发请求, 或多个命令同时启动) 会让落败的子进程的正常退出变成误报; 用维护端口判断而不是给管理进程新增退出码, 是为了不改变管理进程一侧, 代价是客户端要知道这个固定端口 (它已在同一模块中定义).

### ADR Evaluation

权威来源: 进程创建值仍只由操作系统对目标进程的观察给出, 身份文件仍只是其副本, 没有新增权威.

持久状态: 身份文件外形不变, 只扩大了 Linux 上值的形式, 并保留一个版本的旧形式兼容, 删除条件已写明. 一个真实的限制: 新形式一旦写入, 降级到旧版本不受支持, 旧版本把它读成 `unknown` 而保留文件, 需要维护者核实后手工删除. 接受这一限制的理由是降级到旧版本本身不是受支持的路径, 而且身份文件只在进程存活期间存在, 正常降级流程会先停止管理进程并删除它们, 只有崩溃残留才会触发这个代价. 新增的 `daemon-stderr-<后缀>` 是私有运行状态目录中的短命诊断文件, 不参与恢复.

恢复合同: 进程退出判断的合同 (存活, 已结束, 未知及其后续处理) 不变, 只是 Linux 上不再因墙钟步进误判已结束, 旧记录在兼容期内按原判断恢复.

调用方可见结果: 管理进程启动失败时, 原先等到 `messageTimeoutMs` 超时并报 `timed out before delivery`, 现在立即报 `exited during startup` 加退出码和原因; 沙盒与权限拒绝的既有响应不变; 其他失败文字不变. 这是错误文字的收窄, 不是新增成功路径.

安全与授权边界: 标准错误文件位于已按当前用户加固的私有状态目录, 访问权限限定为当前用户, 内容只有管理进程写出的错误信息, 不含凭据 (凭据由管理进程在启动后写入单独文件, 不经过标准错误); 客户端只读取自己本次创建的文件, 不读取任意路径; 其他用户或仓库不能通过它得到新的访问能力.

与已有 ADR 的关系: ADR 0030 和 ADR 0033 把身份描述为 "操作系统进程创建时间", 它们决定的是用操作系统对目标进程的观察, 而不是文件时间; 新值仍是这种观察, 只是不再以墙钟时间的形式表达. ADR 0030 还规定正常管理进程启动持有维护端口直到启动完成, 本规范的 "另一个管理进程正在启动" 判断依赖的正是这一既有合同. 因此不需要新 ADR, 也不修改这两份 ADR: 两项选择都容易撤销 (回到旧读取与丢弃标准错误), 不改变管理进程边界, 不引入新的架构边界.

## Testing Decisions

测试边界是身份读取器与客户端的公开行为; 不启动真实管理进程和 Codex.

- 身份读取器: 用假 `/proc` 内容 (通过替换文件读取并还原) 作输入, 观察 Linux 值由 `boot_id` 与滴答数组成, 同一输入两次相同, 墙钟相关字段 (`btime`) 取不同值时结果不变. 这防止身份值重新依赖墙钟. 以旧形式记录为输入时, 观察旧公式重算的当前值与旧版本写入的值相同时判为存活, 不同判为已结束; 这防止升级后遗留的旧记录无法核对. `boot_id` 变化 (系统重启) 判为已结束. 观察不启动 `getconf`.
- 记录读写: 对新形式, 旧形式 (纯数字), 与畸形值各读取一次, 观察存活, 存活或已结束, `unknown`; 写入新形式后文件内容为 `<PID>,<值>`. 这防止校验拒绝新形式或接受任意内容.
- 客户端启动失败: 用一个只向标准错误写一行并以非零退出的真实子进程作管理进程入口 (这是套件中唯一为本规范增加的真实进程测试, 因为退出事件与标准错误文件的接线只有真实子进程能展示), 观察客户端在预算用尽之前以包含退出码和该行文字的错误失败. 同时观察另一个管理进程正在启动 (维护端口被占用) 时, 同样的子进程退出不使客户端失败, 客户端在控制端口随后可连接时成功送达请求. 这防止启动失败仍然等到超时, 也防止并发冷启动被误报.
- 文件创建失败的结果就是原来的探测失败: 该文件取代探测文件, 现有的沙盒拒绝测试 (状态目录不可写时给出沙盒失败响应且不启动子进程) 因此直接观察它, 不另设测试.
- 启动结束后不留下标准错误文件: 上面两个客户端观察 (失败, 以及另一个管理进程启动时的成功) 和一个超时观察 (启动的子进程退出而维护端口始终被占用, 请求在预算用尽时以现有的超时失败结束, 取代现有的并发冷启动超时测试里使用不存在入口的写法) 结束时都检查运行状态目录里没有该文件; 这防止每次冷启动留下文件.
- 现有客户端测试里使用不存在入口文件的字符串入口的几个测试, 子进程会立即退出; 它们按新语义指向未被占用的维护端口并占用它, 或改为观察新的失败文字, 其观察目标不变.

这些测试都是确定性的, 不依赖休眠恢复本身; 休眠恢复引起的墙钟步进由 "`btime` 变化而结果不变" 的观察代表, 不在本机真实复现.

## Out of Scope

- Windows 与 macOS 的进程身份读取.
- 旧形式记录的墙钟步进问题.
- 管理进程一侧的启动流程, 退出码和错误文字.
- 把进程观察移到公共模块, 或合并共享 App Server 与 Claude 回合进程的身份文件.
- 对 标准错误文件内容的大小限制与轮转, 以及孤儿文件的扫描清理.

## Further Notes

管理进程运行安装目录中的代码, 本改动影响身份文件的写入与核对 (管理进程一侧), 因此真实管理进程须经 `node install.mjs` 更新后才使用新形式; 客户端一侧的启动失败报告在下一次调用时即生效.
