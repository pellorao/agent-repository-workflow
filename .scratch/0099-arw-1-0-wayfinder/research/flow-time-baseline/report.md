# 当前 ARW 流程的耗时分布

## Scope

本记录回答 Wayfinder issue "测量当前 ARW 流程的耗时分布": 近期真实 ARW 工作中, Agent 的工作时间主要花在哪些步骤. 只计 Agent 工作时间, 不计用户阅读和回复前的等待. 数据是维护者本机 2026-10-25 到 2026-11-08 的 ARW 源码仓库日常工作 (ARW 自己维护自己), 在 2026-11-08 统计. 这是一台机器, 一位用户, 一个仓库的样本, 不代表其他用户; 它只作为 ARW 1.0 评测的初始基线和步骤取舍的输入, 不作架构决定.

## Data sources and boundary

数据来源与读取边界由 Main Agent 在 11-07 确认:

- Claude Code 会话记录 (`~/.claude/projects` 下的 jsonl, 含 subagent 记录和 ARW 后台管理进程以 `claude -p` 启动的会话). 统计脚本只读取每条记录的时间戳, 记录类型, 工具调用的工具名与配对 ID, 模型 ID, 以及 subagent 元数据中的任务标签; 不读取, 不输出消息正文, 工具输入和工具结果.
- 本机任务调度日志中每个 worker 的开始与结束时刻 (用于核对 worker 边界).
- 11-03 到 11-06 本机每日效率分析对 Commit Audit 轮次的既有统计. 当时的轮次记录在仓库 `.tmp` 下, 现已清理, 本轮无法重算, 只引用当时的结论.
- Codex 一侧不读取 `~/.codex/` 下的任何记录. 下文 "Codex side" 节引用的阶段数字来自本机 Codex 无人值守驱动器已经生成的阶段记录 (该驱动器当时由 Codex 会话记录中的工具调用时间推得); 本轮只读这些已生成的数字. Main Agent 11-08 确认采用: 它们只是阶段起止时间, 与 Claude Code 一侧允许读取的元数据同类, 不含会话正文.
- ARW 后台管理进程对 Reviewer 和后台 Agent 的工作时间计量 (见 [当前流程驱动方式研究](../current-flow-driver/report.md)) 只存在于各会话 `.tmp` 下的恢复记录里, 随临时目录清理而消失, 本轮可用的只有当前会话的一次 Commit Audit, 不足以统计.

## How time is attributed

本机的 ARW 工作方式: 用户把需求交给与其对话的 Main Agent, Main Agent 把每项工作交给一个 worker (Claude Code subagent) 在 ARW 仓库中完成, 包括实施, 验证, 启动 Reviewer 的 Spec Readiness 与 Commit Audit; 需要用户决定的事项写入异步待决定列表, 不在会话里等待. 所以 "用户发出消息到 Agent 结束回复" 在本机对应一次 worker 运行.

脚本把 worker 记录中相邻两条用户或助手记录之间的时间归入一类:

- 模型时间: 从用户消息或工具结果到下一条助手记录, 即模型生成和思考 (含实施时写代码和判断验证结果).
- 等待 ARW 后台运行: 工具调用 (几乎都是 Bash) 或后台等待的区间与 ARW 后台管理进程启动的 `claude -p` 会话的活动区间重叠的部分. 本机 Claude 后端 Reviewer 默认用 Haiku, 这类会话 400 个中 390 个是 Haiku, 所以这部分基本是等待 Reviewer (推断, 会话正文未读, 不能逐个确认角色).
- 其他命令: 其余工具调用时间, 主要是测试, Git 和 `arw` 命令.
- 后台等待: 助手结束回合后等待通知的时间, 与 ARW 后台会话不重叠的部分.
- 超过 10 分钟的模型间隔视为暂停或续跑, 不计入.

## Claude Code side

11-02 到 11-08 共有 82 次 ARW worker 运行. 其中 17 次是交付一个实施 issue (或一组合并的 issue) 并经过 Reviewer 审核的运行:

| 类别 | 分钟 | 占比 |
| --- | --- | --- |
| 等待 ARW 后台运行 (主要是 Reviewer) | 247 | 50% |
| 模型时间 | 190 | 38% |
| 其他命令 (测试, Git, `arw`) | 60 | 12% |
| 后台等待及其他工具 | 1 | 0% |
| 合计 | 497 | 100% |

- 每次运行中位数 24.9 分钟, 最短 8.3 分钟, 最长 74.4 分钟. 每次运行启动 1 到 9 个 ARW 后台会话.
- 等待 Reviewer 的占比在单次运行之间差别很大: 只有一轮审核的小修复为 30% 到 50%, 多轮审核的运行 (例如一次 74 分钟, 9 个后台会话的运行) 达 67%; 需要大量设计与改写的运行 (47 分钟) 只有 5%, 主要是模型时间.
- 其余 65 次运行是分析, 日常检查, 能力测试和研究, 中位数 6.4 分钟; 其中能力测试与无人值守驱动的运行有大量后台等待 (单次 55 到 123 分钟), 它们测的是工作流本身, 不属于用户请求的交付流程.
- ARW 后台管理进程在此期间以 `claude -p` 启动 400 个会话: Haiku 390 个, 单个会话活动时间中位数 6.0 分钟, 90 分位 14.2 分钟; Sonnet 6 个, Opus 4 个 (后者是长时间运行的测试类会话).
- Main Agent 自己的时间不在上表: 它的会话同时管理本机所有工程, 无法按 ARW 拆分. 在所有 worker 运行之外, Main Agent 会话中与 ARW 后台会话重叠的命令时间 8 天共约 16 分钟, 说明审核基本发生在 worker 运行内.

## Commit Audit rounds

11-03 到 11-06 本机每日效率分析对 Commit Audit 轮次记录的统计 (Spec Readiness 未单独统计):

- 11-03, 92 轮: 单个 Reviewer 一次运行约为 47 秒加每 KB 报告 39 秒 (n=180, r=0.70); 首轮报告平均 2.0 KB, 复审 1.1 KB. 两个 Reviewer 并行, 结束时间平均相差 29 秒. 只有 2 轮直接复用上一轮结果.
- 11-04, 7 次提交审核共 21 轮: 审核约 39 分钟, 同一提交审核内轮间修复等待约 26 分钟. 5 次两轮结束, 另外两次 3 轮 (约 18 分钟) 和 5 轮 (约 20 分钟).
- 11-05, 5 次提交审核共 16 轮: 每次至少 3 轮, 每次合计 7 到 14 分钟; 审核约 38 分钟, 轮间修复约 13 分钟. 首轮约占审核时间一半 (2.7 到 7.7 分钟), 后续每轮 0.6 到 1.5 分钟.
- 11-06: 结论为 "No problems." 的轮次仍要 4 到 6 分钟, 耗时主要由受审内容量决定, 与有没有问题无关.

## Codex side

本机 Codex 无人值守驱动器在 10-31 到 11-08 完成 29 个 issue (每个 issue 以一次成功提交为界, 已排除一次多个 issue 合并提交的运行). 阶段边界由驱动器按命令推得: 分析到实施以第一次修改文件为界, Spec Readiness 为 `prepare` 到 `promote`, 提交审核为第一次 `arw commit-audit prepare` 到提交, 已扣除等待用户的 138 分钟.

| 阶段 | 分钟 | 占比 |
| --- | --- | --- |
| 提交审核 (含轮间修复) | 378 | 58% |
| Spec Readiness | 171 | 26% |
| 实施 | 61 | 9% |
| 分析 | 34 | 5% |
| 其他 | 12 | 2% |

- 每个 issue 中位数 14.8 分钟, 四分位 5.7 到 24.3 分钟, 最长 110.8 分钟; 提交审核中位数 8.2 分钟. 29 个 issue 中 12 个有 Spec Readiness, 其中位数 3.6 分钟.
- 驱动器自己的说明列出的误差: 模型思考时间计入以该次工具调用结束的阶段; 批量 Spec Readiness 计入第一个 issue; 提交审核包含修复与复审循环; 有 12 行的总时长与各阶段之和不一致.
- 这些数字是 Codex 会话记录派生的阶段时间元数据, 不含正文, Main Agent 11-08 确认采用.

## What cannot be separated

- grilling: 本机按自主方式工作, 需要用户决定的事项进入异步列表, worker 运行中没有 grilling 等待; 首次需求讨论在 Main Agent 会话中进行, 与其他工程混在一起, 无法单独计时.
- Claude Code 一侧的 Spec Readiness 与 Commit Audit: 两者都表现为等待 Reviewer 会话, 不读会话正文就分不开; 只能用 Codex 一侧的阶段比例和上节轮次数据推断 Commit Audit 占大头.
- 实施与验证: 模型时间同时包含写代码和读验证结果, 测试命令与其他命令都计入 "其他命令".
- 等待 Codex 后端 Reviewer 的时间: 不产生 Claude 会话, 会被计入 "其他命令"; 本期 Reviewer 默认在 Claude 后端, 影响小.
- 11-03 有三个 worker 同时运行, 它们与同一批后台会话的重叠会被重复计算, 使该日的 Reviewer 等待偏高.

## Findings

- 有证据的事实: 在本机近期的实施交付中, 审核关卡是最大的单项耗时. Claude Code 一侧等待 Reviewer 占 worker 时间的 50%; Codex 一侧提交审核与 Spec Readiness 合计占 84%. 模型自己的生成与思考是第二大项 (Claude 38%, Codex 实施加分析 14%), 测试和其他命令约 12%.
- 有证据的事实: 一次 Reviewer 运行的时间主要由受审内容和报告长度决定, 调度和重复审核不是瓶颈; 每次提交审核通常 2 到 5 轮, 首轮占一半, 后续轮次每轮约 1 分钟加一次修复.
- 推断: ARW 1.0 若用 Jev 类模型或确定性检查在审核前拦下格式与记录类问题, 节省主要来自减少轮次与修复循环, 而不是缩短单次 Reviewer 运行; 预检本身的成本要比一轮复审 (约 1 到 2 分钟加修复) 低得多才有意义.
- 推断: 用户可感知的交付时长基线是每个实施 issue 约 15 到 25 分钟 (中位数), 长尾到 75 到 110 分钟. ARW 1.0 的评测与转正条件可以以此为对照, 但样本只有本机 46 个 issue, 且时长不反映结果质量和用户满意度.
- 未确认: Spec Readiness 在 Claude Code 一侧的占比.

## Reproduction

统计脚本 (只读元数据, Python 3 标准库) 和逐次运行的明细表保存在维护者本机的任务目录, 不进仓库. 重测时用同一方法即可: 按记录类型和工具调用配对归类时间, 用 ARW 后台会话的活动区间 (相邻记录间隔不超过 5 分钟的部分) 求重叠.
