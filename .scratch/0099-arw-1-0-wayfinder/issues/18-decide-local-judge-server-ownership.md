# 确定本地判断模型服务的运行责任

Type: grilling
Status: resolved
Blocked by: issue:0099:16

##### Question

本地 Jev 类候选 (如 Laya, NeoHorse) 以本机 HTTP 服务提供 `/v1/systemone`. 这个服务由用户自己安装并保持运行, ARW 只知道端点 (与托管服务同等对待); 还是由 ARW Engine 按需启动和停止, 并负责与同机其他本地模型 (如 Strata) 分配显卡? 若由 ARW 管理, 是推广现有 Strata 提供方的 lease 机制, 还是另设一套?

## Answer

用户 11-09 分三次答复, 原问题的三个选项 (用户自己运行, ARW 按需启停并推广 Strata 的 lease, 交给 Strata) 都没有原样采用.

选择顺序 (用户原话): "理想情况下, 本机如果能运行判断模型, 那么就取消 strata 的运行, 只运行这个判断模型. 模型选用机器能正常运行, 速度符合要求, 且智能最高的模型. 如果本机没有 gpu, 或是 cpu 模型对 cpu 的消耗过多, 则选用机构内部部署的模型. 上面两条都无法满足, 再退化到使用公开部署的模型."

与 Strata 的优先关系 (用户原话): "总之, 目前我判断, 这个判断模型的价值要高于 strata. 如果结论不是如此, 再改设计."

不退化与启动方式 (用户原话): "首先 "都没有时按 issue 16 交给高智能 Agent" 这个不对. ARW 1.0 肯定是要用判断模型的, 不会退化到交给高智能 agent. 而且我们的判断模型的速度有要求, 必须要让整体的任务执行速度快于不用判断模型时很多. 然后, 判断模型的启动其实就和 strata 一样, ARW 会创建一个开启脚本, 然后在 ARW 工作的时候, engine 会执行这个脚本, 启动判断模型, 这样才能开始正式工作. 没有判断模型, ARW 的 engine 基本无法工作."

因此:

- 判断模型是 Engine 的必需组件, 不是可选加速. 判断模型不可用时 Engine 不退化为把判断交给高智能 Agent, 而是不开工或停在可恢复状态, 并明确告诉用户缺什么, 怎样配置. 这改写了 [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md) 的回退部分.
- 选择顺序: 本机 (能正常运行, 速度达标的候选中智能最高的) → 机构内部部署 → 公开部署. 本机没有可用显卡, 或只用 CPU 的候选占用 CPU 过多时才看下一档. 公开部署由用户在配置中明确开启; 三档都不可用时 Engine 不开工. 速度和 CPU 占用的数值门槛由 [本地 Jev 类候选的可行性小实验](15-task-local-candidate-feasibility.md) 给出.
- 启动: ARW 配置时探测硬件, 按上述顺序选定模型写入用户级配置, 并生成一个开启脚本. Engine 开工时执行该脚本, 等判断模型通过就绪检查后才开始正式工作; 机构内部或公开部署没有本机进程, 开启步骤只做连通与兼容核对.
- 判断模型优先于同机的 Strata: 能运行判断模型的机器上, 两者争用显卡时由判断模型使用, 开启脚本先让 Strata 让出显卡; 因此不需要把 Strata 的 lease 推广为通用显卡分配. 若实验结论相反 (判断模型的价值不高于 Strata), 再改设计.
- 速度要求: 用判断模型的整体任务执行要比不用时快很多. 这是 1.0 的端到端验收条件, 由实验测量 "用与不用判断模型" 的任务墙钟, 不只测单次判断延迟; 具体倍数由实验和规范定.
- 失败恢复 (Main Agent 11-09 补充, 与不退化配套): 运行中判断模型进程退出或连接失败时, Engine 重新执行开启脚本并重试; 仍失败时流程停在可恢复状态并报告用户, 不改由高智能 Agent 代答.

仍待规范写明, 移入地图的 Not yet specified: Python 与推理运行时, 模型文件由谁安装和固定版本 (ARW 配置时安装还是给出安装说明), 开启脚本的内容与依赖, 怎样让同机其他显卡占用者让出显卡.
