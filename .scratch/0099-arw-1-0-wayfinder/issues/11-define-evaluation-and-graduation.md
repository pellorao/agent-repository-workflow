# 定义 Jev 类模型的评测与转正条件

Type: grilling
Status: resolved
Blocked by: issue:0099:02, issue:0099:05, issue:0099:12

##### Question

以用户发出消息到 Agent 结束回复的时长, 结果质量和用户满意度为指标, 怎样建立当前 ARW 的基线, 评测托管 Jev 与本地开源候选, 并按任务类别决定何时从全量高智能复核改为抽样复核? 漂移, 回退和停止使用某类判断的条件是什么? 托管评测可以发送哪些仓库内容?

## Answer

结论由 worker 分析, 交 Main Agent 综合; 11-14 按用户 D24 答复与批判审读一.2, 四.4, 四.5 改写 (原四阶段转正与对照方式的去向见 Comments). D24 后判断模型可选, 配了只做提示 (见 [定义分流判断的复核与回退合同](08-define-routing-review-and-rollback.md)), 不再有 "判断结论直接用于动作" 的阶段, 所以转正只剩 "离线评测过门槛就启用为提示, 线上记无效率, 超门槛停用". 下文的数值是首版默认, 是可调参数, 不是新的用户决定.

1.0 的验收对照:

- 对照现行 ARW (D23, D24): 同一类真实任务上比较 1.0 与现行 ARW 的高智能请求数, 整体墙钟, 上下文中规则与流程的占比, 规则与流程误判率, 以及停机点 (停下等用户) 的次数. 门槛按用户 D23 (普通流程墙钟比不超过 0.85, 高智能请求比不超过 0.65, 规则与流程上下文占比不超过 5%; 误判率按每天观察 codex 真实工作统计). 1.0 不配判断模型也要达到这些目标; 不再要求 "用判断模型比不用快很多".
- 时长: 一个流程从用户发出消息到 Agent 结束回复的墙钟, 只计 Agent 工作时间, 外加审核轮数. 现行 ARW 的基线来自 [测量当前 ARW 流程的耗时分布](12-research-flow-time-baseline.md): 每个实施 issue 中位数约 15 到 25 分钟, 提交审核通常 2 到 5 轮. 1.0 的 Engine 自己记录每步起止时间, 不再从会话记录推算.
- 结果质量: 沿用现行 ARW 的质量守护, 即 Reviewer benchmark 的盲评分与真实缺陷检出不下降.
- 用户满意度: ARW 不能直接测量, 用 Engine 记录中可数的替代量: 用户推翻或要求重做已交付结果的次数, 以及停机点的次数. 只靠替代量是已知局限, 规范中写明.
- "1.0 关闭判断模型" 只用于判断模型自身的取舍: 同一类流程开着与关着某类提示, 比较请求数, 墙钟与审核轮数, 看提示有没有收益; 它不是 1.0 的验收对照.

判断模型的使用条件与离线评测 (每类提示, 每个候选, 每个模型版本各一次):

- 使用条件 (用户 11-13, 见 [确定本地判断模型服务的运行责任](18-decide-local-judge-server-ownership.md)): 候选要比 DeepSeek flash 一类托管小模型快很多倍, 且准确率不明显降低, 否则不用. 两者在同一题集上测.
- 题集: [本地 Jev 类候选的可行性小实验](15-task-local-candidate-feasibility.md) 的 E3 判断题集 (带证据标签, 第二个模型复标 20%), 分出校准集与测试集. 必测: 准确率, 有害方向误判率, 所选项概率的校准 (ECE 与分桶准确率), 高概率错误率, 调换选项顺序后的翻转率, 单次与批量延迟, 成本.
- 门槛: 在校准集上为每类提示选一个概率阈值, 使阈值以上的测试集精度不低于 0.95; 阈值以上的案例占比 (覆盖率) 过低时该类没有收益, 不启用. 托管 Jev 1.14 与托管小模型用同一批案例作基准: 候选的阈值以上精度与覆盖率不明显低于基准即可启用, 不要求超过.

启用与停用:

- 启用: 过了离线门槛的提示类别在配置了该候选时启用为提示 (09); 没过的类别不出提示.
- 线上记录: 按 "提示类别 x 实际模型版本 x 题目模板版本" 记每条提示是否被核实它的会话判为无效 (09 中由 worker 核实). 累计满 100 条后无效比例超过 5% (与离线精度门槛 0.95 对应), 该类停用. 停用不需要用户决定; 重新启用需要新的模型版本或题目模板并重新离线评测, 候选若需要下载或付费, 按本机资源规则另报.
- 漂移: 响应中的实际模型版本或题目模板变化时, 该类提示停到新版本通过离线评测为止 (题目模板随 graph 与 Engine 一起发布, 见 22).

托管评测可发送的内容 (沿用 D3 的默认): 托管 Jev 与其他托管模型只接收取自 ARW 公开仓库的案例, 只用于离线评测; 线上提示在用户的私有仓库中只使用本地候选. 某个托管方案确实需要更多内容时另列待决定事项. 调用记录默认不保存 `state` 原文, 只保存长度, 哈希和来源, 见 [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md); 离线案例集本身取自公开仓库, 可以保存原文.

## Comments

11-11: 用户答复 [确定本地判断模型服务的运行责任](18-decide-local-judge-server-ownership.md) 后核对本答案. 两处不受影响: 对照组 "关闭判断模型" 只是实验对照, 不是运行时的退化路径; 某类判断停用后该类步骤由高智能 Agent 处理, 是评测结论决定该类不用判断模型, 不是判断模型不可用时的退化, 判断模型仍服务其他类别. 一处收紧: 用户要求用判断模型的整体任务执行比不用时快很多, 所以除每类判断各自要有时间收益外, 1.0 还要满足端到端的提速条件; 倍数由 [本地 Jev 类候选的可行性小实验](15-task-local-candidate-feasibility.md) 的端到端测量和规范定. 若各类判断转正后整体仍达不到, 回到设计重新考虑判断的用法, 不靠放宽门槛.

11-14 (D24 答复, 任务 v1-d24ans): 用户 11-13 选 A, 判断模型改为可选, 配了只做提示, 1.0 验收对照现行 ARW, 不再要求 "用判断模型比不用快很多"; 同日用户定下判断模型的使用条件 (比 DeepSeek flash 一类快很多倍且准确率不明显降低). 本答案相应改写: 删去影子, 全量复核, 抽样复核三个转正阶段, 60 条与 100 条的进入条件, Clopper-Pearson 上界, 滚动窗口, 覆盖率漂移检测和 "有害分歧" (它们都为判断直接驱动动作而设, 批判审读一.2 也指出规则几乎每天在改, 计数会一再清零); 改为离线评测过门槛就启用为提示, 线上记无效比例, 超门槛停用. 对照组由 "1.0 关闭判断模型" 改为现行 ARW (批判审读四.5), 关闭判断模型只用于判断模型自身的取舍. 上一条 11-11 中 "端到端提速条件" 与 "不靠放宽门槛" 两句随之作废; 其中 "若整体达不到就回到设计重新考虑判断的用法" 正是 D24 所做的事.
