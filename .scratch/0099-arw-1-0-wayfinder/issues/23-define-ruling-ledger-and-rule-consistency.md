### Where conflicts remain in 1.0

graph 中同一节点的每个结果值恰好一条边 (22), 所以一张 graph 内部不会再出现随机选择. 剩下的冲突来源:

3. 依赖数据的循环: 结构上合法的 graph 中, 某步要求的事实只在后面的屏障产生 (G06); 修复循环在特定输入下不收敛 (G05 的措辞问题每轮被重报).
4. 语义判断的先例: Agent 步骤对 "此例外是否适用", "此项是否属于某范围" 的判断 (A01, A07, A08), 用户答过一次的同样情况应沿用.

### Ruling ledger

- 格式: 每条裁决一行 JSONL, 行内自足, 与 D26 的逐节点 JSONL 同一风格 (grep 裁决 ID 或节点全名即可单独读到, 改动是行级 diff). 字段:
  - `id`: 裁决编号. `at`, `by`: 时间与回答者.
  - `node`: 产生它的 graph 节点全名 (`子流程/id`), 即等待用户节点, 或走了 "交用户" 分支的 Agent 节点. `nodeHash`: 记录时该节点的内容哈希.
  - `key`: 情况键, 由 Engine 从问题模板 ID 和问题的结构化来源 (冲突的两个节点全名或文档路径; 迁移后不再有源锚点, 见 22, 涉及的路径, 授权项) 机械算出, 不由 Agent 自拟.
  - `scope`: `user`, `repo`, `effort:<NNNN>`, `issue:<NNNN>:<NN>` 或 `instance:<id>`.
  - `question`, `answer`: 问题摘要, 用户所选项 (节点选项之一) 和一句理由.
  - `standing`: 用户回答时是否选了 "以后同类情况照此办理", 默认否.
  - `cause`: `rule-conflict`, `decision`, `info-missing` 或 `redundant`, Engine 按节点类别与答复预填, 用户可改.
  - `fix`: `rule-conflict` 类对应的 graph 或规则修复 (issue ID 或提交).
- 保存位置: `instance`, `issue` 与 `effort` 范围记在 Engine 私有状态库 (07 的待答事项已含问题, 选项, 背景与所属实例, 只加上述字段); `repo` 范围记在仓库中受跟踪的 JSONL, 由 Engine 作为非实施记录写入并提交; `user` 范围记在 Engine 的用户级目录. 两级与 07 模型映射表的 "全局加仓库两级" 一致 (待用户确认 1).
- 不承载要求, 不是第二个规则来源: 改变某个 issue 的范围, 行为或验收的答复仍写入该 issue 的 `## What to build` 或 `## Acceptance criteria` (现行 `issue-tracking` 规定记录章节不承载授权例外, 13 原样保留 issue 格式), 台账只记引用. `rule-conflict` 类裁决是规则缺陷的临时处置, 必须有 `fix`; 修复使 `node` 的哈希变化后该条自动失效.
- 注入: Agent 节点开始时, Engine 选出 `node` 为本节点, `scope` 覆盖本实例且 `nodeHash` 仍与当前节点一致的裁决, 作为 "已有裁决" 一段附在本步消息中 (条数上限与截断由规范定). 进入等待用户节点 (含 Agent 的 "交用户" 分支) 前, Engine 按 `node` 加 `key` 精确匹配: 有 `standing` 裁决时取其答案继续, 步骤记录写明所用裁决 ID, 用户可在入口撤销; 没有匹配时照常等待用户, 答复后写入台账. 匹配只做精确比较, 不做语义相似检索, 所以不依赖判断模型. graph 可以把某个等待用户节点标为不接受常设裁决 (如每次开工的授权) (待用户确认 2).
- 失效: `nodeHash` 不符的裁决不再注入或自动作答, 在一致性检查中列为待复核; `issue` 与 `effort` 范围的裁决随其终态失效.

### Consistency check

在 graph 改动的同一提交中运行 (D26 后 graph 是权威, 改 graph 即改规则; 一次性迁移时同样运行). 能静态检出的作为源码仓库检查的错误; 只能由夹具检出的写成夹具要求; 两者都检不出的留给审核与每日观察.

静态检出 (Engine 加载与源码仓库检查共用同一段代码, 是 22 第 1 层的扩展):

- 同一节点同一结果只有一条边, 没有默认边 (22 已有); 子流程调用无环, 调用方 `next` 与被调方 `returns` 一致 (试转换的 `check.py` 已做).
- 数据依赖循环: 子流程头声明 `reads` 与 `writes` (22 的 Graph format 节), 原语声明自己产生的事实 (如提交号只由提交原语在提交屏障之后写出). 某节点读取的状态键在所有到达它的路径上都只能由它之后的节点写出时报错. 这检出 graph 内部的 G06 类循环.
- 跨层保证: 子流程头为每个结果声明经过的屏障或关卡 (`guarantees`), 原语要求的前置 (如提交前须过正式关卡) 机械核对; 做法见 22 Verification 节第 1 层的必经边.
- 文档引用闭包: Agent 节点附带的规则文档中 "读取 `<路径>`" 一类必读引用 (`docs/agents/writing.md` 要求引用写成反引号路径, 所以可以机械提取), 不在该节点读取范围内或与节点读写属性相反时报冲突. 这检出 G04 类. 没有写成路径引用的散文要求检不出, 归入审核.
- 节点能力对文档禁令: 节点输出 schema 的分支 (如 "交用户") 与附带文档中以固定句式写出的禁令相反时报错. 禁令要写成可提取的固定句式, 由 21 归类 Reviewer 文档与方法类 Skill 时整理.
- 台账自身: 每条的 `node` 存在, `answer` 是该节点现有选项之一; `nodeHash` 不符的列为待复核, `rule-conflict` 类没有 `fix` 的列出 (不阻断).
- 停机点清单: 列出每个子流程的等待用户节点和 "交用户" 分支, 附台账中的历史停机次数, 作为改动说明的一部分, 供逐个审查能否改为自动恢复 (D25 第五目标).

分支夹具检出 (22 Verification 节第 2 层的分支测试):

- 接线错误: 试转换中互换同一节点两条边的 164 个变异, 静态校验拦住 0 个, 加上边要求也只拦住 4 个, 只能靠夹具.
- 不收敛的循环: graph 中每个环至少有一个夹具让 mock 的 Agent 输出每轮重复同一结果 (如 Reviewer 每轮重报同一措辞问题), 断言实例在设计的轮次上限内离开环或进入设计好的等待用户节点, 不出现无限循环或计划外的停机. 这检出 G05 类.
- 停机回归: 每条 `rule-conflict` 与 `redundant` 类裁决对应的情况写成一个夹具 (输入取当时的实例状态), 修复后断言该情况不再停. 真实停机由此变成回归测试.

两者都检不出, 靠审核与观察: 两份散文文档对同一事实写法相反, 又没有落到节点或路径引用上 (由改动提交的要求符合审核对照, 22 Verification 节第 3 层); 依赖工作项内容的循环, 如 issue 的验收标准写了提交后的事实, 它不在 graph 中, 改由下节在写 issue 时检查.

### Work list check

工作清单 (triage) 指一次开工的工作项: 规划流程产出的 issue, 其 What to build 中的授权例外, 以及用户开工时的指示. 常设约束 (brief) 指与具体工作无关, 每次都生效的约束: graph 的缺省动作 (如行为保持), 仓库配置中的禁改路径与体积参数, 用户级规则, `repo` 与 `user` 范围的裁决. 检查在规划流程写完 issue, 进入 Spec Readiness 之前运行:

- 机械部分 (Engine 程序): issue 列出的路径对禁改路径 (未被授权例外覆盖即矛盾, 沿用现行驱动派发前检查的做法); issue 的结构化声明对缺省动作 (如含 `行为保持重构例外:` 段落又列了行为修复); 分组对 Engine 约束 (如例外工作流要求一个 effort 只有一个实施 issue, 即 E5b 的 G02, G03); 验收项引用提交, Commit Audit, 提交号等提交后才有的事实 (G06; 现行 `lib/spec-readiness/precheck.mjs:36` 已对验收项做机械检查, 可在同处扩展).
- 语义部分: 写 issue 的 Agent 步骤的输出 schema 加一个必填字段, 列出它发现的工作项与常设约束的矛盾 (D24: 语义判断放进正在干活的 Agent 步骤的必填字段, 不另设判断题).
- 有矛盾时进入一个等待用户节点, 一次列出全部矛盾; 改变 issue 的答复写进 What to build, 常设的写进台账. 执行阶段因此只会遇到开工时看不到的矛盾, 不再有 A03 到 A06 那种明写在清单与指令里的.
