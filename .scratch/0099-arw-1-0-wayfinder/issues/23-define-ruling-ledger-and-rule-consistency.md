### Ruling ledger

用户 11-14: 台账也改为 graph 形式 (原话见 Comments). D27: 规则冲突与流程问题先改规则与流程本身, 改不了才用台账修正; ARW 源码仓库中对所有安装成立的修正直接改 graph; 已安装 ARW 的仓库与机器把发布的 graph 当只读, 自己的规则与流程调整记在它之上. 所以台账从 "已答复的裁决" 扩为采用方的定制层, 就是 22 Layers 节的上层: 流程调整是补丁, 新节点与新子流程, 裁决是其中的预置答案. 本节只定预置答案; 分层, 合并, 校验与过期检出见 22.

- 预置答案记录与其他 graph 记录同一格式, 每行一条, 字段:
  - `answer`: 产生它的节点全名 (`子流程/id`), 即等待用户节点, 或走了 "交用户" 的 Agent 节点. `base`: 记录时该节点合并后的内容哈希与 ARW 版本 (22).
  - `id`: 记录编号, 步骤记录与撤销用它. `at`, `by`: 时间与回答者.
  - `key`: 情况键, 由 Engine 从问题模板 ID 和问题的结构化来源 (冲突的两个节点全名或文档路径, 涉及的路径, 授权项) 机械算出, 不由 Agent 自拟.
  - `choice`: 用户所选项 (节点选项之一). `reason`: 一句理由.
  - `cause`: `rule-conflict`, `decision`, `info-missing` 或 `redundant`, Engine 按节点类别与答复预填, 用户可改. `fix`: `rule-conflict` 类对应的修复 (本仓库的补丁, 或报给 ARW 的 issue).
  - `until` (可选): `effort:<NNNN>` 或 `issue:<NNNN>:<NN>`, 该 Artifact 进入终态后记录失效.
  - 只记结构化字段, 不记问题背景的自由文本, 因为仓库层受 Git 跟踪, 由协作者共享.
- 哪些答复成为记录: 用户答复时可选 "以后同类情况照此办理", 并选本仓库 (仓库层) 或本机 (本机层); 默认不选, 答复只属于本次待答事项, 留在 Engine 私有状态的步骤记录中, 不写进 graph. 所以上层只有常设的答案, 原先的 `standing` 字段, 非常设的持久裁决和 `instance` 范围随之取消. 原先的 `user` 范围 (所有仓库通用, 存在 Engine 的用户级目录) 也不设: 用户提出的只有仓库与本机两级, 有跨仓库的需要时再加.
- 写入: 本机层由 Engine 直接写文件 (该目录被 Git 排除, 不是 Git 写入, 不占写入令牌). 仓库层先在 Engine 状态中生效, 再由 Engine 作为非实施记录写入并提交, 这是一次需要令牌的写入 (07, 10). 写入前按 22 校验合并结果.
- 不承载要求, 不是第二个规则来源: 改变某个 issue 的范围, 行为或验收的答复仍写入该 issue 的 `## What to build` 或 `## Acceptance criteria` (现行 `issue-tracking` 规定记录章节不承载授权例外, 13 原样保留 issue 格式). `rule-conflict` 类记录是规则缺陷的临时处置, 应有 `fix`; ARW 源码仓库按 D27 直接修管理层, 不留这类记录.
- 注入: Agent 节点开始时, Engine 选出 `answer` 为本节点, 未过期且 `until` 未到的记录, 作为 "已有裁决" 一段附在本步消息中 (条数上限与截断由规范定), 会话因此不必再问同样的情况.
- 自动作答: 进入等待用户节点 (含 Agent 的 "交用户" 分支) 前, Engine 按节点加 `key` 精确匹配有效记录 (两层都有时本机层优先): 有匹配时取其答案继续, 步骤记录写明所用记录的 `id`, 用户可在入口撤销 (删除该记录, 从下一次匹配起生效); 没有匹配时照常等待用户. 匹配只做精确比较, 不做语义相似检索, 所以不依赖判断模型. graph 可以把某个等待用户节点标为不接受常设裁决 (如每次开工的授权), 合并校验拒绝指向它的记录. 这一用法由 Main Agent 11-13 定 (原待确认 2 的选项 A), 见 Comments.
- 失效: `base` 不符 (ARW 升级或下层改了该节点) 的记录按 22 为过期, 不注入也不自动作答, 照常问用户, 并列入复核; `until` 的 Artifact 进入终态后失效. 预置答案不随实例绑定, 每次使用时读当时的记录 (07 的共享状态可见性).
- 停机计数: 每日观察按 Engine 步骤记录中的全部待答事项统计停机 (含非常设的答复), 待答事项同样带 `cause` 与 `key` (07).

### Consistency check

在 graph 改动的同一提交中运行 (D26 后 graph 是权威, 改 graph 即改规则; 一次性迁移时同样运行). 能静态检出的作为源码仓库检查的错误; 只能由夹具检出的写成夹具要求; 两者都检不出的留给审核与每日观察.

静态检出 (Engine 加载与源码仓库检查共用同一段代码, 是 22 第 1 层的扩展):

- 同一节点同一结果只有一条边, 没有默认边 (22 已有); 子流程调用无环, 调用方 `next` 与被调方 `returns` 一致 (试转换的 `check.py` 已做).
- 数据依赖循环: 子流程头声明 `reads` 与 `writes` (22 的 Graph format 节), 原语声明自己产生的事实 (如提交号只由提交原语在提交屏障之后写出). 某节点读取的状态键在所有到达它的路径上都只能由它之后的节点写出时报错. 这检出 graph 内部的 G06 类循环.
- 跨层保证: 子流程头为每个结果声明经过的屏障或关卡 (`guarantees`), 原语要求的前置 (如提交前须过正式关卡) 机械核对; 做法见 22 Verification 节第 1 层的必经边.
- 文档引用闭包: Agent 节点附带的规则文档中 "读取 `<路径>`" 一类必读引用 (`docs/agents/writing.md` 要求引用写成反引号路径, 所以可以机械提取), 不在该节点读取范围内或与节点读写属性相反时报冲突. 这检出 G04 类. 没有写成路径引用的散文要求检不出, 归入审核.
- 节点能力对文档禁令: 节点输出 schema 的分支 (如 "交用户") 与附带文档中以固定句式写出的禁令相反时报错. 禁令要写成可提取的固定句式, 由 21 归类 Reviewer 文档与方法类 Skill 时整理.
- 台账 (上层记录): 节点存在, 答案是现有选项之一, 节点接受常设裁决, 常设答案不造成无出口的环, `base` 不符的列为过期, 都是 22 Layers 节的合并后校验, 不另设检查; 只另列出 `rule-conflict` 类没有 `fix` 的记录 (不阻断).
- 停机点清单: 列出每个子流程的等待用户节点和 "交用户" 分支, 附 Engine 步骤记录中的历史停机次数, 作为改动说明的一部分, 供逐个审查能否改为自动恢复 (D25 第五目标).

分支夹具检出 (22 Verification 节第 2 层的分支测试):

- 接线错误: 试转换中互换同一节点两条边的 164 个变异, 静态校验拦住 0 个, 加上边要求也只拦住 4 个, 只能靠夹具.
- 不收敛的循环: graph 中每个环至少有一个夹具让 mock 的 Agent 输出每轮重复同一结果 (如 Reviewer 每轮重报同一措辞问题), 断言实例在设计的轮次上限内离开环或进入设计好的等待用户节点, 不出现无限循环或计划外的停机. 这检出 G05 类.
- 停机回归: ARW 源码仓库修复的每个 `rule-conflict` 与 `redundant` 类停机 (D27: 直接修管理层) 写成一个夹具 (输入取当时的实例状态), 修复后断言该情况不再停. 真实停机由此变成回归测试.

两者都检不出, 靠审核与观察: 两份散文文档对同一事实写法相反, 又没有落到节点或路径引用上 (由改动提交的要求符合审核对照, 22 Verification 节第 3 层); 依赖工作项内容的循环, 如 issue 的验收标准写了提交后的事实, 它不在 graph 中, 改由下节在写 issue 时检查.

### Work list check

工作清单 (triage) 指一次开工的工作项: 规划流程产出的 issue, 其 What to build 中的授权例外, 以及用户开工时的指示. 常设约束 (brief) 指与具体工作无关, 每次都生效的约束: graph 的缺省动作 (如行为保持), 仓库配置中的禁改路径与体积参数, 用户级规则, 仓库层与本机层的预置答案. 检查在规划流程写完 issue, 进入 Spec Readiness 之前运行:

- 机械部分 (Engine 程序): issue 列出的路径对禁改路径 (未被授权例外覆盖即矛盾, 沿用现行驱动派发前检查的做法); issue 的结构化声明对缺省动作 (如含 `行为保持重构例外:` 段落又列了行为修复); 分组对 Engine 约束 (如例外工作流要求一个 effort 只有一个实施 issue, 即 E5b 的 G02, G03); 验收项引用提交, Commit Audit, 提交号等提交后才有的事实 (G06; 现行 `lib/spec-readiness/precheck.mjs:36` 已对验收项做机械检查, 可在同处扩展).
- 语义部分: 写 issue 的 Agent 步骤的输出 schema 加一个必填字段, 列出它发现的工作项与常设约束的矛盾 (D24: 语义判断放进正在干活的 Agent 步骤的必填字段, 不另设判断题).
- 有矛盾时进入一个等待用户节点, 一次列出全部矛盾; 改变 issue 的答复写进 What to build, 用户选了常设的写成预置答案. 执行阶段因此只会遇到开工时看不到的矛盾, 不再有 A03 到 A06 那种明写在清单与指令里的.
