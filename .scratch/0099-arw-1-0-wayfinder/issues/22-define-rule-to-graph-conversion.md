### Goals served

- 高智能请求数与墙钟: 现行 worker 请求中规则流程类 (读规则, 关卡命令, 写记录, 决定下一步) 约占 63% (15 的 11-13 Comments, 元数据统计); 这些由 graph 的程序节点和 Agent 节点输出 schema 中的分支字段承担, 估算的节省主要来自这里.
- Agent 上下文中规则与流程的占比: Agent 步骤只收到本步指令, 迁移后转换范围内的规则原文不再存在.
- 规则与流程上的误判率: 顺序, 门禁和跳过条件由程序执行, 不受会话压缩影响; 剩下的语义判断都是有 ID 的 Agent 节点中的分支字段, 误判可以按节点与字段统计. 规则互相矛盾时不再随机选一种做法, graph 的行为是确定的, 错了每次都错, 便于发现 (用户 11-13, D25).
- 代价: graph 错了是系统性错误. 形状由静态校验拦住, 接线由分支测试拦住, 见 Verification 节.

### Authority and one-time migration

- 用户 11-13 (D26): 迁移后 graph 加节点上的说明是唯一权威. 改流程直接改 graph; 给人看的流程说明由 graph 生成, 不手写 (Changing flows after migration 节).

- 迁移源映射只用于一次性的完整性核对: 转换范围内每个段落一行 (路径, 段落, 类别, 去向节点, 或删除及理由). 核对每段都有去向后, 在迁移的最后一步把转换范围内的规则正文, 源映射和节点上的源锚点一并删除, 之后不再维护; 不做段落哈希的过期检查, 也不做增量重新转换.
- 迁移时发现的规则矛盾与歧义 (试转换遇到的: 共享文件的语义归属, 一个段落含约 10 条规则的粒度问题, 步骤中途的事件, 规则之外转换者自己补的步骤), 按 D25 一次列给用户问清, 答案直接写进 graph, 不默选, 也不进裁决台账 (23). 现行规则中的 G05, G06 已由 0.x 的 0121 (`b42278c`) 修复, 见 23.

### Source checkout graphs

- 用户 11-13: ARW 源码仓库自身的规则和流程也转成 graph. 范围是 21 中源码仓库专用的 17 项 (约 41.7K 字符, 转换范围约 26K): `release` (含发布, fixture 与回滚), `reviewer-capability` 与漂移检查, Reviewer 能力测试的触发与待测项, 根 `AGENTS.md` 仓库自有区域中的触发与 Baseline 例外; 验证命令与模型映射表按 21 的决定 B 移到配置. 与分发部分同一次迁移.
- 11-14 起这些 graph 就是 ARW 源码仓库的仓库层 (Layers 节), 与采用方的仓库层同一机制: 只在本仓库加载, 不随 Engine 分发, 打包时排除, 与现行仅供 Source Checkout 使用的 Skill 不进入 Workflow Distribution 的边界相同. 所以 Engine 不必识别当前仓库是不是 ARW 源码检出, 也不再限 "只能整体替换顶层流程": 需要改变分发流程行为的地方 (如改动 Reviewer 规则的提交之后进入能力测试或登记待测项) 用补丁把管理层节点的边接到仓库层的子流程. 能写成参数的例外 (如单回调耗时阈值, 规则改动的确认方式) 是仓库配置字段, 由分发 graph 读取.
- 与采用方不同, ARW 源码仓库中对所有安装都成立的修正直接改管理层, 不写上层记录 (D27). 改了管理层节点的提交同时用命令行工具更新指向它的仓库层记录的 `base`, 源码仓库检查以 `HEAD` 中的管理层核对; 重新安装 Engine 之前, 本机 Engine 把这些记录视为过期, 与团队成员 ARW 版本不同时同一处理 (Layers 节).
- 上层 (含采用方) 的程序节点同样只调用 Engine 原语. 仓库专用的操作 (如 `scripts/release-vm.mjs`, `scripts/reviewer-capability.mjs`) 经一个通用的运行仓库命令原语调用: 命令与参数写定在 graph 中, 结果按退出码映射为结果值, 与运行仓库测试命令同一做法. 所以 Engine 不加载仓库提供的原语代码; 仓库层写定的命令与仓库配置中的验证命令信任程度相同, 不增加信任边界.
- 原 "其他已采用仓库的自有扩展 graph 不在首版开放" (D20 取舍 1 的选项 B, Main Agent 的取舍) 由用户 11-14 的提议推翻: 采用方的流程调整写在仓库层与本机层. 采用方散文形式的自有规则 (写作, 输出等) 按 13 仍是文本.

### Migration workload

以下是推断, 由迁移实测校正.

- 试转换: commit 流程分层后 74 个节点 (其中 20 个 `call`), 用到 24 个原语 (现有 2 个, 需拆分 7 个, 新写 15 个), 约 65 次高智能请求, 墙钟 26 分钟, 其中分层加改 JSONL 约 10 分钟.

- 源码仓库专用部分 (用户 11-13 追加): 转换范围约 26K 字符, 约为分发部分转换范围 (约 64.6K) 的 40%, 主要是 `release` 与 `reviewer-capability` 两个流程加几处触发; 按字符比例外推约 150 到 200 次请求, 1 到 1.5 小时. 它的程序节点多是经运行仓库命令原语调用现有脚本, 新原语较少.

- 迁移后的维护 (试转换估算, 转换范围内 9 个文件 19 天里提交 45 次): graph 为权威时每次流程改动约 10 到 25 次请求; 若仍以文本为权威, 每次要加增量转换, 约 25 到 50 次.

### Graph format

用户 11-13: 不用整份 JSON 文件, 因为读其中一段也要全量解析, agent 和人都难读大型 JSON; 每个节点一条自足的记录.

- 每个子流程一个 JSONL 文件, 一行一条记录, UTF-8 与 LF, 键按固定顺序写出. grep 节点 id 即可单独读到一行, 改动是行级 diff. 第一行是子流程头, 其后每行一个节点. 一个工作流共用的参数和工作键各占一行, 放在该工作流目录的 `_shared.jsonl`.
- 子流程头: `flow` (名称), `desc` (说明), `entry` (入口节点), `returns` (每个返回值和一句说明), `reads` 与 `writes` (读写的实例状态键), `guarantees` (每个返回值必经的边, 见 Verification 节).
- 节点: `id` (子流程内唯一, 全名 `<子流程>/<id>`), `type`, `desc` (必填, 一句话), 类型字段, `next` (结果值到目标; 目标是同一子流程的节点 `id`, 或 `return:<返回值>`), 以及下文的节点属性.
- 参数: 规则中的数字和可配置值 (如 "第 3 轮起只为行为缺陷开修复轮" 的 3) 写成 `_shared.jsonl` 中的参数记录 (名称, 值或来源 (graph 常量, Repository Profile, 仓库配置, 用户配置), 类型, 说明). Agent 节点的指令用 `{param:<名称>}` 引用, Engine 组装消息时代入; 原语经参数接收, 代码中不写死. 读改实测中 graph 组把 "第 3 轮" 改为 "第 4 轮" 要改指令, 节点说明, 原语备注和代码四处, 集中后只改一处.
- Agent 节点的指令是 `rules[]`: 每条一句可单独 diff 的规则, 带序号; 不把 1 到 2 KB 的规则段塞进一个字符串, 读改实测显示那和读文本没有区别, 只是多了转义.
- 例 (试转换的一个子流程头和一个节点, 改为本格式, 有省略):

```jsonl
{"flow": "audit-round", "desc": "一轮 Commit Audit: 冻结候选, 计轮次, 两个 Reviewer 与完整验证并行, 汇总结果.", "entry": "freeze", "returns": {"all-clear": "两轴无问题且验证通过", "findings": "有问题或验证失败", "error": "冻结失败或 Reviewer 未完成"}, "reads": ["authorizingIssueIds"], "writes": ["round", "findings"], "guarantees": {"all-clear": ["audit-round/freeze:frozen"]}}
{"id": "round", "type": "program", "desc": "按同一授权范围数轮次, 第 {param:noFixFromRound} 轮起的处置规则由此生效.", "primitive": "round.next", "args": {"scope": "$state.authorizingIssueIds"}, "next": {"counted": "axes"}}
```

### Graph shape

graph 是有向图, 允许环 (修复循环, 审核轮次). graph 本身是声明式数据, 不含代码 (D20).

分层 (D26 前提之一): 逻辑包成有名字的子流程, 头部声明输入 (`reads`), 输出 (`writes` 与 `returns`) 和说明; 用 `call` 节点调用, 按 07 的栈同步执行, 子流程结束后沿调用节点上与返回值同名的边继续; 子流程可以嵌套, 不能递归 (调用图无环). 每层都有说明, 人和 agent 从顶层子流程读起, 需要时才进入下一层. 试转换的 commit 流程分 4 层 (顶层 1 个子流程 4 个节点, 第 2 层 4 个子流程 22 个, 第 3 层 8 个 39 个, 第 4 层 3 个 9 个), 单个子流程最多 11 个节点; 同一流程不分层的平面边表明显比文本难读. 顶层子流程的返回值就是实例的终止结果 (如 `done`, `cancelled`), 不另设终止节点.

节点类型:

- 程序节点 (`program`, 机械步骤): 调用一个原语, 参数是常量, graph 参数, 实例状态字段或前面节点的结果. 结果是原语声明的一个结果值加数据. 例: 冻结审核候选, 运行确定性检查, 切出预检单元, 轮次计数, 暂存与提交.
- 判断节点 (`judge`, 可选的判断模型提示, D24): 一道 `choice` 或 `noul` 题, 含题目模板, 选项, `state` 的组装方式 (取哪些输入), 提示类别 (预检, 输出检查, 修复核对, 对 Agent 输出字段的核对), 以及提示交给哪个 Agent 节点核实. 题目模板加选项的哈希就是 11 所说的 "题目模板版本". 结果只有 "提示" 与 "不提示": 判断模型未配置, 该类提示未按 11 启用, 调用失败或低于阈值时一律为 "不提示". 需要语义判断才能决定走向的分支 (分流, 是否需要用户决定, 是否需要关卡) 不用判断节点, 写成正在干活的 Agent 节点输出 schema 中的必填分支字段; 前面没有可用 Agent 节点之处, 把边直接接到保守分支 (需要用户, 需要关卡).
- Agent 节点 (`agent`, 高智能步骤): 角色, 本步指令 (`rules[]`, 只含本步需要的方法), 输入收集 (Engine 要收集的路径与摘要), 输出 schema, 工作键 (07: 同一工作键的节点沿用同一会话, 如 Reviewer 一项审核的各轮), 时间预算 (超出后按 07 先问用户, 不中断). Agent 步骤宜粗 (07 Flow state 节): 只在冻结, 门禁, Git 写入, 等用户处切分, 一段连续的 Agent 工作写成一个节点. 选模型不由节点自选: 节点带默认档位和允许范围, 实际模型和推理强度由 07 的两段选择给出. 结果是输出 schema 中的分支字段, 本步要回答的语义判断题都作为必填分支字段, 由会话在本步一并作答, 不另开请求. 每个 schema 另含 "提议改 spec" 一项, 对应 07 的共同决定 (处置步骤加独立会话). 实施类 Agent 节点 (worker 实施一个授权 issue 的步骤) 的输出 schema 另含 `criteria` 必填字段: 授权 issue 的每条验收标准一项, 写明标准编号, 是否满足 (`met` 或 `unmet`) 和一句依据 (验证命令或观察位置); 缺任一条即输出不合格, 由 Engine 在收到输出时按 issue 的验收条目数核对条数, 不合格时让会话补全. 09 第 1 步的验收勾选就取自这个字段 (Engine 只写入, 不判断标准是否满足, D24).
- 问用户 (Agent 节点的共同能力): 每个 Agent 节点都可以在输出中选 `ask-user` 并附问题, 对应 07 的 "流程定义没有覆盖的情况一律转为等待用户". Engine 代办: 生成待答事项 (07), 先按 23 匹配常设裁决, 用户答复后把答复交回同一会话, 回到同一节点继续本步. 只有用户选择停止时节点得到结果 `ask-user:stop`, 这一条要连边; 其余情形不连边, 所以试转换少了 7 个样板问用户节点. Reviewer 与其他 Agent 一样可以问用户 (用户 11-13 的 "Agent 一视同仁", Main Agent 定), 取代现行 `docs/agents/reviewer.md` 中 Reviewer 不与用户沟通的规定; Reviewer 仍不向作者会话索取信息. 问用户经 Engine, 不经 harness 原生的用户输入请求.
- 交给用户的文字 (用户 11-14 "规则细节在输出时失效", 原话见 Comments): 表达与交互规则 (问用户的写法, 报告格式, 术语解释, 语言) 不改结果, 只在 Agent 写给用户的那一刻起作用, 写在会话开头读入的常读规则里, 到输出时已隔了整段工作, 容易被遗忘. 所以凡是 Agent 交给用户的内容都是输出 schema 中的结构化字段, 不靠会话记住规则:
  - `ask-user` 的必填字段 (取代 `grilling` 的书写格式与 "每个问题要自成一体" 一段, 以及各处 "向用户说明 X 并请求决定" 的写法): `questions[]` 一次列出本步全部要问的问题. 每个问题有 `kind` (`decision` 要用户选择, `action` 要用户动手做一件事, `info` 要用户提供 Agent 查不到的事实, `confirm` 要用户确认 Agent 对其原话的理解), `title` (问题本身, 用用户的说法, 不含内部编号; `decision` 由 Engine 在其后附上推荐项, 用户读完标题就能答), `situation` (只写读者答题缺的那一点, 一到两句: 从用户上次看到或决定的地方讲起, 现在哪里不对或有什么新情况; 与用户记得的可能不同时说明变了什么; 各选项共有的事实写在这里), `whyUser` (为什么要用户定: Agent 为什么不能自己决定或查明, 为什么现在必须定; 要调整已确认的要求时写明该要求. 这是给 Agent 的门槛, 写不出就不该问; Engine 默认不显示, 只在 `showWhy` 为真时显示, Agent 在理由对用户不显而易见时 (如要放宽数据约定, 要用户花钱, 要对外发布) 设它), `terms[]` (用户以后还会碰到的术语, 每项一句普通说法的解释, 可以为空; 其余术语与编号直接换成普通说法). `decision` 另有至少两个 `options[]` (每项 `label` 与 `meaning`: 选了之后用户得到, 看到或付出什么, 不写怎么实现) 和 `recommendation` (推荐项, 必填; `reason` 可选, 选项已显示出理由时不写); `action` 另有 `steps` (用户要做什么, 命令原样给出) 与 `doneSignal` (做完怎样告诉 Engine, 成功是什么样子), 取代根 `AGENTS.md` 中 "先告知用户并结束当前回复" 一条; `confirm` 另有 `quote` (用户原话的关键几个字), `reading` (Agent 的理解, 一到两句) 与 `ifWrong` (理解不对时会做得不一样的地方), 答复是 "对" 或 "不对" 加用户的说明, 可以与同一批的 `decision` 问题并列. 缺字段或 `decision` 少于两个选项按 07 的 "输出不符 schema" 重答, 仍缺时照样展示并记录 (07 的 Failures 节).
  - Engine 按字段渲染待答事项: 标题加推荐, 缺的背景, 选项及其结果, 一键 "按推荐" (取代 "回答 '是' 即表示接受推荐" 的措辞要求), 术语解释; `whyUser` 只在 `showWhy` 为真时显示; 用户答复前实例不前进, 只有用户明确的选择才算答复 (07). 渲染后的字数由 07 记录, 不作为退回条件.
  - 报告字段: 流程结束或停下时要交给用户的 Agent 节点 (如实施类节点) 的输出 schema 含 `report`: `summary` (结论, 偏离与遗留; 实施类节点的无关删除在此单列) 与 `unconfirmed[]` (推断和未核实的事项, 与有证据的事实分开; 取代根 `AGENTS.md` 中 "向用户汇报时区分有证据的事实, 推断和未确认事项" 一条). 可由 Engine 从状态生成的内容由 Engine 生成或原样转交, 不由 Agent 转述: 审查范围说明, 按轴的 Reviewer 报告, JIRA 授权前要展示的路径与评论, Reviewer 超时与早退时的状态与询问 (现行 `code-review`, `application-workflow`, `reviewer-launch` 中的相应段落).
  - 字段说明就是本步短指令: 上述字段在 schema 中的说明 (description) 写明各自的要求, 每项一句, 合计约 0.4K 字符, 是管理层 `_shared.jsonl` 中的参数, 随 graph 发布, 改措辞就是改 graph. 理由: 模型生成某个字段时读到的正是该字段的说明, 离输出最近. Engine 组装含这些字段的 Agent 节点消息时, 另在消息末尾 (紧挨输出要求) 附一行约 60 字符的提醒; 这些规则不再放在常读规则中 (21 的 Expression and interaction rules 节).
  - 交给用户前的机械检查与退回改写一次见 07 的 Before text reaches the user 节; 对话入口中的自由回复见 [确定 Engine 对话入口的形态](19-decide-conversation-entry-form.md). 对话会话的自由回复不是 schema 字段 (用户 11-14 D29): 回复边生成边经 07 的会话事件流显示, 结束后才检查, 命中时改写版经 "回复替换" 事件替换原回复, 原回复保留可展开; 其余交给用户的字段在检查与改写之后才交给入口.
- 等待用户节点 (`wait-user`): 流程本身设定的停机点 (授权, 确认, run 或 skip 的选择), 含问题模板, 选项, 背景来源, 以及是否接受常设裁决 (23). 问题模板用与 `ask-user` 相同的字段 (`title`, `situation`, `whyUser`, 每个选项的 `meaning`, `terms`), 可以代入实例状态, 由 Engine 渲染; 迁移时现行规则中 "向用户展示..." 一类段落转成这些字段, 不转成 `rules[]`. 结果是用户所选项.
- 调用节点 (`call`): 调用另一个子流程, 结果是被调子流程的返回值.
- 并行节点 (`parallel`, 07 的分支): 同时执行几个分支, 全部结束后汇合. `branches` 列出本子流程中的分支节点, 或用 `forEach` 对实例状态中的一个列表逐项运行同一个分支节点; 分支节点没有 `next`, 可以是 `call` 节点以运行整个子流程. 各分支的结果值与写入的状态键按分支 (逐项时按项) 存入实例状态, 并行节点只有一个结果值 `joined`, 由后面的节点 (通常是程序节点) 汇总. 试转换的 `audit-round` 已用这种形式, `check.py` 已校验分支节点没有 `next`. 同一工作键的分支共用一个会话, 回合只能逐个执行, 要真正并行就给各分支不同的工作键.
- 启动节点 (`spawn`, 07 的启动独立实例): 以实例状态中的值为输入, 启动另一个顶层工作流的新实例, 启动方不等待. 唯一结果值 `started`, 新实例 ID 写入状态, 只用于显示与来源记录; 没有等待它的节点, 要结果就用 `call` 或 `parallel`.

前四类对应 07 的四类步骤 (确定性操作, 判断, Agent 步骤, 等待用户), 调用, 并行与启动节点分别是 07 的栈, 分支与启动独立实例的表示.

节点属性 (由 graph 给出, Engine 机械使用):

- 写入: 只读, 只写实例的 `.tmp` 工作区, 或写工作区中的路径范围; 以及会写哪些仓库 (多仓库怎样取令牌留到 Application 工作流再定, 见 10). Agent 节点的权限策略由此得出, 即 07 中 Engine 对批准请求的应答.
- 正式关卡: 09 的关卡结论只来自 Reviewer 角色的 Agent 节点, 产生关卡结论的节点标为正式关卡.
- 是否产生验证事实 (10).

迁移后节点不带源锚点 (源映射已删除). 计量不是属性: Engine 对每个节点都记起止时间, 高智能请求数与 token (09 的 Interfaces), 规则与流程在上下文中的占比可以直接从 Engine 组装的消息中算出.

边: 节点 `next` 中的一项, 即 (源节点, 结果值) 到目标. 每个节点的每个可能结果值恰好有一条边: 程序节点的结果值来自原语目录, 判断节点是 "提示" 与 "不提示", 等待用户节点来自选项, Agent 节点来自输出 schema 的分支字段 (加 `ask-user:stop`), 调用节点来自被调方的 `returns`, 并行节点是 `joined`, 启动节点是 `started`. 唯一的例外是分支节点: 它没有 `next`, 结果值存入状态, 由并行节点汇合. 没有默认边, 边上也不写条件表达式; 循环上限等条件用程序节点 (如轮次计数原语) 产生结果值来表达, 所以 Engine 不需要表达式语言. 运行故障 (harness 退出, 输出不符 schema) 不是结果值, 按 07 的失败合同处理, 不出现在 graph 中; 判断模型不可用不是故障, 判断节点的结果为 "不提示" (16). 判断节点的 "提示" 边只通向核实它的 Agent 节点, 判断模型的结论不直接驱动其他走向 (08, D24).

试转换留下, 本格式尚未表达, 留给规范正文: 对集合逐项的判断 (每项要走一个子流程时可用 `parallel` 的 `forEach`; 一个 Agent 步骤内对多项分别作答的输出形式仍未定), 多入口节点的进入原因, 分支的优先次序, 步骤中途的事件 (如 "审核中先处置"). 并行节点与用户 11-13 提出的多个 graph 同时执行, 从一个 graph 中途启动另一个 graph 已由上面的 `parallel`, `spawn` 与 07 的 Stacked and parallel flows 节, Coexisting instances 节表达 (11-14).

### Layers

用户 11-14: 台账也改为 graph 形式, 所有数据一个格式, 一种应用方式; ARW managed 部分不可变, repository owned 部分叠加在上面, 可变 (原话见 Comments). 合上 D27 (仓库与本机的规则与流程调整记在发布的 graph 之上, 升级 ARW 时不合并; 整个仓库适用的纳入 Git, 本机适用的放在仓库内被 Git 排除的目录), graph 分三层, Engine 按仓库合并后执行:

- 管理层: 随 Engine 发布的 graph. 安装方不可改; 只在 ARW 源码仓库中改 (Source checkout graphs 节).
- 仓库层: 仓库内一个受 Git 跟踪的目录中的文件, 对该仓库的所有克隆生效.
- 本机层: 仓库内一个被 Git 排除的目录中的文件, 只对本克隆生效. 不放在 `.tmp/`, 因为 `.tmp/` 可以随时清空; 该目录与 `.tmp/` 一样由 Engine 写进受跟踪的 `.gitignore` (用户 11-14 D28, 选 B: 让用户看得见, 不用 `.git/info/exclude` 一类隐式方式), 写入前用 `git check-ignore` 核对, 没被忽略时 Engine 不写本机层文件; 写入时机, 核对, 缺失时的处置见 [确定判断模型与兼容端点的安装与配置](20-decide-installation-and-configuration.md) 的 Repository ignore rules 节 (写入后归仓库所有, `workflow remove` 不撤). Engine 进程原子写入该目录 (写临时文件再改名), 会话不直接写它, 改动经命令行工具 (10). 两个目录的名称留给规范正文.

上层文件与管理层同一格式 (JSONL, 每行一条自足记录, 键按固定顺序), 由同一读取, 校验与命令行工具处理. 上层只有四种记录:

- 新子流程或新顶层工作流: 与管理层同样的文件 (头加节点). 名称带层前缀 (如 `repo.`, `local.`), 不与管理层现在或以后的名称相撞.
- 新节点: 加进下层某个子流程的节点, 写明所在子流程, id 带层前缀; 只能经补丁改边进入.
- 补丁 (`patch`): 指向一个下层节点全名, 只能改 `next` 中个别结果值的去向 (目标可以是该子流程的新节点或 `return:`), 或给 Agent 节点的 `rules[]` 追加条目; 子流程头中只有 `entry` 可以改.
- 预置答案 (`answer`, 即原裁决台账, 字段与用法见 23): 对一个等待用户节点或 Agent 节点的问用户, 按节点加情况键记下用户选的答案.

上层不能改的, 也就是保护下层 `guarantees` 与静态校验的边界: 子流程头 (`entry` 除外), 节点的类型, 原语与参数, 角色, 输出 schema 与结果值, 正式关卡与写入属性, 是否接受常设裁决; 不能删除下层节点 (改边绕过可以, 只要合并后的校验仍通过); 不能改参数值, 参数的仓库值与用户值按 21 的决定 B 在配置中, 不设第二个来源.

每条补丁与预置答案带 `base`: 写入时目标节点在下面各层合并后的内容哈希 (按固定键序的一行计算), 以及写入时的 ARW 版本. 本机层可以引用仓库层, 仓库层不能引用本机层 (其他克隆没有); 同一节点的同一项两层都改时以本机层为准.

合并后的校验 (Verification 节第 1 层的全部检查在合并结果上运行): 下层声明的 `guarantees` 与原语的前置要求照样核对, 所以改边绕过正式关卡或提交前的必经边会被拦住. 另加: 上层记录只引用存在的节点与本层或更下层的名称; 预置答案的答案是节点现有选项之一, 节点没有标为不接受常设裁决; 把每个常设的预置答案当作该节点唯一的出边时, 每个环仍有离开环的结果值 (否则一个常设的 "再修一轮" 会造成死循环). 被改边绕过而不可达的下层节点只列出, 不报错. 校验时机:

- Engine 打开仓库, 启动, 升级, 以及仓库层在 `HEAD` 中或本机层文件发生变化时, 结果按合并内容的哈希缓存. 失败时该仓库不启动新实例, 列出出错的记录和修复提示, 用命令行工具修上层记录; 运行中的实例按已绑定的版本继续.
- Engine 写上层记录前 (如记下常设答案): 写入后的合并结果不合法就拒绝. 命令行工具的多步改写按 Graph command-line tool 节, 中间状态可以不合法, 提交时核对.
- 采用方改动仓库层的提交: 作为提交流程第 1 步的确定性检查 (09), 审核包附受影响子流程的路径摘要.

ARW 升级后的检出: 合并时 Engine 重算每条补丁与预置答案的目标节点哈希, 与 `base` 不等或目标已不存在即为过期. 过期记录不生效, 也不静默丢弃: 过期的预置答案等于没有, 照常问用户; 实例到达带过期补丁的节点时转为等待用户, 选项为按新节点重新确认 (更新 `base`), 删除该记录, 或停止实例. Engine 打开升级后的仓库时把全部过期记录合成一项待答事项, 列出每条记录和节点的当前内容, 用户可以开工前一次复核. 记录的 ARW 版本高于本机所装版本 (团队成员版本不同) 时, 提示升级 ARW, 不要求复核. ARW 改名或删除节点同样表现为过期, 所以管理层节点全名与上层记录格式成为公开 Interface: 节点改名与删除写进发布说明, 上层记录格式的不兼容变化按 13 的版本闸门经 `workflow update` 迁移.

理由与代价:

- 升级不合并: 管理层整体替换, 上层原样保留, 只按哈希检出受影响的记录, 不做文本合并 (D27).
- 一种应用方式: 原裁决台账的常设裁决, 采用方的流程调整和 ARW 源码仓库专用的流程都是上层记录, 同一套加载, 合并, 校验, 绑定与工具; 台账不再有自己的格式与检查.
- 安全不变式 (提交前须过正式关卡等) 由下层 `guarantees` 与原语前置要求在合并结果上机械核对. 上层改边的接线对不对 (互换结果值一类) 静态校验拦不住, 与管理层一样靠审核中的路径摘要; ARW 为管理层与自身仓库层写分支测试, 不要求采用方为自己的上层写.
- 代价: 管理层节点全名和上层记录格式要承担兼容责任 (原先不开放的理由); ARW 每次改到被采用方补丁的节点, 采用方都要复核一次.

### Engine execution

- 加载: 管理层随 Engine 安装; 每个仓库另加载仓库层 (取实例启动时 `HEAD` 中的版本, 不读工作树, 所以写入链尚未提交的 graph 改动不会被其他实例执行, 见 07 的 Coexisting instances 节) 和本机层, 按 Layers 节合并. Engine 启动时校验管理层, 打开仓库时校验合并结果 (Verification 节第 1 层与 Layers 节), 管理层失败即不开工, 合并失败按 Layers 节处理; 正常情况下管理层的错误在源码仓库检查中已被拦住.
- 绑定: 实例记录工作流名与三层合并后该工作流全部记录的内容哈希, 即 07 "实例绑定启动时的流程定义版本" 的具体化; 唯一例外是预置答案, 每次使用时读当时的记录 (23, 07 的共享状态可见性). Engine 升级后保留正在运行的实例所用的旧 graph 直到实例结束, 等待中的实例按 07 在新版本中找同名节点继续.
- 解释执行: 取当前节点, 按类型执行 (程序节点调用原语; 判断节点在判断模型配置了且该类提示已启用时按 16 提题, 否则直接得 "不提示"; Agent 节点按 07 组装消息, 代入参数, 附上本节点的常设预置答案 (23), 启动或继续会话, 输出 `ask-user` 时代办问用户后回到同一节点; 等待用户节点按 07 展示待答事项; 调用节点压栈; 并行节点按 07 为每个分支建子实例, 全部结束后得 `joined`; 启动节点按 07 新建顶层实例), 得到结果值, 按 07 先持久化步骤记录, 再沿边进入下一节点.
- 解释器不含任何工作流知识; 与具体工作流有关的机械逻辑只在原语中, 顺序与分支只在 graph 中.

### Verification

验证只留两层机械检查加常规审核 (D26): 原方案的段落哈希过期检查, 增量转换, 变异检查和 "夹具由另一会话, 另一模型编写" 删除; 历史回放随之删除, 规则与流程误判改按每天观察 codex 真实工作统计 (D25). 迁移时和以后每次改 graph 都过以下各项.

1. 静态校验 (与 Engine 加载时是同一段代码, 也在源码仓库检查中运行):
   - 单个子流程: 记录合法; 每个节点有 `desc`; 每个结果值恰好一条边; 每个节点从入口可达, 且能到达某个返回值 (每个环至少有一个离开环的结果值); Agent 节点有 `rules[]` 与输出 schema; 等待用户节点的问题模板有非空的 `title`, `situation`, `whyUser` 和每个选项的 `meaning`; 判断节点的 "提示" 边只通向 Agent 节点; 正式关卡的结论来自 Reviewer 角色的 Agent 节点.
   - 跨文件: `call` 的目标存在; 调用节点的 `next` 键恰好等于被调方的 `returns`; 每个声明的返回值都有路径到达; 调用图无环; 每个子流程都能从某个顶层流程到达; 引用的原语, 参数与工作键存在, 程序节点的 `next` 键等于原语的结果值; 上层只引用下层与本层, 仓库层不引用本机层 (Layers 节, 合并后另加的检查也在那里). 并行与启动 (07 的分支与启动独立实例): 分支节点只被并行节点引用, 不被任何边指向; 分支 (连同它调用的子流程) 中没有 Git 写入原语, 各分支写入的状态键与写入范围互不相交 (`forEach` 按项存放, 不算相交); `spawn` 的目标是顶层工作流, 输入覆盖其 `reads`; 调用图无环的检查把 `spawn` 也算作边, 以免实例无限地自我启动.
   - 必经边: 子流程头的 `guarantees` 为每个返回值列出必经的边 (`<节点全名>:<结果值>`, 如冻结成功, 正式关卡得到 `No problems.`). 校验从入口到该返回值的每条路径都经过所列的边, 经过 `call` 节点时以被调方对该返回值的 `guarantees` 计入. 原语可以声明前置要求 (如提交原语要求本实例已经过实施提交的正式关卡并通过), 校验到达调用它的节点的每条路径都满足. 这取代原来 "提交之前有固定候选与正式关卡" 一条, 并能跨层核对; 试转换中没有它时, 跨层要求只能退化成 "调用了含该类节点的子流程".
   - [定义裁决台账与规则一致性检查](23-define-ruling-ledger-and-rule-consistency.md) 的一致性检查 (数据依赖循环用 `reads` 与 `writes`, 文档引用闭包, 节点能力对文档禁令, 台账, 停机点清单) 是本层的扩展.
   - 出错时给出修复提示: 尤其子流程头的 `returns`, 调用节点的 `next` 和原语的结果值三处不一致时 (读改实测: 加一个分支要同步改这三处), 指出缺哪个键, 在哪个文件哪一行.
   - 局限: 静态校验只管形状. 试转换把同一节点两条边的目标互换, 164 个变体静态校验拦住 0 个, 加上必经边要求也只拦住 4 个; 漏掉的包括危险接错, 如 `implementation-commit/close` 的 `committed` 与 `needs-round` 互换. 接线是否正确靠第 2 层.
2. 分支测试 (23 称分支夹具): 每个分支条件至少一条正例和一条反例, 每条必经边至少一个必过场景. 测试以 mock 的原语结果, 判断答案, Agent 输出和用户答复驱动 graph 解释器, 断言经过的节点序列与关键状态; 它们是 ARW 测试套件中的普通测试, 不起真进程. 试转换估计每个流程约 60 到 100 个场景. graph 与相应测试在同一提交中改动; 写测试的可以是改 graph 的同一会话. 分支测试覆盖管理层与 ARW 源码仓库的仓库层; 采用方的上层不要求分支测试 (Layers 节).
3. 审核: graph 改动与其他实施提交一样走 Spec Readiness 与 Commit Audit, 不新增 Reviewer 角色或关卡. 审核包 (09) 附上受影响子流程改动前后的路径摘要 (命令行工具生成), 互换结果值这类在 graph 中形状合法的错误在路径摘要里可见; requirements-reviewer 对照授权 issue 核对 graph 与路径摘要的差异, code-standards-reviewer 审新原语与测试. 采用方改动仓库层的提交同样附路径摘要.

### Changing flows after migration

- 改流程直接改 graph (D26), 用下节的命令行工具; 同一提交改相应的分支测试; 源码仓库检查运行静态校验与测试. 采用方改自己的流程只写本仓库的仓库层或本机层, 不改管理层 (Layers 节).
- 给人看的流程说明由 graph 生成: 每个工作流一份 Markdown (各层子流程的说明, 输入与输出, 路径摘要), 不手改; 源码仓库检查像现有 `scripts/generate-install-arw.mjs --check` 一样重新生成后比较, 过期即失败. 手册中逐步描述流程的段落改为链接生成的说明. 交互式查看见 [设计给人看的 graph 查看界面](24-design-graph-viewer.md).
- 判断节点的题目模板或选项变化时, 其哈希随之变化, 11 规定的 "该类提示停到新版本通过离线评测为止" 由此自动触发.
- 管理层随 Engine 版本发布, 上层随所在仓库或克隆; 已在运行的实例按 Engine execution 节的绑定处理.

### Graph command-line tool

用户 11-13: graph 大而复杂时, 先出几个脚本来搜索和改写 graph, 就像现在阅读和改写状态页那样. 读改实测显示 agent 读改 graph 多花的时间主要在跨文件追路径和多处同步修改, 正是这类工具能省掉的, 所以首版就带, 不等 graph 变大.

- 查询: 按节点全名显示一条记录, 连同调用它或指向它的位置; 按 id, 关键词, 原语名或参数名查节点 (如列出引用某个参数的全部指令与原语); 列子流程的路径摘要, 即入口到每个返回值的节点与结果值序列, 经过 `call` 时可展开一层; 列子流程的调用方.
- 改写: 改边; 加删节点 (删除仍被引用的节点时列出引用并拒绝, 或按选项连同引用一起改); 改名 (节点或子流程), 同步全部引用 (`next` 目标, `call` 目标, `guarantees`, 分支测试中的节点全名, 同一仓库中引用它的上层记录; 采用方的上层记录不在 ARW 源码仓库中, 改名后在采用方表现为过期, 见 Layers 节); 加删返回值时同步子流程头与各调用节点的 `next`; 改参数值.
- 每次改写后自动运行静态校验, 输出结果与修复提示. 多步改动的中间状态可以不合法, 提交前的源码仓库检查必须通过.
- agent 读改 graph 时优先用这个工具, 不直接手改 JSONL; 这一条写进改 graph 步骤的本步指令.
- 11-14 起采用方也要改自己的上层, 所以它随 Engine 分发, 是公开的 `arw` 命令: 查询, 路径摘要与校验作用于当前仓库的合并结果; 改写在 ARW 源码仓库中可写管理层与仓库层, 在其他仓库只写仓库层与本机层; 另有上层记录的子命令 (按节点列预置答案与补丁, 列过期记录并重新确认 `base` 或删除, 撤销预置答案). 读取, 路径摘要与校验代码和 Engine 加载, 查看界面共用.
