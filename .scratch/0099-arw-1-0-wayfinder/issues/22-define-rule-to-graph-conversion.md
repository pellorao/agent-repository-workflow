## Answer

11-13 worker 分析, 交 Main Agent 综合. 依据: 用户 11-13 的原话 (见 Comments), 07 的步骤四类与实例状态, [定义分流判断的复核与回退合同](08-define-routing-review-and-rollback.md) (11-14 按 D24 改: 判断只做提示, 语义判断是 Agent 输出 schema 的必填字段), [定义 Reviewer 与正式关卡在 Engine 下的执行协议](09-define-reviewer-protocol.md) 与 [定义并行流程的读取与写入隔离](10-define-parallel-flow-isolation.md) 的 Interfaces 中已写下的 graph 节点属性, 13 的规则归类, [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md) 的题型, [定义 Jev 类模型的评测与转正条件](11-define-evaluation-and-graduation.md) 的题目模板版本, [本地 Jev 类候选的可行性小实验](15-task-local-candidate-feasibility.md) 11-13 Comments 中的四项目标与估算, 以及 ARW HEAD `78aa110` 的 `scripts/generate-install-arw.mjs --check` (派生文件过期检查的现有做法). 三处方向性取舍已由用户 11-13 (D20) 按建议确认, 选项与答复见 Comments.

### Goals served

- 高智能请求数与墙钟: 现行 worker 请求中规则流程类 (读规则, 关卡命令, 写记录, 决定下一步) 约占 63% (15 的 11-13 Comments, 元数据统计); 这些由 graph 的程序节点和 Agent 节点输出 schema 中的分支字段承担, 估算的节省主要来自这里.
- Agent 上下文中规则与流程的占比: Agent 步骤只收到本步短指令, 转换范围内的规则原文不进入任何会话.
- 规则与流程上的误判率: 顺序, 门禁和跳过条件由程序执行, 不受会话压缩影响; 剩下的语义判断都是有 ID 的 Agent 节点中的分支字段, 误判可以按节点与字段统计.
- 代价: 转换错了每次都错, 是系统性错误. 所以下文的验证是本机制的必需部分, 不是可选项.

### Conversion inputs and outputs

转换只在 ARW 源码仓库中进行 (用户 11-13 确认, D20): 维护者让高智能模型按一个 Source Checkout Skill (暂名 `rule-graph`, 不分发) 转换, 产物随 Engine 发布. 已采用的仓库不运行转换; 仓库自有规则按 13 仍是文本, 由 harness 原生加载.

输入:

- 规则源: 转换范围内的规则正文. 哪些文件和段落属于转换范围由 21 逐份确定.
- 当前 graph 与源映射 (增量转换时).
- 原语目录: Engine 代码中可供程序节点调用的操作, 每项有名称, 参数与结果 schema 和全部可能的结果值. 目录由 Engine 代码导出, 不手写.
- 节点合同: 本 issue 的 Graph shape 节, 以及 07, 08, 09, 10, 16 定下的约束 (步骤类型, 题型, 判断只做提示, 正式关卡, 写入属性). 写在 Skill 中.

输出 (与规则改动在同一提交):

- 每个工作流一份 graph 文件: JSON, 键和数组按固定顺序写出, 使 `git diff` 可读.
- 源映射: 转换范围内每个规范段落的去向 (对应哪些节点或边, 进入哪个 Agent 节点的本步短指令, 或删除及理由) 和该段落的内容哈希.
- 新原语: 规则需要原语目录之外的机械操作时, 转换者在 Engine 代码中编写该原语及其单元测试. 这就是用户所说 "机械程序由高智能模型编写" 的落点.

分支夹具不是转换者的输出, 由另一个会话编写, 见 Verification 节.

### Graph shape

graph 是有向图, 允许环 (修复循环, 审核轮次). graph 本身是声明式数据, 不含代码 (用户 11-13 确认, D20). 顶层有: 名称, 内容哈希 (即版本), 入口节点, 参数 (取自 Repository Profile 或用户配置的值, 如仓库的测试命令), 节点表, 边表.

节点类型:

- 程序节点 (机械步骤): 调用一个原语, 参数是常量, graph 参数, 实例状态字段或前面节点的结果. 结果是原语声明的一个结果值加数据. 例: 冻结审核候选, 运行确定性检查, 切出预检单元, 轮次计数, 暂存与提交.
- 判断节点 (可选的判断模型提示, D24): 一道 `choice` 或 `noul` 题, 含题目模板, 选项, `state` 的组装方式 (取哪些输入), 提示类别 (预检, 输出检查, 修复核对, 对 Agent 输出字段的核对), 以及提示交给哪个 Agent 节点核实. 题目模板加选项的哈希就是 11 所说的 "题目模板版本". 结果只有 "提示" 与 "不提示": 判断模型未配置, 该类提示未按 11 启用, 调用失败或低于阈值时一律为 "不提示". 需要语义判断才能决定走向的分支 (分流, 是否需要用户决定, 是否需要关卡) 不用判断节点, 写成正在干活的 Agent 节点输出 schema 中的必填分支字段 (见下一条); 前面没有可用 Agent 节点之处, 转换者把边直接接到保守分支 (需要用户, 需要关卡).
- Agent 节点 (高智能步骤): 角色, 本步短指令 (转换者从规则正文中只取本步需要的方法写成), 输入收集 (Engine 要收集的路径与摘要), 输出 schema, 会话策略 (复用本实例该角色的会话, 或按 09 新建, 如 Reviewer), 时间预算 (超出后按 07 先问用户, 不中断). Agent 步骤宜粗 (07 Flow state 节): 转换者只在冻结, 门禁, Git 写入, 等用户处切分, 把一段连续的 Agent 工作写成一个节点. 选模型不由节点自选: 节点带默认档位和允许范围, 实际模型和推理强度由 07 的两段选择 (概要参数加机械映射表) 给出. 结果是输出 schema 中的分支字段, 本步要回答的语义判断题都作为必填分支字段写在这里, 由会话在本步一并作答, 不另开请求; 每个 schema 都含 "交用户" 一项, 对应 07 的 "流程定义没有覆盖的情况一律转为等待用户", 另含 "提议改 spec" 一项, 对应 07 的共同决定 (处置步骤加独立会话).
- 等待用户节点: 问题模板, 选项, 背景来源. 结果是用户所选项.
- 子流程节点: 调用另一个 graph, 按 07 的栈执行, 结果是子 graph 的终止结果.
- 终止节点: 实例结束, 带终止结果 (如 `done`, `cancelled`).

前五类对应 07 的四类步骤, 子流程是 07 的栈的表示.

节点属性 (由转换给出, Engine 机械使用):

- 写入: 只读, 只写实例的 `.tmp` 工作区, 或写工作区中的路径范围; 以及会写哪些仓库 (多仓库怎样取令牌留到 Application 工作流再定, 见 10). Agent 节点的权限策略由此得出, 即 07 中 Engine 对批准请求的应答.
- 正式关卡: 09 的关卡结论只来自 Reviewer 角色的 Agent 节点, 产生关卡结论的节点标为正式关卡.
- 是否产生验证事实 (10).
- 源锚点: 该节点来自规则源的哪些段落, 是源映射的反向索引, 供增量转换和审核使用.

计量不是属性: Engine 对每个节点都记起止时间, 高智能请求数与 token (09 的 Interfaces), 规则与流程在上下文中的占比可以直接从 Engine 组装的消息中算出.

边: 一条边是 (源节点, 结果值) 到目标节点. 每个节点的每个可能结果值恰好有一条边: 程序节点的结果值来自原语目录, 判断节点是 "提示" 与 "不提示", 等待用户节点来自选项, Agent 节点来自输出 schema 的分支字段. 没有默认边, 边上也不写条件表达式; 循环上限等条件用程序节点 (如轮次计数原语) 产生结果值来表达, 所以 Engine 不需要表达式语言. 运行故障 (harness 退出, 输出不符 schema) 不是结果值, 按 07 的失败合同处理, 不出现在 graph 中; 判断模型不可用不是故障, 判断节点的结果为 "不提示" (16).

判断节点的 "提示" 边只通向核实它的 Agent 节点, 判断模型的结论不直接驱动其他走向 (08, D24).

### Engine execution

- 加载: graph 文件随 Engine 安装. Engine 启动时对全部 graph 做静态校验 (Verification 节第 1 层), 失败即不开工并报告; 正常情况下这在源码仓库检查中已被拦住.
- 绑定: 实例记录 graph 名与内容哈希, 即 07 "实例绑定启动时的流程定义版本" 的具体化. Engine 升级后保留正在运行的实例所用的旧 graph 直到实例结束, 等待中的实例按 07 在新版本中找同名节点继续.
- 解释执行: 取当前节点, 按类型执行 (程序节点调用原语, 判断节点在判断模型配置了且该类提示已启用时按 16 提题, 否则直接得 "不提示", Agent 节点按 07 组装消息并启动或继续会话, 等待用户节点按 07 展示待答事项, 子流程节点压栈), 得到结果值, 按 07 先持久化步骤记录, 再沿边进入下一节点.
- 解释器不含任何工作流知识; 与具体工作流有关的机械逻辑只在原语中, 顺序与分支只在 graph 中.

### Verification

每次转换都过以下各层, 全部通过才能提交:

1. 静态校验 (与 Engine 加载时是同一段代码, 也在源码仓库检查中运行): schema 合法; 每个结果值恰好一条边; 每个节点从入口可达, 且能到达终止节点 (每个环至少有一个离开环的结果值); 引用的原语, 子 graph 与参数存在且签名一致; 提交之前有固定候选与正式关卡; 判断节点的 "提示" 边只通向 Agent 节点; 正式关卡的结论来自 Reviewer 角色的 Agent 节点.
2. 源映射完整: 转换范围内每个规范段落都有去向, 且记录的哈希与当前规则源一致 (见下节).
3. 分支夹具: 规则源中的每个分支条件至少有一条正例和一条反例. 夹具由另一个会话只读规则源与原语目录编写, 不看 graph, 优先用与转换者不同的模型, 以免两边犯同样的错. 夹具以 mock 的原语结果, 判断答案, Agent 输出和用户答复驱动 graph 解释器, 断言经过的节点序列与关键状态; 它们是 ARW 测试套件中的普通测试, 不起真进程.
4. 变异检查: 自动对 graph 做小改动 (删一条边, 交换两个结果值的目标, 去掉提交前的正式关卡), 每个变异都必须使至少一个夹具或静态校验失败; 存活的变异说明夹具不足, 补夹具后重跑. 只在转换提交中运行, 不进日常测试.
5. 历史回放: 用 15 的误判基线实验中标注过的历史决策点, 把当时的输入交给 graph, 比较结果与正确动作. 1.0 验收时全量回放一次; 之后的规则改动只回放受影响 graph 的决策点.
6. 审核: 转换提交与其他实施提交一样走 Spec Readiness 与 Commit Audit, 不新增 Reviewer 角色或关卡. 授权 issue 的 What to build 写明规则源改了什么; requirements-reviewer 对照规则源的差异核对 graph, 源映射与本步短指令的差异, code-standards-reviewer 审新原语与夹具. 用户按实施 issue 复核整体 diff 的做法不变.

### Rule changes and consistency

规则源是唯一权威, graph 与源映射是派生物 (用户 11-13 确认, D20). 维护者只改规则源, 不手改 graph; 这与现有 `scripts/generate-install-arw.mjs --check` 对派生文件的做法相同, 区别是派生由模型而不是脚本完成, 所以一致性靠哈希检查而不是重新生成后比较.

- 过期检查 (确定性, 加入 Source Checkout 验证): 重算转换范围内每个规范段落的哈希并与源映射比较; 有段落新增, 删除或改动而 graph 没有重新转换时失败, 并列出这些段落.
- 增量重新转换: 按 Skill 只把变化的段落连同源锚点指向的节点交给转换者, 输出 graph 补丁, 新的源映射和需要的新原语; 夹具作者同时补改对应夹具; 然后跑 Verification 节各层 (回放只跑受影响的 graph). 规则, graph, 源映射与夹具在同一提交中改动, 所以任何提交上规则源与 graph 都一致.
- 只改措辞不改语义时, 转换者只更新源映射中的哈希, 仍经审核由 requirements-reviewer 确认没有语义变化.
- 判断节点的题目模板或选项变化时, 其哈希随之变化, 11 规定的 "该类提示停到新版本通过离线评测为止" 由此自动触发.
- graph 随 Engine 版本发布; 已在运行的实例按上节的绑定处理.

### Relation to 13 and 07

- Upstream Sync (用户 11-13 D21): 1.0 删除 Upstream Sync 流程, 21 已定稿. 以后上游有改动时开普通任务, 照上游改动修改我们的 Skill, 再按本 issue 的机制转换或生成 graph; 没有专门的同步流程, 转换也不为上游同步另设步骤.
