# 定义并行流程的读取与写入隔离

Type: grilling
Status: resolved
Blocked by: issue:0099:07, issue:0099:08

##### Question

多个 worker 的流程在同一仓库并行时, Engine 怎样给每个读取者一致的仓库视图, 并按单一写入者原则排列修改? 一个 worker 的投机动作被复核否定, 而另一个 worker 已在其后写入时, 哪些动作必须回退或重做, 怎样避免丢失已验证的工作? 临时目录不受单一写入者约束时, 边界在哪里?

## Answer

11-13 worker 分析, 交 Main Agent 综合. 依据: [定义 Engine 驱动流程的运行合同](07-define-engine-runtime-contract.md) (每仓库一个写入者令牌, 子实例继承, 会话一视同仁, Git 写入只由 Engine 执行), [定义分流判断的复核与回退合同](08-define-routing-review-and-rollback.md) (投机写入, 上限与屏障, 私有引用下的恢复快照, 回退只撤本实例的投机写入), [定义 Reviewer 与正式关卡在 Engine 下的执行协议](09-define-reviewer-protocol.md) (冻结候选, 按冻结输入机械判断失效), [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md) 的调用记录, 以及 ARW HEAD `8637e9c` 的 `docs/agents/agent-writes.md` (Issue concurrency 节), `docs/agents/environment.md`, `docs/agents/parallel-implementation.md`, `docs/agents/reviewer.md` (Review versions and concurrency 节), `lib/commit-audit/commit-audit.mjs` (Reviewer 只用 `git show <tree>:<path>` 读取受审版本) 和 `lib/spec-readiness/spec-readiness.mjs` (subject 身份是登记路径加内容摘要). 原问题中的 "worker" 按 07 的会话一视同仁理解为流程实例: 隔离按实例是否持有令牌区分, 不按会话角色区分.

### What the premises already settle

- 已跟踪内容 (含未被忽略的未跟踪文件, 下同) 在任何时刻只由一条写入链写入, 即持有令牌的实例连同其子实例栈. 08 中的 "本实例" 指这条写入链: 子实例的写入步骤位于父实例未复核判断之后的分支上, 按 08 的依赖定义同样依赖这些判断, 计入同一上限, 推翻时一并回退.
- 令牌只在提交后或停在无未提交修改的状态时释放 (07). 提交已是 08 的屏障; 本 issue 把释放令牌也列为屏障: 释放前, 写入链已执行的写入所依赖的判断须全部复核且未被推翻. 否则写入链可能先做投机写入又改回原样, 以干净状态交出令牌, 之后判断被推翻时, 回退会落到下一个持有者已写的文件上.
- 因此其他实例不可能在未复核的投机写入之上写已跟踪内容. 原问题中 "另一个实例已在其后写入" 只剩三种情形: 它读到了投机内容; 它在自己的临时工作区写了基于这些内容的产物; 它正等待令牌. 下面的视图规则使前两种不影响它的正式结果, 回退与重做只发生在写入链内部.

### Consistent views

Engine 中的视图一律是 Git 树对象或提交: 内容按对象 ID 固定, 不随工作区变化, 读取用 `git show <树>:<路径>`, 检索用 `git grep <模式> <树>`. 读取者分三类:

- 写入链的会话读工作区本身, 那就是写入链自己的当前内容. 测试, 检查等产生验证事实的确定性操作不与同一写入链的写入步骤在工作区中并行, 所以结果对应确定的内容; 需要并行时 (如 09 中审核进行期间的修复) 改在普通快照中运行, 见 Temporary directories 节.
- 其他实例 (含对话会话的自由对话, 它不属于任何写入链) 的正式依据是基准提交加本实例的草稿. 基准提交是该实例开始时的 `HEAD`, 落盘前不变, 使实例内各步看到同一内容; 它只含已提交内容, 而已提交内容都通过了屏障, 不会因推翻而回退. 工作区中可能有写入链未提交 (可能是投机) 的改动: Engine 在这类实例的每条 Agent 步骤消息中写明基准提交并列出工作区与它不同的路径, 要求读这些路径时用 `git show <基准提交>:<路径>`; 其余文件照常浏览.
- 冻结输入与判断按视图固定. 写入链的审核候选取自工作区 (冻结是屏障, 不含未复核内容); 其他实例的冻结输入由 Engine 用基准提交加草稿合成树对象. 09 保留的 "Spec Readiness Reviewer 只读检索工作树" 例外改为检索本轮视图的树, 以免读到其他实例的未提交改动. 判断的 `state` 含未提交内容时, Engine 在调用时把这些文件写成 Git 对象 (`git hash-object -w`), 调用记录的来源记对象 ID; 16 写的来源 "仓库提交与文件路径" 不能重建未提交内容, 由本条补全. 08 的盲答异步复核按这些对象 ID 重建 `state`, 不读复核时的工作区.

未采用: 为每个非持有实例检出一份 `HEAD` 副本作工作目录. 隔离最彻底, 但每个实例要多写一份仓库, 依赖目录 (如 `node_modules`) 不在副本中, 测试仍要另行准备, 而上面的做法已保证正式结果只建立在已提交内容上. 也未采用不加区分地读实时工作区: 草稿, 审核和判断可能建立在随后被回退的投机内容上.

### Write queue

- 排队: 一个全局队列按进入 `waiting-writer` 的时间排序. 请求在它要的全部仓库令牌都空闲, 且没有更早的等待请求需要其中任何一个仓库时获得令牌. 流程定义声明实例会写哪些仓库 (Application 工作流写 Application 与 Module 两类仓库), Engine 在第一个写入步骤前一次取得全部, 取不全就一个不占. 这样不会有两个实例各持一个仓库互等, 单仓库请求也不会一直插到多仓库请求前面. 首版不设优先级, 没有需要它的流程.
- 等待令牌时, 不写已跟踪内容的步骤照常推进: 研究, 分析, 起草 issue 或 spec, 对草稿运行判断与 Spec Readiness. 草稿写在实例临时工作区, 步骤输出标明它将落到的仓库路径.
- 落盘: 取得令牌后, Engine 比较基准提交与当前 `HEAD` 在本实例输入路径上的差异 (草稿目标路径, 冻结输入, 步骤消息给出的路径). 没有交集时直接把草稿写到目标路径, 作为本实例第一个写入步骤 (照 08 先建恢复快照). 有交集时, 已冻结结果按 09 的失效规则机械处理 (例如实施开始前 Spec Readiness 的 Input 变化使记录失效, 做增量复审), 再由一个 Agent 步骤拿着交集的 diff 核对并修改草稿, 然后落盘. 就绪记录绑定 issue 的登记路径与 subject 内容摘要, 不绑定内容当时所在的位置, 所以对草稿得出的就绪结论在逐字节落盘后仍然有效.
- 写入链内部可以同时运行多个写入步骤, 前提是流程定义给出的写入范围互不包含 (Engine 按路径包含关系检查), 与现行 `docs/agents/agent-writes.md` 的 Assign and hand off 节一致. 回退多个步骤时, 每个路径恢复为被回退步骤中最早覆盖它的那份恢复快照.
- 持有令牌的实例等待用户时继续持有令牌, 同仓库其他实例只能先做不写已跟踪内容的步骤 (用户 11-13 定, 理由见 Comments). Engine 记下每个实例处于 `waiting-writer` 的时长, 计入 [定义 Jev 类模型的评测与转正条件](11-define-evaluation-and-graduation.md) 的墙钟数据, 供以后判断是否值得改为让出令牌.

### Reversal across instances

写入链中的判断 J 被推翻时:

- 写入链照 08 回退与重做, 不涉及其他实例.
- 其他实例的已跟踪写入不存在, 见 What the premises already settle 节.
- 其他实例的正式结果 (冻结的审核轮, 判断, 就绪记录) 都建立在基准提交加草稿上, 不含 J 的投机内容, 不回退也不重做.
- 其他实例读过投机内容后写出的草稿不回退. 落盘时的差异比较会显出写入链最终提交的内容与它当时可能看到的不同; 投机内容被整体撤销而没有提交时比较不出, 但草稿落盘前后仍要经过它自己的审核与验证, 不会直接成为交付. Engine 不主动重做其他实例的步骤, 因为多数草稿与 J 无关, 自动重做会白花高智能请求.

不丢已验证的工作:

- 结果按输入内容复用: 每个步骤结果 (测试与检查, 只读 Agent 步骤, 判断, 审核轮) 记下输入的对象 ID, 重做后输入的对象 ID 不变就直接复用. 08 的 "只读步骤输入未变时复用" 与 09 的 "轴结果按冻结输入复用" 都是这条规则的特例.
- 被推翻的工作可取回: 08 在回退前把当前状态另存为快照. 重做的 Agent 步骤收到的更正消息附上该快照引用及其相对回退点的 diff, 会话可以挑出仍然成立的部分 (如新写的测试) 重新应用, 不必重写.
- 其他实例的草稿, 判断与审核结果不因写入链的推翻而作废, 只按输入比较判断是否仍有效.

### Temporary directories

- 位置: 每个实例一个临时工作区, 位于仓库 `.tmp/` 下, 路径由 Engine 生成并交给会话, 取代现行 `docs/agents/environment.md` 的按会话目录 `.tmp/<agent-platform>/<sessionId>/` (09 的就绪记录 `request.filePath` 已指向这里). 同一实例的会话 (含 Reviewer) 共用它; 每次步骤执行写在以执行编号命名的子目录中, 重做是新的执行, 写新目录, 被作废执行的产物不再被引用, 也不会被重做覆盖. 子实例有自己的工作区, 父实例的产物由 Engine 以路径传入.
- 不受约束: 临时工作区不受写入者令牌约束, 不进恢复快照, 不随推翻回退, 不进审核候选或提交. Engine 的全部 Git 操作 (快照, 冻结, 核对, 暂存) 都用路径排除 `.tmp/`, 不依赖目标仓库忽略它 (现行安装不为目标仓库添加这条忽略规则).
- 仍受约束: 会话只写本实例的工作区, Reviewer 只写绑定的报告. 每个步骤结束时, Engine 核对已跟踪内容的变化都落在写入链当前写入步骤的范围内; 范围外的变化无法归属任何步骤, 按 08 的 "不属于任何步骤的改动" 处理, 写入链在下一个屏障前停下交用户判断. 这也覆盖其他实例的会话越权写工作区的情形, 两个 harness 上无法事前阻止 (见 07).
- 被忽略的共享路径: 构建输出, 依赖目录, 测试缓存等被忽略且不在 `.tmp/` 下的路径不进快照 (08), 却会被并行运行的命令争用. 只有写入链在工作区中运行会写这类路径的命令 (构建, 测试, 安装依赖); 其他实例需要时在自己工作区的普通快照中运行 (沿用现行 `docs/agents/environment.md` 不用 `git worktree` 的规定), 或等到取得令牌. Engine 在步骤结束时删除它为该步创建的快照目录, 因为可以随时从树对象重建; 其余临时内容沿用现行不自动清理的规则.
- 仓库之外 (用户主目录, 全局缓存, harness 配置) 不在隔离范围内; 以改变它们为目的的步骤是 08 的 "作用到工作区以外的操作", 是屏障.
- 删除 `.tmp/`: 1.0 中实例状态与会话绑定都在 Engine 私有状态库 (07), `.tmp/` 只有中间产物, 删除不会使运行无法恢复. 现行 `docs/agents/parallel-implementation.md` 中删除 `.tmp` 前先卸载后台 Agent 的检查因此不再需要; 产物被删的实例在下一步按输入对象 ID 核对时发现缺失, 停下报告.

### Worktrees

`docs/agents/parallel-implementation.md` 的并行实施 (用户开启后每个 issue 一个 Git worktree, 再合并回主分支) 按 [确定现有 ARW 合同在 1.0 中的继承范围](13-decide-legacy-contracts.md) 并入本 issue. 1.0 不提供 (用户 11-13 定, 理由见 Comments). 07 定为每仓库一个令牌; 改为按工作树发令牌, 合并冲突, 合并后的完整验证, 跨工作树的视图与推翻都要另立规则. 本 issue 的草稿与落盘已让研究, 起草和 Spec Readiness 与实施并行, 剩下串行的只有实施与提交审核. 先用 `waiting-writer` 时长衡量串行造成的等待, 等待显著时再按数据决定是否加回.

### Scenarios

1. 草稿与就绪并行: 实例 A 持有令牌实施一个 issue. 用户发起下一个 issue 的规划, 实例 B 在临时工作区起草并对草稿跑完 Spec Readiness, 输入取 B 的基准提交. A 提交后 B 取得令牌; A 的提交只改了 `lib/`, 与 B 的输入无交集, Engine 直接落盘, 就绪记录有效, B 开始实施.
2. 落盘时有交集: 同上, 但 A 的提交改了 B 的 issue 所引用的 `spec.md`. B 的实施尚未开始, 就绪记录按 09 失效; B 的会话拿着该 diff 核对草稿, 落盘后做增量复审.
3. 推翻时其他实例读过投机内容: A 的判断 J 让 worker 改了 `lib/x.mjs`, B 此时在分析同一文件. B 的步骤消息列出 `lib/x.mjs` 有未提交改动, B 读基准提交中的版本. J 被推翻, A 照 08 回退重做; B 的分析和基于它的判断都建立在基准提交上, 不受影响.
4. 测试与修复并行: A 在审核进行期间按 09 继续修复, 同时要跑测试. Engine 用修复开始前的树在 A 的临时工作区建普通快照并在其中运行测试, 结果绑定该树, 修复写入工作区不影响它.
5. 越权写入: B 的会话误改了一个已跟踪文件. 步骤结束时 Engine 发现该变化不在 A 当前写入步骤的范围内, A 在下一个屏障前停下, 交用户判断这处改动的去留.

### Interfaces
