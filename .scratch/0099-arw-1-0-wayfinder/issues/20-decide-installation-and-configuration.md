# 确定判断模型与兼容端点的安装与配置

Type: grilling
Status: resolved
Blocked by: issue:0099:07, issue:0099:16, issue:0099:18

##### Question

判断模型是 Engine 的必需组件, 由开启脚本启动 (见 [确定本地判断模型服务的运行责任](18-decide-local-judge-server-ownership.md)). ARW 配置时怎样探测硬件, 怎样按本机, 机构内部, 公开部署的顺序选定判断模型; 推理运行时与模型文件由谁安装, 怎样固定版本; 开启脚本写什么, 依赖什么; 同一台机器上另有程序 (如 Strata) 占着显卡时怎样让它让出; Claude Code 或 Codex 升级后经兼容端点接入的本地或第三方模型失效时怎样应对?

## Answer

事实见 [判断模型与兼容端点的安装与配置: 事实核对](../research/install-and-config/report.md) (11-13), 其中有维护者本机部署 GLiDE-9B 的实测 (安装布局, 开启脚本, 防火墙, WSL 访问). 答案由 worker 分析, 交 Main Agent 综合; 四处方向性取舍已由用户 11-13 (D19) 按建议确认, 见 Comments. 11-14 按用户 D24 答复改写: 判断模型可选, 首版只需配置一个端点 (可不配); 本机安装, 显卡探测, Strata 让出, 防火墙与 WSL 放置移到 When a qualified local model exists 节, 首版不实现; 经过见 Comments.

### What the premises already settle

判断模型可选, 配了只做提示, 未配置或不可用时 Engine 照常工作且不出提示 (D24, 见 [确定本地判断模型服务的运行责任](18-decide-local-judge-server-ownership.md) 与 [定义分流判断的复核与回退合同](08-define-routing-review-and-rollback.md)); 首版按 18 的使用条件实际不配. Engine 在进程内调用 `/v1/systemone`, 配置在 ARW 用户级配置的独立一节, 调用失败时该题不提示 (见 [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md)). 本答案定首版的端点配置, 并保留有合格模型时的本机部署做法; Engine 自启与对话入口的网络放行, 以及 harness 版本漂移, 与判断模型无关, 首版照做.

### First version: one endpoint

- 判断模型一节可以为空. 用户要用时在配置中给出一个端点, 模型名, 凭据文件路径, 超时和按提示类别的指派 (16); 端点可以是机构内部部署, 也可以是用户明确选择的公开部署, 内容边界按 [定义 Jev 类模型的评测与转正条件](11-define-evaluation-and-graduation.md).
- 配置命令 (例如 `arw judge configure`) 只登记端点, 并做一次兼容核对 (返回字段, 概率之和为 1, 模型名) 与一组固定题目的延迟测量, 结果 (日期, 实际模型版本, 延迟) 写入配置; 核对不通过时报告原因, 不登记该端点, Engine 照常工作. 哪些提示类别启用按 11 的离线评测.
- 首版不探测显卡, 不下载运行时或模型文件, 不生成开启脚本, 不让出 Strata, 不建防火墙规则; Engine 不开启, 释放或重启判断模型服务, 服务由用户或其部署方维护.

### When a qualified local model exists

以下是 11-13 按 D19 定下的本机部署做法 (四处取舍见 Comments). 首版不实现; 有满足 18 使用条件的本机候选时再启用, 届时按当时的模型, 运行时与数据重新核对. 选择顺序沿用用户 11-09 的本机 → 机构内部部署 → 公开部署, 本机选能跑且够快的候选中智能最高的, 判断模型优先于同机 Strata (18).

#### Configuration command and probing

- 配置是一个显式命令 (例如 `arw judge configure`), 首次安装后和用户要求时运行, 不在 Engine 运行中自动重选. 结果写入用户级配置的判断模型一节; Engine 开启判断模型前只核对所选项仍然可用 (文件存在且大小一致, 显卡仍在, 端点可达), 不可用时按 16 不出提示, 原因写在配置状态中.
- 探测: 先看 `nvidia-smi` 是否可用并读取每块卡的名称, 总显存, 已用显存和驱动版本 (Windows, Linux 和 WSL 都可用); 没有时按平台选 Vulkan, ROCm 或 Metal 构建; 再用所选运行时的 `--list-devices` 核对. 同时记下 CPU 核数和内存. 按进程的显存在 Windows 上不可见, 所以探测只用整卡数值, 不尝试判断谁在占用.
- 本机档: ARW 发布内附一份候选目录, 每项写明模型文件, 运行时构建, 所需显存和最小上下文, 按 ARW 案例上的准确率排好次序 (案例与门槛来自 [本地 Jev 类候选的可行性小实验](15-task-local-candidate-feasibility.md) 和 [定义 Jev 类模型的评测与转正条件](11-define-evaluation-and-graduation.md)). 配置命令从高到低取第一个所需显存不超过可用显存 (总量减去不可让出的占用, 再留余量) 的候选, 安装后做一次本机测量: 兼容核对 (返回字段, 概率之和为 1, 模型名) 加一组固定题目的延迟. 通过速度门槛就选定; 不通过就试下一个. 只有 CPU 时同样测量, 并记 CPU 占用, 超过门槛视为本机不可用. 数值门槛由实验给出, 不在此定.
- 机构内部档与公开档: 用户在配置中给出端点, 模型名和凭据文件路径, 配置命令做同样的兼容核对与延迟测量; 公开档只在用户明确开启时参与. 三档都不可用时配置命令报告缺什么, 不配判断模型, Engine 照常工作.
- 选定项和测量结果 (候选 ID, 测得的显存与延迟, 日期) 一并写入配置, 供以后比较和排查.

#### Runtime and model files

由 ARW 的配置命令安装运行时与模型文件, 不只给出安装说明 (用户 11-13 确认, D19).

- 1.0 的候选目录只收由 llama.cpp `llama-server` 提供 `/v1/systemone` 的 GGUF 模型. 理由: 运行时是自带依赖的二进制包 (程序加对应 CUDA 运行库), 不需要 Python, torch 或包管理器; 维护者本机已用它跑通 GLiDE-9B. 需要 Python 服务的候选 (如 Laya, NeoHorse) 要多管一个数 GB 的环境和 CUDA 版本耦合, 不进首版目录.
- 固定版本: 运行时按构建号, 资产名和 GitHub 资产 `digest` (SHA-256) 固定; 模型按 Hugging Face 仓库, 完整提交哈希, 文件名和 LFS SHA-256 固定, 下载地址用提交哈希而不是分支. 这些值写在 ARW 发布的候选目录里, 只随 ARW 发布更新; 更新时先做兼容核对与 ARW 案例评测, 模型变化按 11 重新离线评测.
- 下载前显示文件大小, 许可 (例如 GLiDE-9B 的社区许可对大型商业实体另有要求) 和存放位置, 用户确认后才下载. 用户已有同一文件时可以给出本地路径: 校验 SHA-256 一致后直接使用, ARW 只记录路径, 不复制, 卸载时也不删除. ARW 自己下载的文件放在安装目录下的判断模型目录 (`runtime/`, `models/`, `logs/`, 开启脚本), 归属清单登记, 卸载时删除.
- 完整校验只在安装时做一次; 每次开启只核对文件大小与修改时间, 避免每次读取近 10 GB.
- 显卡驱动由用户安装. 配置命令读出驱动版本, 所选构建在本机启动失败时换同平台的另一 CUDA 主版本构建再试 (本机 CUDA 13.5 构建在 13.4 用户态驱动上可用), 仍失败则报告需要的驱动.

#### Start script

- 内容: 一个由配置命令生成的 Node.js 脚本 (ARW 本身只依赖 Node.js, 所以各平台同一种脚本), 顶部是全部可调参数: 运行时与模型文件路径, 绑定地址 (默认 `127.0.0.1`), 端口, 上下文, GPU 层数, 并行数, 设备, 让出列表. 提供 `start` 与 `stop` 两个动作, Engine 只经这两个动作开启和释放, 用户也可以手工运行排查.
- 开启时机 (原写在 07, 11-14 移到这里): 第一个需要判断模型的流程开始时 Engine 执行 `start`, 没有流程运行超过配置的时长后执行 `stop`; 不在 Engine 进程启动时就开启, 因为 Engine 常驻到关机, 否则判断模型会长期占用显卡. `start` 失败或判断模型运行中退出时按 16 不出提示, 流程照常, 下一个流程开始时再试.
- `start`: 按让出列表让出显卡 (见下节), 确认空闲显存足够, 启动 `llama-server` 并记录 PID 与进程创建时间 (Engine 识别崩溃用同样做法), 轮询 `/health` 到 200 (加载中为 503), 再做一题兼容核对, 输出写日志. 任何一步失败都停止已启动的进程并恢复已让出的占用者, 返回失败原因.
- `stop`: 按 PID 与创建时间结束本脚本启动的进程, 再按让出列表恢复占用者. 不按命令行文本查找或结束进程.
- 端口在配置时选一个空闲端口写入脚本, 不沿用其他服务的端口 (本机曾用 8000 与 Strata 前端冲突).
- 依赖: Node.js, 所选运行时目录 (含 CUDA 运行库), 模型文件, 显卡驱动; Engine 在 WSL 而判断模型在 Windows 侧时另需 WSL 互操作 (默认开启). 不依赖 Python, 包管理器或管理员权限 (下文的一次性防火墙步骤除外).

#### Windows and WSL placement

- Engine 与判断模型在同一操作系统环境时 (Windows 原生, Linux, macOS), 判断模型只绑 `127.0.0.1`, 不触发防火墙, 也不需要认证.
- Engine 在 WSL 中时 (用户 11-13 确认, D19), 判断模型作为 Windows 原生进程运行 (显卡驱动在 Windows 侧, 模型文件放在 Windows 磁盘, 维护者本机已验证). 开启脚本在 WSL 中经互操作启动 Windows 侧的 `llama-server.exe`, 绑定 WSL 虚拟网卡的主机侧地址; 该地址每次启动时取 WSL 默认网关, 不写死, 因为重启后会变. Engine 按同一地址访问.
- 这需要一条入站放行规则, 只能由管理员建立: 配置命令生成精确的 PowerShell 命令 (只放行该程序路径, 该 TCP 端口, 远端本地子网), 先说明用途与撤销方法, 由用户在管理员 PowerShell 中执行; ARW 不自行提权, 不修改防火墙. 必须在第一次非回环绑定之前建好: 没有规则时第一次监听会弹框, 无人应答就生成 Block 规则并压过放行规则.
- `start` 的就绪检查从 Engine 所在环境经该地址实际连接, 不只看进程已启动; 连不上时报告可能存在名为 "Query User" 的 Block 规则, 给出删除命令, 不自动改动. 运行时升级会改变程序路径, 按程序路径的规则要随之重建, 配置命令在升级后重新生成该命令.

#### Yielding the GPU

- 让出只针对配置中登记的占用者, 因为按进程的显存在 Windows 上不可见, Engine 无法安全判断一个未知进程能否停止. 未登记的占用使空闲显存不足时, `start` 失败并报告整卡已用量和 Windows 侧可见的进程名, 由用户处理.
- Strata 用内置的让出方式, 复用 ARW 现有 Strata 驱动的控制协议: 取得 lease, 调用 `/model/stop` 停掉常驻模型, 判断模型运行期间一直持有该 lease, 使 Strata 不会重新加载; `stop` 时归还 lease. lease 的持久化与 Engine 异常退出后的释放沿用现有驱动. 这比结束 Strata 的计划任务更稳妥: 前端继续运行, 归还后其他调用方立即可用.
- lease 已被其他调用方持有时不抢占 (用户 11-13 确认, D19). 判断模型这次不开启, 期间按 16 不出提示, 流程照常; 配置状态显示 Strata 的持有情况, 下一个流程开始时再试. 判断模型优先于 Strata 体现在 Engine 自己的配置上: 同一台机器上, 需要与判断模型共用显卡的本地模型不能配置给任何 Agent 角色 (显存同时装得下两者时除外), 配置命令据此拒绝.
- 其他占用者用通用方式: 用户登记一对让出与恢复命令 (固定参数数组, 不拼接命令解释器字符串), `start` 执行让出命令后重新读取空闲显存, `stop` 执行恢复命令.

#### Scenarios when a local model is used

- 新机器, 有 12 GB 显卡, 无其他占用: 配置命令选定目录中第一个装得下且测得够快的候选, 显示大小与许可, 用户确认后下载并校验, 生成开启脚本; 第一个流程开始时 Engine 执行 `start`, 约数秒后就绪.
- 同机 Strata 常驻模型但 lease 空闲: `start` 取得 lease, 停掉 Strata 模型, 启动判断模型; 释放判断模型时归还 lease.
- Strata lease 被测量任务持有: 判断模型不开启, 流程照常但不出提示; 测量结束归还后, 下一个流程开始时开启成功.
- Engine 在 WSL, 判断模型在 Windows 侧, 用户还没建放行规则: 配置命令先给出管理员命令; 未执行前 `start` 的连通检查失败并说明原因, 不出现无人应答的弹框.
- 没有显卡, 只用 CPU 的候选占用超过门槛, 用户配置了机构内部端点: 配置命令核对该端点通过后选定它; 没有配置时不配判断模型, Engine 照常工作.

### Autostart and LAN entry

- 对话入口要能远程连接, Engine 必须在用户登录时启动 (07). Windows 原生: 写入当前用户的 `Run` 注册表项, 不需要管理员. Linux: systemd 用户服务; 要在用户未登录时也可连接, 另需 `loginctl enable-linger`, 由用户选择. WSL: 在 Windows 当前用户的 `Run` 项中启动 WSL 内的 Engine, 并核对发行版不会因空闲被关闭 (`instanceIdleTimeout`); 常驻进程能否阻止空闲关闭要在实施时验证.
- Engine 的 HTTPS 入口绑定非回环地址时同样需要预先建立放行规则 (Windows 原生, 管理员一次). Engine 在 WSL 默认 NAT 网络下, 局域网设备连不上, 需要 portproxy (目标地址随重启变化, 每次都要管理员) 或 mirrored 网络模式 (管理员一次, 全局影响所有发行版); 配置命令检测当前网络模式, 报告缺什么并给出两条路径的步骤与代价, 不自动修改 `.wslconfig` 或防火墙. 未完成这些步骤时入口只在本机可用, 不阻止流程.

### Harness version drift

Engine 跟随用户安装的 Claude Code 与 Codex (用户 11-13 确认, D19), 不自带固定版本的 harness; 靠版本变化时的自检发现兼容端点失效.

- Engine 在每个 Agent 步骤开始时读取该 harness 的版本 (Claude Code 每回合一个进程, 用户的交互会话自动更新后下一回合就会换版本; Codex App Server 在重启时读取).
- 某角色经兼容端点使用本地或第三方模型时, (harness 版本, 端点, 模型) 三元组第一次出现前先做一次兼容自检: 一个包含工具调用的最小回合, 检查请求被接受, 工具调用往返成功, 输出完整. 通过的三元组记入 Engine 状态, 之后直接使用; 使用官方模型的角色不做此检查.
- 自检失败时该角色不可用, 需要它的流程停在可恢复状态, 报告失败的请求与错误, 上一个通过的版本, 以及怎样装回该版本并暂停自动更新 (Claude Code: 按版本号安装并设置 `DISABLE_AUTOUPDATER`; Codex: npm 按版本安装并设置 `check_for_update_on_startup = false`). Engine 不悄悄把该角色换成别的模型, 因为角色用哪个模型是用户的选择.
- Engine 不替用户修改 harness 的安装或更新设置; 用户固定版本后, Engine 只按上述自检使用.

### Scenarios

- 没有配判断模型 (首版默认): Engine 正常开工, 所有流程照常, 不出任何提示, 也没有关于判断模型的提醒.
- 用户配置了机构内部端点: 配置命令核对通过后登记; 已按 11 离线评测通过的提示类别启用, 其余类别不提示.
- 运行中端点不可用: 该题不提示, 流程照常, 调用记录记下失败类别.
- 用户的 Claude Code 自动更新后兼容端点返回 400: 下一回合前的自检失败, 流程停在可恢复状态, 报告给出上一个通过的版本与安装命令; 用户装回旧版本或上游修复后从该步继续.

### Interfaces

- 用户级配置的判断模型一节 (沿用 16 的结构, 可以为空): 端点, 模型名, 凭据文件路径, 超时, 按提示类别的指派, 配置时的兼容核对与测量结果; 以后的本机档另有候选 ID, 运行时与模型文件的固定值和路径, 端口, 让出列表, 空闲释放时长.
- 配置命令: 首版登记端点并核对; 以后另有探测, 选择, 下载与校验, 生成开启脚本和放行规则命令.
- 以后: 开启脚本的 `start` 与 `stop` 两个动作及其退出状态与失败原因; 安装归属清单新增判断模型目录与 Windows 侧文件 (Engine 在 WSL 时).
- Engine 状态中的兼容自检记录 ((harness 版本, 端点, 模型) 与结果).
