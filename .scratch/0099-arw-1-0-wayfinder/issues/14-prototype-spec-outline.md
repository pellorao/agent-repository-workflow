11-14 (任务 v1-wtfix, 依据墙钟研究 v1-walltime, D23 选 A): 验收场景中的墙钟验收写成下面的口径, 同一批 issue 在现行 ARW 与 1.0 下各跑一遍, 用同一套脚本从记录里算.

- 主口径是活动时间, 即一个流程的总墙钟减去等用户答复的时间与空闲时间 (研究口径). 两种比值都要达到不超过 0.85: 合计比 (这批 issue 的活动时间之和, 1.0 除以现行) 与逐流程中位比 (每个流程各算一个 1.0 除以现行的比值, 取中位数). 两个都写, 因为合计比受大 issue 左右, 逐流程中位比反映典型的小 issue, 而小 issue 里 Reviewer 占比高, 只有审核包能省, 交接开销相对大.
- 研究对已交付的 46 个 issue 回放的估计: 合计比中值 0.79 (悲观 0.92, 乐观 0.66), 逐流程中位比中值 0.84 (悲观 0.98, 乐观 0.71, bootstrap 区间 0.82 到 0.86). 逐流程中位比刚好压线, 区间跨过 0.85, 所以不能事先断言验收通过; 决定成败的三个量见地图 Not yet specified, 都由原型 (D25) 实测.
- 另报两项, 不作通过条件: 含等待口径 (活动时间加等用户答复的时间; 研究估计中值合计比 0.75, 逐流程中位比 0.83), 和每个流程的用户介入次数 (停下等用户的次数, 对应第五目标 "减少停机点", 与 11 的停机点次数是同一项).
- 实测结果与上述两个门槛的差距如实报告, 由用户决定调整门槛还是加做法; 不自行改门槛.
- 基线 (11-14, 任务 v1-15, 由 11 转来): 现行 ARW 的基线有两组, Claude 侧 (12: 17 次交付, 每个实施 issue 活动时间中位约 24.9 分钟, 即 11 所说 15 到 25 分钟) 与 Codex (sol) 侧 (墙钟研究: 46 个交付, 活动墙钟中位 9.9 分钟, 提交审核期间 luna xhigh 使复审更慢), 两组的审核时长与机械请求占比不同, 研究明确说 E2 的 Claude 结论 (只省约 7%) 不适用于 sol. 大纲要写明验收用哪组基线, 或两组各自对照 (建议各自对照, 因为 1.0 对两个平台完全对等, 04); 未写明前 11 与 14 的墙钟门槛没有确定的比较对象.

11-14 (任务 v1-rulecue): 用户 11-14 提出规则细节在输出时失效, 用户听不懂 (原话见 [定义规则到 graph 的转换与 Engine 按 graph 执行](22-define-rule-to-graph-conversion.md) 的 Comments). 机制在 22 (Graph shape 节 "交给用户的文字"), 07 (Before text reaches the user 节), 19 (Free replies in the conversation entry 节) 与 21 (Expression and interaction rules 节). 大纲要有 "交给用户的文字" 一节, 验收写成下面的口径.

- 主指标: 用户回 "听不懂" 一类的次数, 按每 100 份交给用户的文字计, 分种类 (`ask-user`, `wait-user`, `report`, 对话回复), harness 与模型. 信号有三种: 入口 "没看懂" 按钮, 用户调用 `wait-what`, 用户消息被词表认出. 词表规则: 消息不超过 30 字符且含下列正例短语之一. 验收只按所列例子判定. 正例: "听不懂", "看不懂", "没看懂", "什么意思?", "啥意思", "说人话", "解释一下", "I don't understand", "what do you mean". 反例: "看懂了, 继续", "不用解释, 直接做", "我懂你的意思", "这个函数到底是什么意思我们以后再查, 先把测试跑通再说" (超过 30 字符).
- 现行的基线: 用户说现行每天可达上百次, 但没有计数. 可选两条路: 以原型对照组按同一口径测出的值为基线 (下一条); 或用脚本按上面的词表扫现行会话记录中的用户消息, 只输出数目. 后者要读消息正文, 超出现有 "会话记录只由脚本取元数据" 的数据边界, 待用户确认.
- 原型 (D25) 中的测法, 单独排一段, 不与墙钟运行混跑, 以免影响墙钟测量:
  - 素材: 原型与对照运行中全部交给用户的文字 (问用户, 停机点, 结束报告), 加约 20 个构造的情形: 取已交付 issue 中真实出现过的要用户决定的停机点, 在已做完一段实施的长会话末尾让模型提问, 重现 "规则在会话开头读入, 隔了整段工作才输出".
  - 两组: 现行 (规则在会话开头, 自由文字提问) 与 1.0 (`ask-user` 字段, 字段说明, 末尾提醒, 07 的检查与改写一次); Codex 与 Claude Code 各跑, 每个情形每组 3 次.
  - 量: 07 四项检查的命中率 (现行组只查不改, 1.0 组记改写前与改写后); 盲读: 一个看不到仓库与会话的裁判 (与盲评裁判同级, 不低于 `sonnet` `high`) 只读交给用户的文字, 写出这是什么问题, 为什么要用户定, 每个选项意味着什么, 并回答能否据此决定, 与按情形事先写好的要点核对, 答不出或答错记一次 "听不懂" 代理; 改写比例, 每次改写的请求数与耗时 (07 的交接预算).
  - 通过条件 (建议值, 待用户确认): 1.0 组盲读 "听不懂" 代理的比例不超过现行组的三分之一, 且不超过 10%; 改写后仍有检查命中的文字不超过 2%; 改写比例不超过 15% (07). 两个 harness 分别达到.
- 上线后: Engine 按 07 的步骤记录每周报告主指标. 用户回 "听不懂" 的次数是用户感受的直接量, 原型的盲读只是代理; 两者差距大时以前者为准, 调整字段说明, 提醒与检查项.
