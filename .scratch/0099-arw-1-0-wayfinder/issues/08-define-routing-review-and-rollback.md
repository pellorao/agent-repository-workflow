# 定义分流判断的复核与回退合同

Type: grilling
Status: resolved
Blocked by: issue:0099:05, issue:0099:07

##### Question

Jev 类模型先判断一件事该由谁处理, 再在适合时作答; 置信度不足时同步交高智能 Agent, 初期即使置信度高也异步复核, 复核结论不同时撤销并改按高智能结论执行. 怎样把这些变成精确的动作与失败合同: 待复核写入动作的上限, 可逐级回退的仓库快照放在哪里, 回退后哪些动作重做, 何时必须请人类判断? 用跨多个动作的不同结论, 双方置信度都低和需要用户授权的场景检验.

## Answer

11-14 按用户 D24 答复改写 (原答案写于 11-12, 11-13 按用户确认的投机写入上限与自动回退定稿, 改写经过见 Comments). 依据: D24 (判断模型可选, 配了只做提示), 用户 11-13 "首版不做回退, 回退与判断模型绑定", 批判审读一.1 与二.2, 以及 [定义 Engine 驱动流程的运行合同](07-define-engine-runtime-contract.md), [定义 Reviewer 与正式关卡在 Engine 下的执行协议](09-define-reviewer-protocol.md).

### Judgments do not drive actions

- 1.0 中判断模型的结论不直接决定流程走向, 所以不存在 "按判断先执行, 事后被推翻" 的情形. 原问题中的投机执行, 高智能 Agent 盲答异步复核, 投机写入上限, 推翻后的回退与重做, 以及为它们设的屏障全部删除; 07 的实例状态不加 `waiting-review`.
- 需要语义判断才能决定走向的分支 (例如 "这项改动是否需要用户决定", "这次修改是否需要 Spec Readiness 复审", 分流) 写成正在干活的 Agent 步骤输出 schema 中的必填字段, 由已有上下文的会话在本步一并作答, 不另开请求 (07, 22). 流程中没有可用 Agent 步骤之处不提题, 直接走保守分支 (需要用户, 需要关卡).
- 判断模型配置了时只做提示: 09 的提示类 (预检, 输出检查, 修复核对), 以及对上述 schema 字段的事后核对 (例如字段答 "不需要用户决定" 而判断模型高置信认为需要时, 提醒该会话复看). 提示交给会话核实, 动作由会话核实后的结论决定. 判断模型未配置, 某类提示未按 [定义 Jev 类模型的评测与转正条件](11-define-evaluation-and-graduation.md) 启用, 调用失败或低于阈值时不提示, 流程照常. 判断模型的使用条件见 [确定本地判断模型服务的运行责任](18-decide-local-judge-server-ownership.md).
- 这守住 05 的边界: 判断模型不替代正式审核结论, 也不替代用户授权.

### Restore points

- 每个写入步骤开始前, Engine 把该步写入范围内的工作区内容写成 Git 快照: 用临时索引文件 (`GIT_INDEX_FILE` 指向 Engine 私有路径) 把已跟踪文件和未被忽略的未跟踪文件写成树对象与提交对象, 挂在仓库的私有引用 `refs/arw/baseline/<实例>/<步骤>` 下, 引用名写进步骤记录. 不改用户的索引, `HEAD` 和工作区.
- 用途只有一个: 用户停止实例后 (07 的 Waiting for the user 节), 或实例 `stopped` 后用户选择回退时, 作为手动恢复点. Engine 不做任何自动回退. 用户在入口中选定某个恢复点后, Engine 先把当前状态另存为快照, 再把该步写入范围内的文件恢复为所选快照的内容 (撤销修改和删除, 删除快照中没有的新文件).
- 理由: 现行规则以已暂存内容为基线, 但暂存区同时是 Code Review 与 Commit Audit 冻结的审核候选, 而且只有一层. Git 对象按内容去重, 每步只新增改动过的文件, 成本低. 用引用而不是只在状态库记对象 ID, 是因为无引用的对象会被 `git gc` 清理, 而 `stopped` 实例可能等用户很久. 代价: 私有引用在 `git for-each-ref` 中可见, `git push --mirror` 会推送它们, 规范中写明.
- 范围: 只覆盖该步写入范围. 被忽略规则命中的路径与 `.tmp/` 不在快照中.
- 建立和删除快照引用是 Engine 的 Git 写入, 07 在每个 Agent 步骤后核对引用时不计 Engine 自有的引用; 会话改动或删除这些引用同样算会话做了 Git 写入.
- 清理: 实例 `done` 后删除它的私有引用; `stopped` 与 `cancelled` 的实例保留, 用户回退完毕或在入口中丢弃该实例后删除. 现有快照列在 07 的可观察内容中.
- 回退本身失败 (Git 命令出错, 文件被占用) 时报告用户, 不反复重试.
- 这改写现行基线规则 (`docs/agents/agent-writes.md` 的 Prepare the baseline 节): 1.0 中基线由 Engine 在每个写入步骤前自动建立, 不再由 Main Agent 暂存.

### Scenarios

1. 需要用户授权: 实施 worker 的输出 schema 有必填字段 "是否含需要用户决定的设计取舍". 答 "是" 时转为等待用户. 答 "否" 时, 若配了判断模型且这类提示已按 11 启用, 判断模型高置信认为 "是" 就提醒该会话复看; 会话复看后仍答 "否" 就继续, 正式关卡照常.
2. 没有可用 Agent 步骤: 某个分支前面只有程序节点, 没有正在干活的会话可以作答; 转换时把边接到保守分支 (例如交用户或跑关卡), 不提题, 也不为此新开高智能请求.
3. 用户停止后恢复: 用户在实施中途停止实例; 入口列出各写入步骤前的恢复点, 用户选定一个, Engine 先另存当前状态, 再恢复该点; 用户也可以不回退, 改动留在工作区.

### Interfaces

- 07: 写入步骤前的恢复点即本节的私有快照, 只供用户手动恢复; 判断只做提示, 语义判断是 Agent 输出 schema 的必填字段; 状态集合不加 `waiting-review`.
- [定义 Reviewer 与正式关卡在 Engine 下的执行协议](09-define-reviewer-protocol.md): 正式 Reviewer 关卡不是判断; 提示类按 09.
- [定义并行流程的读取与写入隔离](10-define-parallel-flow-isolation.md): 没有投机写入, 不存在跨实例的推翻与回退.
- 11: 提示的启用与停用.
- [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md): 判断模型失败或超长时不提示.
- [定义规则到 graph 的转换与 Engine 按 graph 执行](22-define-rule-to-graph-conversion.md): 判断节点只产生 "提示" 或 "不提示", 语义判断写在 Agent 节点的输出 schema 中.
