# 定义分流判断的复核与回退合同

Type: grilling
Status: resolved
Blocked by: issue:0099:05, issue:0099:07

##### Question

Jev 类模型先判断一件事该由谁处理, 再在适合时作答; 置信度不足时同步交高智能 Agent, 初期即使置信度高也异步复核, 复核结论不同时撤销并改按高智能结论执行. 怎样把这些变成精确的动作与失败合同: 待复核写入动作的上限, 可逐级回退的仓库快照放在哪里, 回退后哪些动作重做, 何时必须请人类判断? 用跨多个动作的不同结论, 双方置信度都低和需要用户授权的场景检验.

## Answer

11-12 worker 分析, 交 Main Agent 综合. 依据: [定义 Engine 驱动流程的运行合同](07-define-engine-runtime-contract.md) (步骤四类, 每步持久化, 写入者令牌, Git 写入由 Engine 执行), [确定 Jev 类模型在流程中的职责边界](05-decide-jev-role-boundary.md), [定义 Jev 类模型的评测与转正条件](11-define-evaluation-and-graduation.md) 的转正阶段, [定义 Engine 调用 Jev 类模型的接入方式](16-define-judge-model-integration.md) 的失败与超长处理, 以及 ARW HEAD `79e2497` 的 `docs/agents/agent-writes.md` (以已暂存内容为基线) 和 `.agents/skills/code-review/SKILL.md`, `lib/commit-audit/commit-audit.mjs` (以 `git write-tree` 冻结索引作为审核候选). 下文数值是首版默认, 由 [本地 Jev 类候选的可行性小实验](15-task-local-candidate-feasibility.md) 和评测校准, 是可调参数.

### Terms

- 判断: 流程定义中的一个判断步骤 (向判断模型提的一题). 所选项概率达到该类判断的阈值 (按 11 定) 才算阈值以上.
- 依赖: 流程因某判断的结论才走到某一步, 或该结论是这一步的输入, 这一步就依赖该判断. Engine 在步骤记录中记下每步依赖的未复核判断 (所在分支上全部未复核判断), 不需要 Agent 声明.
- 投机写入: 依赖至少一个未复核判断的写入步骤 (改变工作区的确定性操作或 Agent 步骤).

### Who acts on a judgment

1. 阈值以上, 且该类处于全量复核或抽样复核阶段: 按判断结论推进; 全量复核阶段的每条和抽样阶段被抽中的进入异步复核, 未抽中的视为已复核.
2. 阈值以下, 单题超出输入上限 (见 16), 或该类处于影子阶段或已停用: 同步交高智能 Agent 作答, 流程等它的结论; 影子阶段的判断照常记录供统计.
3. 单向题: 流程定义把 "答错会跳过用户授权或正式关卡" 的题标为单向, 例如 "这项改动是否需要用户决定", "这次修改是否需要 Spec Readiness 复审". 判断模型只在保守方向 (需要用户, 需要关卡) 按第 1 路直接生效; 放宽方向不论概率都按第 2 路同步交高智能 Agent. 这守住 05 的边界: 判断模型不替代正式审核结论, 也不替代用户授权.

高智能 Agent 作答 (同步作答与异步复核相同) 的输出 schema: 选项之一或 "交用户", 理由, 以及 0 到 1 的自评置信度. 自评置信度只记入判断调用记录供分歧统计, 不参与分支, 因为它同样没有在 ARW 文本上校准; Agent 拿不准时选 "交用户". 这就是地图 Not yet specified 中高智能 Agent 输出合同的分流部分.

### Asynchronous review

- 复核者是独立于工作会话的高智能 Agent 会话 (复核角色, 模型按配置), 盲答: 只给题目, 选项和 Engine 按来源重建的 `state`, 不给判断模型的答案与概率, 由 Engine 比较. 盲答使 11 的分歧统计不受锚定影响. 同一实例同时待复核的多条判断合并为一次请求.
- 一致: 判断标为已复核, 依赖它的写入不再是投机写入.
- 不一致: 判断被推翻, 按下文撤销. 复核者选 "交用户": 判断标为有争议, 已执行的投机写入暂不撤销, 依赖它的后续写入和屏障步骤暂停, 实例转为等待用户, 用户选定结论后按一致或推翻处理.
- 复核会话失败按 07 的失败合同重试; 仍失败时判断保持未复核, 由下面的上限与屏障让流程在需要它时停下, 不会把未复核判断当作已复核.

### Speculation limit and barriers

- 上限: 一个实例 (连同其子实例栈) 中, 已执行且依赖未复核判断的写入步骤最多 3 个 (用户 11-12 确认首版用 3, 之后由实验校准). 到上限时下一个投机写入步骤等待复核 (实例状态 `waiting-review`, 补入 07 的状态集合); 只读步骤和只写 `.tmp` 的步骤照常推进. 上限约束的是一次推翻最多丢弃的工作量.
- 屏障: 以下步骤开始前, 它依赖的全部判断必须已复核且未被推翻, 不足时等待: 固定审核候选 (为 Code Review, Commit Audit 或 Spec Readiness 暂存或冻结), 提交, 释放写入者令牌, 作用到工作区以外的操作 (推送, 发布, 安装或改环境, 调用外部服务), 等待用户步骤 (不让用户回答一个可能作废的问题; 例外见单向题), 实例结束.
- 写入者令牌只在提交后或停在无未提交修改的状态时释放 (07), 而提交是屏障, 所以其他实例不会在未复核的投机写入之上写入; 其他实例读到投机写入的影响见 [定义并行流程的读取与写入隔离](10-define-parallel-flow-isolation.md).

### Recovery baselines

- 位置: Engine 私有的 Git 快照, 不用暂存区. 每个写入步骤开始前, Engine 用临时索引文件 (`GIT_INDEX_FILE` 指向 Engine 私有路径) 把该步写入范围内的工作区内容 (已跟踪文件和未被忽略的未跟踪文件) 写成树对象与提交对象, 挂在仓库的私有引用 `refs/arw/baseline/<实例>/<步骤>` 下, 引用名写进步骤记录. 不改用户的索引, `HEAD` 和工作区.
- 理由: 现行规则以已暂存内容为基线, 但暂存区同时是 Code Review 与 Commit Audit 冻结的审核候选; 投机写入期间改暂存区会改变候选, 而且暂存区只有一层, 不能逐级回退. 文件副本能逐级回退, 但不去重, 写盘更多, 删除与新增要自己处理. Git 对象按内容去重, 每步只新增改动过的文件, 恢复用现有 Git 命令. 用引用而不是只在状态库记对象 ID, 是因为无引用的对象会被 `git gc` 清理, 而 `stopped` 实例可能等用户很久. 代价: 私有引用在 `git for-each-ref` 中可见, `git push --mirror` 会推送它们, 规范中写明.
- 范围: 只覆盖该步写入范围. 被忽略规则命中的路径不在快照中, 流程定义不把这类路径分给写入步骤; `.tmp` 不受单一写入者约束 (07), 也不回退.
- 回退: 把写入范围内的文件恢复为快照内容 (撤销修改和删除, 删除快照中没有的新文件). 回退前先把当前状态也写成快照, 被推翻的工作因此不丢失, 实例结束前可以查看和取回.
- 用户改动: Engine 在每步结束时记录写入范围内文件的内容身份. 回退范围内有不属于任何步骤的改动 (用户或其他程序手工所改) 时不回退, 实例停下交用户决定, 不覆盖用户的修改.
- 建立和删除快照引用是 Engine 的 Git 写入, 07 在每个 Agent 步骤后核对引用时不计 Engine 自有的引用; 会话改动或删除这些引用同样算会话做了 Git 写入.
- 清理: 实例 `done` 或 `cancelled` 后删除它的私有引用; `stopped` 的实例保留. 现有快照列在 07 的可观察内容中.
- 这改写现行基线规则 (`docs/agents/agent-writes.md` 的 Prepare the baseline 节): 1.0 中基线由 Engine 在每个写入步骤前自动建立, 不再由 Main Agent 暂存.

### Undo after a reversal

- 判断 J 被推翻时, Engine 依次: 中断正在执行且依赖 J 的步骤; 把工作区回退到依赖 J 的第一个写入步骤之前的快照, 此后本实例 (指整条写入链: 实例连同其子实例栈) 的写入步骤一并回退 (它们都在 J 之后的分支上, 按上文 "依赖" 的定义都是依赖 J 的投机写入; 回退只撤销整条写入链 (实例连同其子实例栈) 自己的投机写入, 不动其他实例和用户的改动); 作废依赖 J 的后续判断及其复核任务; 按复核结论从 J 处继续.
- 重做: 回退点之后的步骤按流程定义重新执行. 只读步骤的输入 (路径与内容身份) 未变时复用其结果. 重做的 Agent 步骤在原会话中进行, 附一条更正 (原结论, 复核结论与理由, 已回退的范围), 保留已有理解; 被推翻的判断正是 "交给哪个角色" 时新建会话.
- 多个判断先后被推翻时, 回退到其中最早的回退点; 晚于回退点的判断作废, 其复核结果到达后丢弃.
- 单向题在保守方向直接发出的用户问题被推翻 (复核者认为不需要用户) 时, 用户尚未回答就撤回问题继续; 用户已经回答的以用户答复为准, 不回退.
- 回退本身失败 (Git 命令出错, 文件被占用) 时实例转为 `stopped` 并报告, 不反复重试.

### When a human decides

只有以下情形请用户判断: 高智能 Agent 同步作答或异步复核选 "交用户"; 回退范围内有不属于任何步骤的改动; 回退失败; 复核会话按 07 的失败合同停下. 其他推翻与回退由 Engine 自动完成, 不打断用户, 也不请用户确认 (用户 11-12 确认), 用户可在入口看到推翻记录, 回退范围和保存的快照. 某类判断推翻过多时按 11 退回全量复核或停用, 也不需要用户决定.

### Scenarios

1. 跨多个动作的不同结论: 实施流程中判断 J1 ("修复只涉及测试数据吗": 是, 0.97) 让 worker 直接改测试数据 (写入 W1); 判断 J2 ("还需要改别处吗": 否) 跳过补充修改; Engine 运行测试 (只读), 然后要冻结审核候选. 冻结是屏障, 等 J1, J2 复核. J1 被推翻 ("还涉及实现"): Engine 把 W1 的结果另存快照, 回退到 W1 之前, 作废 J2 及其复核, 走 "还涉及实现" 的分支, 给 worker 一条附更正的消息; 测试的输入变了, 重新运行.
2. 双方置信度都低: 分流题低于阈值, 同步交高智能 Agent, Agent 选 "交用户"; 实例等待用户, 待答事项附两方结论与理由; 同仓库不依赖它的实例照常推进.
3. 需要用户授权: "这项改动是否需要用户决定" 是单向题. 判断模型答 "需要" (0.92) 时直接转为等待用户, 同时异步复核; 复核认为不需要且用户尚未回答时撤回问题继续. 判断模型答 "不需要" 时不论概率都同步交高智能 Agent, Agent 认为需要就等待用户.

### Interfaces

- 07: 状态集合加 `waiting-review`; 写入步骤前的恢复基线就是本节的私有快照; 屏障先于令牌释放.
- [定义 Reviewer 与正式关卡在 Engine 下的执行协议](09-define-reviewer-protocol.md): 正式 Reviewer 关卡不是判断, 不经本节复核; 判断模型的预检与输出检查按本节三路与屏障执行; 固定正式审核候选是屏障.
- 10: 其他实例读取投机写入时的一致视图, 以及回退对它们的影响.
- 11: 阶段决定第 1, 2 路; "推翻且已执行依赖它的写入" 是有害分歧的计数来源.
- 16: 判断模型失败按其失败合同; 超长按低于阈值.
