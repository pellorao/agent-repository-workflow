# ARW 1.0 规范路线图

## Destination

一份可独立阅读, 足以指导后续实现的 ARW 1.0 完整规范 (Engine 运行合同, 规则到 graph 的转换, 可选的 Jev 类模型提示 (D24), Reviewer 协议, 评测与启用, 并行流程隔离, 现有合同的取舍, 验收场景), 经独立审查; 附可行性结论, 写明哪些已经验证, 哪些仍有风险. 本 effort 到规范审查通过为止; 用户 11-08 定下规范通过后在单独分支上完整实现全部工作流, 定期合入 main, 全部实现后再合并回 main, 这一实施不属于本 effort.

## Notes

- 用户 11-07 定下的两个方向: 集成 Jev 类模型做任务分流; 不再以 Codex 为基础, 改为以 Engine 为基础工作. 按 10-25 讨论中用户的原话, 后者指 "代码中的确定性流程加 Jev 类模型的简单语义判断" 构成 ARW 的流程, 由它驱动用户和高智能 Agent, 而不是由 Codex (或 Claude Code) 中的 Main Agent 读规则推进; 用户 11-07 已确认这一理解, 见 [确定 ARW 1.0 的产品边界与 Agent 平台范围](issues/04-decide-product-and-platform-scope.md). 用户 11-13 在 D24 中改为判断模型可选: 不配也完整工作, 配了只做提示, 语义判断由正在干活的 Agent 步骤作为输出 schema 的必填字段回答; 按用户的使用条件, 首版实际不配, 见 [确定本地判断模型服务的运行责任](issues/18-decide-local-judge-server-ownership.md).
- 本 effort 只做可行性研究和方案起草: 不写运行时代码, 不改 main 上现行的 ARW 治理文档, 不增加 ADR 或项目术语表条目, 不发布. 规范正文写在单独克隆的 `arw-1.0` 分支上将来生效的位置, 见 [确定 ARW 1.0 规范的归属与交付形式](issues/06-decide-spec-home.md). 作为 Wayfinder 默认只规划的改写, 地图延伸到规范正文的编写与审查, 但不含实现.
- 10-25 的讨论记录, 旧路线图和旧研究只作参考. 其中的结论按当前 HEAD 或一手来源重新核实后才采用, 采用处注明 "参考 10-25 材料, 已于 MM-DD 核实". 10-25 时用户的表述 (例如待异步复核的写入动作上限为 3) 作为待用户重新确认的候选, 不直接计入 Decisions so far (写入动作上限 3 曾于 11-12 由用户重新确认, D24 删去投机执行后作废, 见 08); 其中 "Jev 类模型不担任正式 Reviewer" 已由用户 11-07 重新确认, "评测先用托管服务后用本地开源模型" 已被 11-07 的答复取代 (托管 Jev 只作评测基准).
- 需要用户决定的 grilling issue 不阻塞其他工作: Main Agent 把它写成自成一体的待决定事项交给用户, 先推进不依赖它的 issue, 用户答复后再记录 `## Answer`.
- 研究按 `research` Skill 使用一手来源. `domain-modeling` 与 `codebase-design` 只用于检验边界和情景, 不写入术语表或 ADR. 规范大纲用 `prototype`.
- 需要 GPU 或本地模型的可行性实验由 Main Agent 按本机资源规则另行排期, 下载和写盘量先报批.

## Decisions so far

- [核对当前 ARW 的流程驱动方式与 Engine 已有能力](issues/01-research-current-flow-driver.md): 现在由 Main Agent 按触发点读规则推进流程, Engine 只提供单项确定性操作, 没有调度命令; Engine 已有用户级后台管理进程, 可经 Codex App Server, `claude -p` 和 Strata 驱动 Reviewer 与后台 Agent; 改为 Engine 驱动会改变 7 项现行合同.
- [核对 Jev 类判别模型的能力与候选](issues/02-research-jev-class-models.md): Jev 只托管, 一次调用可批量回答多个固定选项问题, 价格极低, confidence 不等于答对概率, 官方未声明中文能力; 实测候选为托管 Jev, NeoHorse-Jev-4B, Laya multilingual 和一个未微调对照, 需带标签的 ARW 案例和约 10 GB 下载.
- [核对 Engine 控制 Agent 会话的平台能力](issues/03-research-engine-session-control.md): Codex App Server 与 `claude -p` stream-json 都能由程序启动, 继续, 观察, 中断会话并应答批准, ARW 已各有实现; 两边都不保证崩溃后接回执行中的回合; 第三方与本地模型只有 Codex 有官方路径 (Claude Code 一侧的实际可行性由下一项更正).
- [确定 ARW 1.0 的产品边界与 Agent 平台范围](issues/04-decide-product-and-platform-scope.md): 用户确认 "以 Engine 为基础" 即 Engine 中的确定性流程加 Jev 类模型的简单判断驱动用户和高智能 Agent; Codex 与 Claude Code 完全对等, 两边都支持本地与第三方模型. Claude Code 经 Anthropic Messages 兼容端点可接本地与第三方模型, 已有实例, 但 Anthropic 不支持且随版本漂移; 首版工作流覆盖与跨平台组合另列 issue.
- [确定 Jev 类模型在流程中的职责边界](issues/05-decide-jev-role-boundary.md): Jev 类模型不担任任何正式 Reviewer Role 或审核轴, 只做任务分流, 有明确检查项的预检和最终输出检查; 托管 Jev 只作速度与准确率基准, 正式方案优先找本地或其他托管替代.
- [确定 ARW 1.0 首版覆盖的工作流与跨平台组合](issues/17-decide-workflow-coverage-and-platform-mix.md): 规范覆盖全部现有工作流, 一次做完, 不设过渡期共存, 规范通过后在单独分支上实现; 与用户对话的入口由 Engine 提供, Engine 按用户选的 Main Agent 模型把话交给对应的 harness (Codex 或 Claude Code), 可同时控制多个 harness, 各角色所在 harness 不必相同.
- [定义 Engine 调用 Jev 类模型的接入方式](issues/16-define-judge-model-integration.md): Engine 在进程内直接调用 `/v1/systemone` 兼容接口, 不接成后台 Agent 提供方; 只用 choice 与 noul 题型, 托管与本地只靠配置切换, 密钥在仓库外私有文件; 判断模型可选 (D24), 配置一节可以为空, 调用失败或超长时该题不提示, 流程照常, 不交高智能 Agent 代答, 也不打断用户; 调用记录写在用户私有运行状态且默认不存原文, 记提示是否被判无效.
- [定义 Jev 类模型的评测与转正条件](issues/11-define-evaluation-and-graduation.md): 1.0 验收对照现行 ARW (D23 的四项目标门槛加停机点次数), 不配判断模型也要达到, 不再要求 "用判断模型比不用快很多" (D24); 质量守护沿用 Reviewer benchmark 与真实缺陷检出; 判断模型须比托管小模型快很多倍且准确率不明显降低, 每类提示在 E3 题集上离线评测过门槛 (阈值以上精度不低于 0.95) 就启用为提示, 线上记被判无效的比例, 超过 5% 即停用, 模型或题目模板变化时停到重新评测通过; 关闭判断模型只用于判断模型自身的取舍; 托管模型只接收公开仓库案例.
- [确定本地判断模型服务的运行责任](issues/18-decide-local-judge-server-ownership.md): 判断模型可选 (D24, 推翻 11-11 的 "必需组件"), 不可用时 Engine 照常工作, 不出提示, 配了只做提示; 使用条件 (用户 11-13) 是比 DeepSeek flash 一类托管小模型快很多倍且准确率不明显降低, 以 E3 题集离线评测, 现有 GLiDE-9B 只快约 2 倍, 所以首版实际不配; 首版只需配置一个端点, 本机选模型顺序, 开启脚本与 Strata 优先关系推迟到有合格模型时 (20); "用判断模型比不用快很多" 不再是 1.0 验收条件.
- [确定 ARW 1.0 规范的归属与交付形式](issues/06-decide-spec-home.md): 规范写在单独克隆的 `arw-1.0` 分支上将来生效的位置, 合并回 main 时生效; 整体走一次按章分片加全局一致性的独立审查, 之后每个实施 issue 照常走 Spec Readiness.
- [定义 Engine 驱动流程的运行合同](issues/07-define-engine-runtime-contract.md): Engine 是由现有用户级后台管理进程扩展的常驻进程, 开工不依赖判断模型 (D24); 流程定义是随 Engine 发布的 graph 数据加 Engine 代码中的原语 (由 22 细化), 步骤只有确定性操作, 判断, Agent 步骤和等待用户四类, 下一动作由定义和上一步结果唯一决定; 实例状态每步持久化, 仓库 Artifact 仍是交付权威; Engine 对所有 Agent 会话一视同仁, 不区分对话会话, worker 与 Reviewer 会话, 流程中的语义判断是正在干活的 Agent 步骤输出 schema 的必填字段, 没有 Agent 步骤处走保守分支, 判断步骤只做可选提示 (D24); 各 Agent 的唯一区别是工作开始时选定的模型, 整项工作 (含各轮修复与复审) 沿用同一会话与模型以利用缓存, 不自动换模型, 选模型分两段 (D22): 写任务概要的一步同时输出难度, 推理强度, 速度要求等参数 (D22(1) 原定由判断模型输出, D24 后首版不配判断模型), 机械映射表把参数对到模型和推理强度, 参数估计的校准题待测; 压缩后沿用原会话和原模型; Agent 步骤宜粗, 只在冻结, 门禁, Git 写入, 等用户处切分; 所有 Agent 步骤超时先问用户, 不中断; 任何 Agent 提议改 spec 由处置步骤加一个独立会话共同决定; Git 写入只由 Engine 执行, 以每个 Agent 步骤后的检测保证, 另对所有会话加不覆盖用户设置的窄范围拒绝 (用户 11-13 确认); Engine 对外提供配对后的 HTTPS 入口, 在用户登录时自启; 子流程压栈并继承写入者令牌, 并行实例按每仓库一个写入者令牌串行写入; 对话连续性由 Engine 的对话记录保持, 跨 harness 换模型时以交接消息开新会话.
- [确定 Engine 对话入口的形态](issues/19-decide-conversation-entry-form.md): 首版入口是 Engine 自带的网页, 局域网和远程设备也能连接; 不设账号密码, 设备第一次连接用本机生成的一次性授权码配对, 之后凭可撤销的设备凭据访问, 非回环访问走 TLS; 不复用 harness 的交互界面, 终端界面与 ACP 不进首版.
- [定义分流判断的复核与回退合同](issues/08-define-routing-review-and-rollback.md): 11-14 按 D24 与用户 "首版不做回退, 回退与判断模型绑定" 改写: 判断模型的结论不直接驱动流程, 删去投机执行, 盲答异步复核, 投机写入上限 3, 屏障与推翻后的自动回退 (用户 11-12 对上限与自动回退的确认随之作废); 语义判断是正在干活的 Agent 步骤输出 schema 的必填字段, 没有 Agent 步骤处走保守分支, 判断模型配了只做提示, 由会话核实; 只留每个写入步骤前 Engine 私有引用下的 Git 快照 (不用暂存区), 作为用户停止实例后手动恢复的点, 不做任何自动回退.
- [定义 Reviewer 与正式关卡在 Engine 下的执行协议](issues/09-define-reviewer-protocol.md): 每个关卡按确定性检查, 提示类判断 (只在配了判断模型时), 冻结, 正式审核, 处置, 修复的顺序执行; 关卡结论只来自 Reviewer; Reviewer 是 graph 中的普通 Agent 步骤, 与被审工作分开的会话, 复审回到原 Reviewer 会话, 处置与修复回到原 worker 会话; 不设覆盖清单, 逐单元送入或每轮抽查, Reviewer 输出只经通用检查, 审核质量靠 Reviewer benchmark (用户 11-13, D15); 结果失效与轴复用由 Engine 按冻结输入机械判断; 就绪记录升到版本 8, 删除 haiku 回退; 每轮交付审核包 (相邻 diff, 前轮发现和台账, 确定性检查结果, 改动文件列表), Role 中可机械判定的检查项移到第 1 步确定性检查; 作者判 "无效" 的处置带回原 Reviewer 会话复审, Reviewer 仍坚持才交用户, 只为核对这类发现而开的复审轮计入轮次 (Main Agent 11-14 定); 轮次规则按 0.x 修好 G05 后的现行文字 (第 3 轮起只为行为缺陷开修复轮, 实施开始后只涉及 subject 措辞, 重复或一致性的问题任何轮次都可记 "记录不修"). 判断模型可选, 在审核中只做提示类 (预检, 输出检查, "修复是否解决发现 X"), 按用户 11-13 定下的四项目标 (高智能请求数, 整体墙钟, 上下文中规则与流程占比, 规则与流程误判率) 衡量; 提示类阈值以下不提示也不同步交高智能 Agent (D16); 范围类首版不启用, 不再预留依附已删 08 机制的接口, 以后要缩小复审另开 issue (D16, D24).
- [定义并行流程的读取与写入隔离](issues/10-define-parallel-flow-isolation.md): 11-14 按 D24 与批判审读一.5 简化: 每仓库一个写入令牌, 按进入等待的先后发放, 非持有实例只读工作区, 草稿写在 `.tmp`, 冻结输入取基准提交 (`HEAD`) 加草稿, 取得令牌后按与新 `HEAD` 的差异落盘; 删去树对象视图, 释放令牌的屏障, 跨实例推翻, 判断 `state` 的对象 ID 与通用的按输入对象 ID 复用, 多仓库取令牌留到 Application 工作流再定; 每个实例一个由 Engine 生成的 `.tmp/` 工作区, 不受令牌约束, 被忽略的共享路径只由写入链在工作区中写. 1.0 不提供 worktree 并行实施, 持有者等待用户时不让出令牌, 两处已由用户 11-13 确认.
- [确定现有 ARW 合同在 1.0 中的继承范围](issues/13-decide-legacy-contracts.md): 交付格式 (`.scratch` Artifact, Canonical ID, issue 格式) 与门禁语义 (Spec Readiness, Commit Audit, Reviewer 独立性) 原样保留, 执行机制改写, 旧握手与路径只作需求证据; 门禁与写入类命令从公开命令中删除, 改由 Engine 提供; Agent 要读的规则大幅减少, 大部分内置进 Engine, 其中多数机械执行, 少数由判断模型触发, 仓库仍经锁与受管区域分发缩减后的规则; 已采用的仓库在静止点一次性升级, 未完成的实施 issue 重跑 Spec Readiness; 锁升到 `lockSchemaVersion: 3` 使 0.x 关闭式失败; 保存 0.x 配置副本, 支持一次手工回退.
- [测量当前 ARW 流程的耗时分布](issues/12-research-flow-time-baseline.md): 本机近期实施交付中审核关卡耗时最多 (Claude Code 一侧等待 Reviewer 占 50%, Codex 一侧提交审核与 Spec Readiness 共 84%), 模型生成其次, 测试与命令约 12%; 每个实施 issue 中位数约 15 到 25 分钟; 提交审核通常 2 到 5 轮, 预检的收益主要在减少轮次.
- [确定判断模型与兼容端点的安装与配置](issues/20-decide-installation-and-configuration.md): 首版只需配置一个判断模型端点 (可不配, D24): 配置命令登记端点并做兼容核对与延迟测量, 不通过就不登记, Engine 照常工作; 首版不探测显卡, 不下载, 不生成开启脚本, 不让出 Strata, 不建防火墙规则. 以后有满足 18 使用条件的本机候选时 (When a qualified local model exists 节, 用户 11-13 D19 确认的四处仍有效): 配置命令探测显卡并按候选目录选第一个装得下且实测够快的本机候选, 否则机构内部端点, 公开端点需明确开启; 只收 llama.cpp 提供的 GGUF 模型, 经用户确认后下载并校验; 生成的 Node.js 开启脚本有 `start` 与 `stop`, 只绑回环地址 (Engine 在 WSL 时判断模型在 Windows 侧, 需一次性管理员放行规则), 只让出登记的显卡占用者, Strata 经其 lease 让出且不抢占, 开不起来时不出提示, 流程照常. Engine 登录时自启与入口的网络放行, 以及 harness 版本变化时对兼容端点角色先自检 (失败即停在可恢复状态), 首版照做.
