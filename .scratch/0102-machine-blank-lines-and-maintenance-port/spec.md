# 机器入口跳过空行, 维护端口移出动态端口段并保持跨版本互斥

## Problem Statement

本 effort 修复外部使用者报告中两个已复现的缺陷. 两者都要改长期规范中的合同, 所以合并在一个 issue 中, 由同一份 spec 统领.

**机器入口的空行.** `arw background-agent` 从标准输入逐行读取 JSONL 请求. 调用方经文本管道发送请求时, 管道常在请求之间或末尾加入空行: PowerShell 的文本管道会这样做, CRLF 文件里的空行切分后只剩一个回车. 现在每个空行都当作请求解析, 对每个空行返回一条 `{id: null, ok: false, error: {code: "background-agent-request-invalid", message: "Unexpected end of JSON input"}}`. 复现: 输入依次为空行, 一个合法的 `list_agents` 请求 (CRLF 结尾), 一个只含回车的行, 一个只含空格和制表符的行, 得到一条成功响应和三条 `id: null` 错误. 报告者因此无法判断哪个请求失败, 只能改用 Node 按原始字节发送. 长期规范的机器入口合同写着 "无法解析或不支持的请求返回错误", 没有把空行和请求区分开, 所以仅修改代码会与合同冲突.

**维护端口落入 Windows 排除范围.** 安装, 更新和卸载的控制进程, 以及正在启动的后台管理进程, 都以监听一个固定的 `127.0.0.1` 维护端口取得用户级互斥. 现在这个端口由当前用户名和家目录的散列值确定, 落在 50000-59999, 全部位于 Windows 默认动态端口段 (49152-65535) 内. Hyper-V, WinNAT, WSL 等组件在动态段内保留端口块, 保留范围随重启变化, 端口落入其中时监听以 `EACCES` 失败: 管理进程拿不到启动 lease 就退出, 客户端报 `manager exited during startup ... listen EACCES`, 安装或卸载则直接失败. 报告者遇到的正是这种情况. 维护者本机实测: 一次检查时排除范围含 59131-59530, 监听其中的 59150 得到 `EACCES`; 重启后的另一次检查为 50000-50059 (管理员设置的持久排除) 和 55731-56130, 位置已经变化. Linux 的默认临时端口段 (32768-60999) 也覆盖旧范围, 与回环出站连接撞上本机临时端口时监听报 `EADDRINUSE`, 维护流程把它误报为维护进行中.

单纯换端口会破坏现有的跨版本互斥. 源码入口和已安装入口启动的都是已安装的管理进程代码, 而升级时新版本的安装器运行时, 已安装的仍是旧版本. 新安装器只绑定新端口, 在它停止旧管理进程之后, 替换运行时文件之前, 另一个会话若需要后台服务, 就会启动旧代码的管理进程; 旧代码只检查旧端口, 能取得启动 lease, 于是在安装写入期间开始运行, 可能加载替换到一半的文件, 或与安装的离线恢复同时写数据库. 降级 (用旧版本的安装器覆盖新版本) 是对称的同一缺口. 长期规范要求取得互斥失败的一方在首次受管理写入前失败, 这个缺口违反该合同.

## Solution

机器入口把只含空格, 制表符或回车的行当作分隔噪声跳过, 不产生响应; 其他行的解析和错误响应不变.

维护端口移到 20000-29999, 不在 Windows 动态端口段和 Linux 临时端口段内. 此前版本使用的旧端口改称兼容维护端口, 由新版本的每个互斥持有者一同绑定, 所以新旧版本的安装器和管理进程启动无论哪一方先持有互斥, 另一方都会遇到端口占用而失败, 互斥跨版本成立. 兼容维护端口本身落在排除范围内时 (监听得到 `EACCES`), 旧版本同样无法绑定它, 新版本跳过它, 只持有新维护端口, 报告的故障因此不再出现. 控制端口不变.

## User Stories

1. 作为经 PowerShell 管道向 `arw background-agent` 发送请求的 Main Agent, 我希望管道加入的空行不产生错误响应, 以便每条错误响应都对应我发出的一个请求.
2. 作为发送了无法解析的非空请求的调用方, 我希望照常收到 `id: null` 的错误响应, 以便发现自己的输入错误.
3. 作为 Windows 用户, 我希望后台服务, 安装和卸载不因维护端口落入系统保留的动态端口块而失败.
4. 作为 Linux 用户, 我希望维护端口不再与回环连接的临时端口相撞而被误报为维护进行中.
5. 作为升级或降级 ARW 的用户, 我希望另一个会话在安装期间启动后台服务时, 旧版本代码的管理进程不会在安装写入期间开始运行.
6. 作为从源码仓库运行 ARW 而已安装的是另一个版本的维护者, 我希望客户端仍能识别另一个管理进程正在启动, 不把这种情况误报为启动失败.

## Implementation Decisions

### Blank lines in the machine entry

空行是去掉行尾换行后只含空格, 制表符和回车 (包括空字符串) 的行. 输入流末尾没有换行的剩余内容同样适用. 机器入口在解析之前跳过空行: 不调用 JSON 解析, 不写响应, 不占用请求 `id`, 不影响其他请求的执行顺序和结束条件; `--wait` 的行为也不变. 只要行中含有其他字符 (例如不完整的 JSON, 或空白之外的任何文字), 仍按现有规则解析, 解析失败返回 `id: null` 的 `background-agent-request-invalid` 错误.

空白集合取 JSON 语法本身的空白 (空格, 制表符, 换行, 回车; 换行已是分行符), 而不是 JavaScript 的全部 Unicode 空白: 这样跳过的恰是 JSON 解析器本来也会忽略的字符, 不扩大到 JSON 不接受的字符. 只含不换行空格等其他空白的行不是 JSON 合法输入, 仍返回错误.

被否决的方案:

- 保留现有错误: 合同上一致, 但这些错误不对应任何请求, 调用方只能逐条猜测, 报告者已因此改换发送方式.
- 跳过空行并在标准错误写提示: 提示没有可执行的处置, 只增加噪声.
- 按 `trim()` 判断: 会把 JSON 不接受的空白也当作空行, 与 JSON 的空白定义不一致.

版本过渡: 不需要. 机器入口在调用方自己的进程内运行, 解析结果不经过管理进程, 不写持久状态, 与管理进程之间的协议不变. 调用方使用哪个版本的入口, 就得到哪个版本的空行处理; 旧版本对空行返回错误, 没有调用方依赖这些错误.

### Maintenance and compatibility ports

两个端口由同一个散列值 `h` 确定: 对 `maintenance`, 当前用户名和家目录 (以 NUL 分隔) 取 SHA-256, 读前 4 字节为大端无符号整数. 维护端口为 `20000 + h % 10000`, 兼容维护端口为 `50000 + h % 10000`, 后者就是此前版本的维护端口. 控制端口 (30000-49999) 不变: 它没有故障报告, 而且改它会使新安装器连不上旧管理进程, 升级被阻断, 需要另一套过渡.

维护互斥的持有者有两类: 安装, 更新和卸载的控制进程, 以及正在启动的后台管理进程 (持有到控制端口可连接). 每个持有者按以下顺序取得互斥:

1. 绑定维护端口. 任何失败按原规则处理: 启动 lease 原样抛出错误, 不再绑定兼容维护端口; 维护流程把 `EADDRINUSE` 报告为维护或启动进行中 (busy), 其他错误报告为 `unknown`, 管理进程启动失败.
2. 绑定兼容维护端口. `EACCES` 时跳过兼容维护端口, 只持有维护端口; 其他任何错误 (包括 `EADDRINUSE`) 先释放已绑定的维护端口, 再原样抛出, 此后与第 1 步的同一错误同样处理.
3. 两个端口 (或跳过兼容维护端口时的一个) 一起持有到原规则规定的释放时刻: 维护控制进程实际退出时由操作系统释放, 管理进程在启动完成时释放.

跨版本的结果:

| 先持有互斥的一方 | 后来的一方 | 结果 |
| --- | --- | --- |
| 新版本持有者 (两个端口) | 旧版本持有者 (只绑兼容维护端口) | 旧版本遇到 `EADDRINUSE`, 失败 |
| 旧版本持有者 (兼容维护端口) | 新版本持有者 | 维护端口绑定成功, 兼容维护端口遇到 `EADDRINUSE`, 释放维护端口后失败 |
| 新版本持有者 | 新版本持有者 | 维护端口遇到 `EADDRINUSE`, 失败 |
| 兼容维护端口处于排除范围 | 任意版本 | 旧版本无法绑定, 任何管理进程启动和维护都失败, 与改动前相同; 新版本只持有维护端口, 新版本之间照常互斥 |

跳过 `EACCES` 是安全的, 因为排除范围对当前用户的所有进程同样生效: 此时没有旧版本进程能持有兼容维护端口, 也就不存在需要用兼容维护端口排除的对方. 若已有进程正在监听该端口, 绑定得到的是 `EADDRINUSE` 而不是 `EACCES`, 所以跳过不会漏掉已有的持有者. Windows 不会在已被占用的端口上新增排除范围.

两个新版本持有者的竞争不会死锁: 绑定不等待, 失败立即返回, 后来者先释放自己已绑定的端口. 并发时可能出现一方因另一方短暂持有维护端口而失败, 而另一方随后也因兼容维护端口被旧版本占用而失败; 这只发生在至少一方确实处于启动或维护中时, 按原有的失败语义重试即可.

客户端判断 "另一个管理进程正在启动" 时 (管理进程在控制端口可连接前退出), 依次探测维护端口和兼容维护端口, 任一个可连接就继续等待. 这样从新版本源码入口启动的客户端, 遇到旧版本已安装管理进程的启动 (只持有兼容维护端口) 时也不会误报启动失败. 探测连接到处于排除范围的端口只是连接被拒, 视为不可连接.

被否决的方案:

- 只换端口, 接受升级窗口: 实现只改一个常数, 但违反现有的互斥合同, 在多个会话同时使用后台服务的机器上, 一次安装期间有另一会话发出请求并不罕见; 后果是旧代码与安装写入并发, 难以排查. 补上缺口的代码量 (约 10 行) 与收益相称.
- 在长期规范中写明跨版本互斥不成立: 放宽的是安全与持久状态合同, 而保持合同的成本很低.
- 首选端口不变, `EACCES` 时按确定序列换下一个候选: 首选端口的排除解除后, 后来者能绑定首选端口而前一持有者在备选端口, 互斥出现缺口; 堵住它要求每个持有者和客户端探测整个序列, 代码与规范改动都比本方案大.
- 改用 Windows 命名管道或 Linux abstract socket 作互斥: 能彻底避开端口问题, 但改变架构与多处 "端口" 合同, 跨版本过渡问题与本方案相同, 额外收益只是覆盖动态段被调低的少数机器.
- 只改进 `EACCES` 的错误提示: 现有错误已带端口号, 根本问题仍在.

停止绑定兼容维护端口会重新打开与此前版本混用时的互斥缺口, 所以长期规范把它写成现行合同, 删除它需要另行决定. 接受的代价: 兼容维护端口仍在动态端口段内, Linux 上偶发的临时端口相撞仍可能把一次启动或维护误报为进行中 (重试即可), 与改动前相同; 只有维护端口本身处于新范围.

### Long-term specification changes

- 机器入口合同 (Agent Repository Workflow 长期规格的 Machine entry 节) 增加空行规则及其理由, 其他无法解析或不支持的请求仍返回错误.
- 安装长期规格的 Background Agent management 节写明控制端口, 维护端口和兼容维护端口的关系, 维护端口的范围及其理由; Uninstallation 节的互斥段落写明两个端口的绑定顺序, `EACCES` 的跳过规则, 跨版本互斥的理由, 以及停止绑定兼容维护端口会重新打开与此前版本混用时的互斥缺口, 删除需另行决定; 安装事务, 卸载步骤, Module Interface 和测试描述中 "绑定固定维护端口" 的写法改为 "取得维护互斥".
- Agent Repository Workflow 长期规格中客户端判断另一管理进程正在启动的规则改为任一维护端口可连接.

## Testing Decisions

机器入口沿用现有的进程内测试: 用内存流向机器入口送入无效请求, 合法请求和空行混合的输入, 观察响应行. 在现有 "无效请求不执行" 测试的输入中加入空字符串行, 只含回车的行, 只含空格和制表符的行 (包括位于末尾且没有换行的一行), 以及一行只含不换行空格的行, 观察空行不增加响应, 执行的操作不变, 只含不换行空格的行与其他非空的无效请求一样各得到一条 `id: null` 的 `background-agent-request-invalid` 错误. 这防止空行再次产生错误响应, 也防止把不完整的 JSON 或 JSON 不接受的空白当作空行吞掉 (即回归到 `trim()` 语义).

维护互斥沿用现有的真实回环端口测试 (守护进程与客户端测试已用临时端口验证 `EADDRINUSE` 和 busy 结果):

- 用两个临时端口作为维护端口和兼容维护端口. 只在兼容维护端口上监听 (模拟旧版本持有者) 时, 维护流程返回 busy, 且维护端口随即可以重新绑定, 证明失败前已释放; 新版本持有互斥时, 单独绑定兼容维护端口 (旧版本的行为) 得到 `EADDRINUSE`. 这防止跨版本互斥缺口回归, 以及失败后遗留端口占用.
- 其他绑定错误: 以无效端口号 65536 作兼容维护端口时, 启动 lease 以原错误 (`ERR_SOCKET_BAD_PORT`) 拒绝, 维护端口随即可以重新绑定; 以 65536 作维护端口时, 启动 lease 以同一错误拒绝, 作兼容维护端口的临时端口仍可绑定. 这证明错误不被吞掉, 失败前释放已绑定端口, 维护端口失败后不再绑定后续端口. 维护流程把这类错误报告为 `unknown` 是不变的既有行为, 不另加测试.
- 兼容维护端口绑定得到 `EACCES` 时跳过: 用 Linux 上非特权用户无法绑定的低号端口作兼容维护端口, 观察启动 lease 成功取得, 维护端口被占用. 该测试先直接探测低号端口, 当前环境绑定不报 `EACCES` 时 (Windows, root) 跳过, 因为这是操作系统行为, 不为测试增加注入接缝. 跳过只由错误码 `EACCES` 决定, 代码与平台无关; Windows 排除范围报同一错误码 (外部报告原文为 `listen EACCES`, 维护者本机也复现), 所以 Linux 上的观察覆盖 Windows 的同一分支. 不另做 Windows 测试: 在 Windows 上制造该错误需要管理员权限新增排除范围, 或依赖当前随重启变化, 可能为空的保留范围, 都不带来新的证明.
- 客户端探测: 在现有 "管理进程退出而另一管理进程正在启动" 的客户端测试中, 把正在监听的端口放在兼容维护端口的位置, 维护端口为关闭端口, 观察客户端仍继续等待到预算用尽, 而不是报告启动失败.
- 端口值: 断言维护端口在 20000-29999, 兼容维护端口等于维护端口加 30000, 防止维护端口回到动态端口段.

不做真实跨版本安装测试: 跨版本行为完全由两个端口上的绑定结果决定, 上述测试已在真实端口上制造每种持有关系; 真实安装两版本的测试成本高, 不增加可观察的证明.

## Out of Scope

- 控制端口不变.
- 不为动态端口段被调低, 或管理员在 20000-29999 内设置排除范围的机器增加回退.
- 不决定何时停止绑定兼容维护端口.
- 不改变机器入口其他请求的解析, 关联和错误合同.

## Module Design

### Modules

后台 Agent 客户端 Module 继续拥有端口计算, 启动 lease 和维护互斥的取得, 新增的责任只是把兼容维护端口纳入同一次取得. 机器入口 Module 继续拥有 JSONL 分行和请求校验, 新增空行跳过. 后台管理进程, 安装和卸载 Module 的责任不变, 仍只调用客户端 Module 取得启动 lease 或维护互斥.

### Interfaces

- 客户端 Module 的维护端口计算从返回一个端口改为返回维护端口和兼容维护端口的有序数组, 前者在先.
- 启动 lease, 维护互斥, 客户端和守护进程创建的端口参数从单个维护端口改为该有序数组, 默认值取上述计算结果. 数组第一个端口是维护端口, 其后的端口按兼容维护端口的规则绑定. 启动 lease 的结果不再返回所绑定的端口 (没有使用者), 仍提供 `release` 和 `unref`; `release` 释放全部已绑定端口.
- 启动 lease 的错误: 维护端口的任何绑定错误原样抛出, 不再绑定兼容维护端口; 兼容维护端口的 `EACCES` 被跳过, 其他错误在释放维护端口后原样抛出. 维护互斥按原规则处理启动 lease 的错误: `EADDRINUSE` (无论来自哪个端口) 返回 busy, 其他错误返回 `unknown`.
- 机器入口的输入合同增加空行跳过; 响应格式, 错误码和 `id: null` 的使用条件不变.

### Seams and Adapters

不新增 Seam 或 Adapter. 安装与卸载仍经已有的维护交接 Seam 调用维护互斥; 测试通过已有的端口参数传入临时端口, 不改生产代码的注入方式.

### Dependencies and Data Flow

依赖方向不变: 守护进程, 已安装管理进程入口, 安装与卸载依赖客户端 Module 的启动 lease 和维护互斥, 客户端 Module 不依赖它们. 端口值只在客户端 Module 内由用户名和家目录计算, 经参数向下传递; 不写配置或持久状态. 机器入口读取的行在进程内解析后交给运行时, 空行在解析前丢弃, 不进入运行时.

### Module Design Rationale

兼容维护端口的绑定放在启动 lease 一处, 因为管理进程启动和安装维护都通过它取得互斥, 放在一处才能保证所有持有者按同一顺序绑定同一组端口; 分别在调用方处理会让两类持有者的跨版本规则各写一份. 代价是启动 lease 从单次绑定变为带跳过与释放的两步取得, 这些分支只能经真实端口测试观察. 端口参数改为有序数组而不是新增一个兼容端口参数, 因为测试已经通过这个参数传入临时端口, 数组让测试能显式给出两个临时端口, 不会在测试中绑定真实用户的兼容维护端口. 代价是数组位置带有含义, 调用方须把维护端口放在第一位; 生产调用方都使用默认值, 只有测试显式传入. 跳过规则只针对 `EACCES`, 因为只有它能证明其他进程也无法持有该端口; 其他错误不能证明这一点, 所以仍使取得失败. 空行判断放在机器入口的分行处, 因为空行是传输层的分隔噪声, 不是请求, 不应进入请求校验. 代价是被跳过的空行不出现在任何响应或诊断中.

### ADR Evaluation

权威来源不变: 端口仍由用户名和家目录确定, 不读配置. 不增加持久状态; 互斥仍由操作系统在进程退出时释放端口, 恢复合同不变. 后台 Agent 用户级管理的现有 ADR (`docs/adr/0030-use-user-wide-background-agent-management.md`) 所述 "独立的固定本机回环维护端口" 仍然成立, 兼容维护端口是长期规范中的版本兼容规则, 可随以后的决定删除, 不改变该 ADR 的取舍, 不需要新 ADR. 机器入口的空行规则只放宽了无意义输入的处理, 不涉及架构边界.
