# ADR 格式

ADR 位于 `docs/adr/`, 并使用连续编号: `0001-slug.md`, `0002-slug.md` 等.

仅在首次需要 ADR 时按需创建 `docs/adr/` 目录.

## Template

```md
# {决策的简短标题}

{用一到三句话说明: 上下文是什么, 做出了什么决定, 以及原因.}
```

仅此而已. ADR 可以只有一个段落. 它的价值在于记录*做出了*什么决定及其*原因*, 而不是填满各个章节.

## Optional sections

只在确实能增加价值时加入以下章节. 大多数 ADR 都不需要它们.

- **Status** 前置元数据 (`proposed | accepted | deprecated | superseded by ADR-NNNN`) - 在重新审视决策时有用
- **Considered Options** - 只在被否决的替代方案值得保留时加入
- **Consequences** - 只在需要指出不明显的下游影响时加入

## Numbering

扫描 `docs/adr/`, 找到已有的最大编号并加一.

## When to offer an ADR

必须同时满足以下三项:

1. **难以撤销** - 日后改变主意的代价不可忽略.
2. **没有上下文就会令人意外** - 未来读者看着代码会问: "他们为什么这样做?"
3. **真实取舍的结果** - 存在真正的替代方案, 并因具体理由选定其中一个.

如果决策容易撤销, 不创建 ADR, 因为以后只需撤销它. 如果它并不令人意外, 没有人会追问原因. 如果不存在真实替代方案, 除了"我们采用了显而易见的方案"以外, 就没有需要记录的内容.

### What qualifies

- **架构形态.** "我们使用单一仓库." "写入模型采用事件溯源, 读取模型投影到 Postgres."
- **上下文之间的集成模式.** "订单和计费通过领域事件通信, 而不使用同步 HTTP."
- **具有锁定效应的技术选择.** 数据库, 消息总线, 认证提供方, 部署目标. 不包括每个库, 只包括需要一个季度才能替换的选择.
- **边界和范围决策.** "客户数据由客户上下文拥有; 其他上下文只能通过 ID 引用它." 明确的否定与肯定同样有价值.
- **有意偏离显而易见的路径.** "由于 X, 我们使用手写 SQL, 而不使用 ORM." 包括任何合理读者会预期相反做法的情形. 这些记录可避免下一位工程师"修复"本来有意做出的选择.
- **代码中不可见的约束.** "由于合规要求, 我们不能使用 AWS." "由于合作方 API 合同, 响应时间必须低于 200 ms."
- **否决原因不明显的替代方案.** 如果因细微理由考虑 GraphQL 后选择 REST, 记录它, 否则六个月后会有人再次建议 GraphQL.
