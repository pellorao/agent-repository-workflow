# 仓库写作规则

遵循以下由仓库拥有的语言, 格式, 编码和文档约定. 保留逐字来源和字面语法. 保持术语与 `CONTEXT.md` 和适用 ADR 一致.

仓库自己编写的文档默认使用中文普通自然语言, Agent 规则文档也必须使用中文. 每份文档的普通自然语言必须完整使用中文或英文之一, 不得混用.

文档的预期语言和最低比例由仓库根 `arw.config.json` 的 `languageChecks` 声明. 写作时遵循适用规则, 验证时消费检查结果, 不根据当前文字比例推断预期语言或自行选择阈值. 未配置, 未覆盖或无法判断的结果按 [验证规则](validation.md) 处理. Upstream 来源合同继续决定内容是否允许改写; 允许改写时, 修改后的普通自然语言仍须统一使用配置要求的语言.

长期文档必须独立表达当前有效的规则, 设计和必要理由. 不得把 `.scratch` 下的短期工作记录作为引用目标, 依据或理解其含义所必需的上下文 (长期文档可以描述 `.scratch` 的通用结构, 路径语法和操作合同, 也可以使用不对应真实工作记录的示例路径). 如果短期工作记录中的决定需要长期保留, 把该决定及其必要理由写入拥有相应责任的长期文档, 不保留指向短期记录的引用.

在中文或英文文档中, 保留必须精确且不属于普通自然语言的文字. 这包括已在治理文档中建立的身份名称, 命令, 字段, 状态值, 路径, 代码标识符, 外部平台名称, 代码, 测试夹具, 逐字来源, 以及已建立的模块或 Interface 名称.

在中文文档中, 只有属于这类精确文字的英文内容才保留原文. 一个词来自常见技术领域或工作流, 不足以使它成为精确文字. 如果中文能够在不损失合同含义的情况下表达普通叙述, 则使用中文.

这些精确文字不决定文档语言, 也不构成中英文混写. 文档语言选择与标题合同相互独立. 模板或公共标题合同要求的精确英文标题不会使中文文档变成混合语言文档.

对于由 Workflow Distribution 投射的规则, 以目标仓库内安装的版本为准. 投射后的 Agent 指引必须能够独立使用, 不得依赖 Source Checkout 或仓库外的全局文档, 也不得为每份文档重复记录来源信息. Repository-owned 区域只记录本仓库新增的规则或对 Baseline 的明确例外, 不得重复 Baseline 内容.

除非有明确的仓库例外, 所有由 Agent 管理的文本必须是没有 BOM 的有效 UTF-8, 并使用 LF 换行符.

编写或修改会创建临时文件或目录的仓库代码前, 读取 `environment.md`.

在 Agent 责任内的文件中创建或重命名文件或目录时, 不得在任何新路径组件中使用 `#` 或 `:`. 选择新路径时应用这项规则.

由 Agent 管理的文档和规划产物使用英文文件名. 该规则不适用于引入的第三方资源. `.scratch` 下的 ARW Artifact 还必须遵循跟踪器路径语法, 当后者更具体时以它为准.

不得手动强制换行 Markdown 散文. 在源码中让每个段落保持自然的一行, 由渲染器负责换行.

## Minimal sufficient contracts

当多个方法都满足已确认需求并保留所有必要保证时, 选择规则, 状态, 数据源和机制更少的方法.

如果某个方法的副作用不会改变已确认结果, 不会违反现有合同, 也不会产生具体可预见的风险, 而消除它会增加不成比例的复杂性, 则接受该副作用. 不要只因为存在副作用就排除这个方法.

- 只实现满足已确认需求和履行现有责任所必需的内容. 不得为假设的未来需求增加机制.
- 模块, 工作流, 验证和实施过程只承担已确认的责任. 不得仅因其内部步骤还能继续拆分, 就逐层为这些步骤新增独立协议, 关卡, 记录或证据链. 只有现有合同或具体可预见的风险要求独立边界时, 才增加这些机制.
- 删除没有当前使用者或兼容责任的机制.
- 默认信任普通运行环境. 只有在适用合同要求或具体可预见的风险证明有必要时, 才增加验证, 防御机制或证据. 不得为纯理论上的恶意调用方或极不可能的状态建立无限的自我验证或证据链.
- 每个事实只保留一个权威来源. 不得在配置, 文档和代码中重复同一事实. 在拥有某项责任的文档中陈述规则. 其他文档引用该规则, 不得复制它.
- 目标不是减少行数. 必要的复杂实现可以保留在小而完整的 Interface 后面.
- 最小充分性不表示削弱必要保证. 不得仅为减少规则或代码而删除必要功能.

## Common capabilities

- 编写代码前, 检查现有公共模块和公共方法, 能复用的尽量复用.
- 当同一责任分散在多个位置时, 优先把它提取为公共方法或公共模块.
- 是否提取能力取决于其责任是否真正通用, 而不是当前调用方的数量.
- 不得创建只转发调用且没有隐藏任何复杂性的公共包装器.
- 公共能力仍须遵循最小充分合同. 不得仅因能力通用, 就在没有已确认需求时为方法和模块增加选项或扩展点.

## Baseline exceptions

Repository-owned 规则可以增加, 收紧或专门化 Baseline. 任何放宽 Baseline 要求的规则, 都必须在拥有该规则的文档的 Repository-owned 区域中明确声明为 Baseline 例外.

## Batch operations

多个数据项需要执行相同的文件系统, 进程, 数据库或远程服务操作时, 优先判断能否批量处理. 如果批处理能够减少重复访问, 且保留授权, 顺序, 可观察结果, 失败处理, 事务和资源边界, 就合并为一次操作, 或按资源上限分批处理. 只读操作也可以一次取得完整数据后在内存中处理.

只有当多个写入共享同一次授权和同一个事务时, 才批量写入. 批量写入必须保留原有的失败报告, 重试和恢复结果. 如果操作需要独立授权, 逐项隔离失败, 保持语义顺序, 或缺少安全的批处理 Interface, 则分别执行.

## Code comments

只为复杂或不明显的行为添加注释. 只有当行为, 设置, 返回结果或重要边界情况无法从代码和 Interface 中清楚看出时, 才为公开方法使用详细的 `/** ... */` 注释块.

## Markdown structure

模板规定的标题结构和固定文字必须保持不变, 其中的占位符则替换为当前文档的实际值. 当没有固定模板时, H1 跟随文档语言, H2 和更深的标题全部使用英文.

`CONTEXT.md` 在 H1 中替换其上下文名称, 并精确保留 `## Language`.

当内部链接目标必须在多个命令解释器之间保持可复制时, 使用 ASCII 锚点和稳定的英文路径.

## Specification design presentation

本节适用于 effort spec 和长期规范. 规范面向理解项目基本概念但没有参与形成该设计讨论的读者. 正文必须包含理解当前合同所需的前提, 不得依赖原始对话补足关键因果或行为边界.

对重要或不直观的规则, 说明触发该规则的情境, 它防止的问题或风险, 要求的行为, 可观察结果, 以及理解当前选择所需的理由. 按内容关系组织这些说明, 可以在一个自然段或场景中完成, 不要求逐项设置字段. 理由解释为什么需要该约束或边界, 不得只复述要求.

应为读者呈现其需要理解的每个设计维度. 当设计包含对象之间的关系, 责任交接, 随时间发生的变化, 状态转换, 数据流, 分支或参与者之间的交互时, 必须呈现这些维度, 不得只把每个元素描述为孤立的静态陈述, 让读者自行重建设计.

使用场景表达包含阶段, 分支或恢复的行为时, 说明正常阶段怎样衔接. 对失败场景, 说明失败发生在哪个阶段, 已经产生和没有产生的影响, 以及修正输入, 重试或停止时从哪个合同边界继续. 场景应消除这些行为歧义, 无需为没有相应风险的简单规则虚构阶段或失败路径.

选择能最清晰, 简洁地表达每个维度的形式. 可用形式包括自然语言段落, 有序或无序列表, 表格, 时间线, 场景序列和 Mermaid 图, 但不限于这些形式. 有序列表通常适合线性过程, 表格适合比较或责任映射, 流程图适合分支或数据流, 时序图适合少量参与者之间的多次交互.

一种表示方式足够时只使用该方式. 当散文, 列表或表格更清晰时, 不得强制要求图, 也不得用多种形式重复同一设计. 没有关系或时间维度的独立事实, 局部属性和简单约束可以保留为简洁的静态陈述, 无需补充不适用的理由或场景.

规范中的测试设计应说明测试制造的情境, 观察的公开结果, 以及该观察防止的错误. 可以集中说明多个测试共用的背景, 但不得用实现导航, 内部辅助程序清单或穷尽测试表代替可观察行为.

列表和表格可以陈述规范性要求. Mermaid 图必须准确呈现它所覆盖的关系或过程, 并与周围文字一致. 用它阐明设计, 不得把它作为规范性要求的唯一来源. 在文字中陈述精确边界, 失败行为和例外.

交付规范前, 从上述读者视角检查完整正文. 对每项适用设计, 读者应能回答为什么需要它, 正常怎样运行, 失败怎样处理, 以及怎样证明它有效. 如果答案仍依赖原始对话, 补足文档. 对简单规则只检查适用的问题, 保持其表达简洁.

## Repository terminology

使用含义不明显的保留术语时, 在当前位置提供简短解释, 并可以链接到术语表中的定义. 仅将短语首字母大写或用反引号包裹, 不能代替解释.

当范围内的 Markdown 使用根 `Output Text` 允许的新名称时, 添加标题精确为 `Terms introduced in this document` 的章节. 每个列表项只包含名称及其普通语言解释. 没有新名称时不得添加空章节.
在只有一个 H1 的文档中, 把 `Terms introduced in this document` 放在任何必要的已渲染元数据之后, 作为第一个 H2. 在有多个 H1 章节的文档中, 如果第一个 H1 是文档概述, 把它放在第二个 H1 中. 否则把它作为第一个 H1.
在 `Terms introduced in this document` 中只保留名称和解释列表. 所有后续普通散文必须从另一个准确标题开始. 对正文原本没有标题的文档添加术语章节时, 添加一个陈述原有正文责任且不改变其含义的标题.
